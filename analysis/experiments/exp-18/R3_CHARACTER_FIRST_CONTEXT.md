# EXP-18 R3 — ガラクタ主体の棄却とキャラクター主体への転換

更新日: 2026-08-29（UTC）  
状態: 文脈・データモデルの再設計。実装は行わない。  
前提: [R2 局所可読・全体把握不能](./R2_CORE_REJECTION_AND_SYSTEM_SCALE.md)

## 0. 結論

「ガラクタや機体そのものを組み合わせるゲーム」を既定案から外す。

中核は、**数人〜十数人の永続するキャラクターと、多数の装備・技能を組み合わせる編成RPG**へ変更する。

ガラクタ、遺物、魔導具、武器などは残してよい。ただし、組み替えられる材料は装備・技能であり、プレイヤーが好き嫌いを抱く対象は人物にする。

> 人物は残る。装備と技能と役割が変わる。

これにより、同じ決定的戦闘・行動権・反応権・条件技能のコアを使いながら、後から次を追加できる。

- キャラクターの立ち絵、表情、戦闘アニメーション。
- 性格、好き嫌い、譲れないこと。
- 仲間同士の会話と関係。
- 装備に対する反応。
- 勝敗やプレイヤーの構築履歴を反映した短い物語。
- キャラクターごとの成長や葛藤。

SCRAP FRONTIERは技術的な仮称として残してよいが、世界観と本編名は未決定へ戻す。

## 1. なぜ機械・ガラクタ主体を疑うか

機械テーマには利点がある。

- 部品交換を説明しやすい。
- 行動順、電力、接続、準備を可視化しやすい。
- 少ないアートでも成立しやすい。
- 固有名詞より共通文法を作りやすい。

一方、長期ゲームでは大きな欠点がある。

### 1.1 個体が交換可能に見える

機体をフレームと部品へ分解すると、現在弱い機体を解体し、強い機体へ交換することが自然になる。これは材料即興には向くが、「この人物を使い続けたい」という感情と衝突する。

### 1.2 成長の主語が部品になる

「この子が強くなった」ではなく「強い部品へ替えた」になりやすい。後から立ち絵を貼っても、プレイヤーの認識が装備スロットの入れ物なら、愛着は生まれにくい。

### 1.3 物語のフックが弱い

敗北、連続行動、仲間の救援、無理な準備、特定装備の酷使は、人物なら性格と関係へ接続できる。無人格な機体では、機能説明か雰囲気に留まりやすい。

したがって、アートや物語を後付け可能にするだけでは不十分である。最初からデータと戦闘の主語をキャラクターにする。

## 2. 推奨する世界観の幅

現時点ではファンタジー、SF、学園などを固定しない。

最も柔軟なのは、**遺跡や辺境を探索する少人数の遠征団**である。

- 人物: 永続する仲間。最初は6〜8人、将来8〜12人程度。
- ガラクタ: 遺跡で拾う武器、遺物、魔導具、技能書。
- 戦闘: 4人編成。
- 遠征: 全員が同行し、戦闘ごとに前へ出す4人を選ぶ。
- 後方: 休息、回復、支援、次戦準備を担当。
- 後半: 複数小隊や複数前線へ発展し、仲間全体を使う。

この枠なら、将来次のいずれにも寄せられる。

- 王道ファンタジーの冒険者。
- 魔導技術の学園・研究部。
- 崩壊世界の回収屋。
- 宇宙遺跡の調査隊。

「ガラクタ」は世界観の主役ではなく、キャラクターが自分なりに使う材料として残る。

## 3. キャラクターのデータモデル

一人のキャラクターは次を持つ。

### 3.1 固定部分

- characterId: 保存・アート・台詞・戦闘ログを結ぶ永続ID。
- 固有will: 好き、嫌い、譲れないことを一文ずつ。
- 固有能力1個: その人物を選ぶ機械的理由。
- 基礎傾向: HP、速度などの小さな差。
- 成長候補: その人物が習得しやすい技能群。
- 表現フック: 戦闘イベントへ反応するID。

### 3.2 可変部分

- 実戦技能4枠。
  - アクティブ2枠。
  - リアクティブ2枠。
- 装備2枠。
- 指揮役なら、小隊指揮効果1個。
- スキルツリー上の取得。
- 遠征中のHP損傷と一時状態。

固有能力は外せない。残りの技能・装備は組み替えられる。

これにより、人物は単なる外見ではなく機械的な個性を保つ。一方で、好きな人物を装備と技能で別の役割へ伸ばせる。

## 4. 固有能力の原則

固有能力は、特定の名前を持つ相手との専用コンボにしない。

悪い例:

- 「キャラクターAとキャラクターBを同時編成すると攻撃力+30%」
- 「BだけがAの準備を短縮できる」
- 「このキャラクターがいなければ撃破連鎖を作れない」

これでは好きな人物を使う自由が減り、特定キャラ待ちになる。

良い固有能力は共通動詞へ接続する。

- 敵破壊時に行動権を回復する。
- 味方が準備を始めたとき、反応権を使って一段進める。
- 防壁が残った状態で被弾すると反撃する。
- 最低HPの敵への攻撃を強化する。
- 味方の行動が反復されたとき、自分も追撃する。
- 仲間が倒れたとき、一度だけ割り込んで守る。

同じエンジンを始動・補助・完了できる人物や装備を複数用意する。人物は強く個性的だが、一組だけの指定コンボにはしない。

## 5. キャラクター原型

名前と外見は未決定とし、機械的個性とwillだけを先に置く。

| 仮ID | 固有will | 固有能力 | 作れるエンジン |
|---|---|---|---|
| executioner | 「自分が決着をつける」 | 敵破壊時、行動権を1回復 | 撃破連鎖、単体処刑 |
| artillery | 「準備不足では撃たない」 | 準備後の攻撃が全体化し威力上昇 | 溜め砲撃、反復 |
| courier | 「待たされるのが嫌い」 | 味方の準備開始時、反応権で一段進める | 即時砲撃、遅延短縮 |
| mimic | 「面白いものは自分でも試す」 | 味方の完了行動を一度だけ反復 | 砲撃反復、回復反復 |
| guardian | 「誰も置いていかない」 | 防壁のある味方への攻撃を一度引き受ける | 防壁反撃、集中防御 |
| tuner | 「一番困っている人から直す」 | 最低HPの味方への支援効果が増える | 持久、損傷管理 |
| gambler | 「安全な勝ち方には興味がない」 | 条件を満たすと大幅強化、外すと行動権を失う | 高天井、条件構築 |
| leader | 「全員に役目を作る」 | 戦闘ごとに共有技能4候補から一つを指揮効果として選ぶ | 柔軟な補完、混成編成 |

これは完成キャストではない。固有willが、戦闘能力、台詞、将来の物語で同じ人物像を指すかを確認するための原型である。

## 6. 装備と技能の役割

### 6.1 装備

装備は単なる攻撃力上昇にしない。次のいずれかを行う。

- 技能を一つ追加する。
- 対象条件を変える。
- コストを変える。
- 発動条件を別の資源へ変換する。
- 明確な利点と代償を同時に持つ。

例:

- 処刑剣: 最低HPの敵を優先し、破壊時の行動権回復を増やす。ただし他の敵への威力低下。
- 二重詠唱具: 準備技能を反復する。ただし最大HP低下。
- 身代わり盾: 後衛への攻撃を引き受ける。ただし自分の行動順低下。
- 未完成の触媒: 一回目の大技を即時化するが、以後の反応権を失う。
- 旅装: 戦闘出力は低いが、遠征後の損傷を軽減。

### 6.2 技能

技能は多く取得してよいが、実戦へ持ち込むのは一人4枠に限定する。戦闘中の読み量を抑えながら、戦闘前の構築空間を大きくする。

技能取得後は好きな人物へ付けられるものを主とし、一部だけ人物固有または習得制限を持たせる。固定職業へ人物を閉じ込めすぎない。

## 7. 好きなキャラクターを使えること

キャラクターゲームにするなら、好きな人物が弱いので使えない状態を主な難易度にしない。

### 必須条件

- 初期加入人物も終盤まで成長できる。
- レベル差または成長差の追いつき手段がある。
- どの人物も、少なくとも複数の一般エンジンへ参加できる。
- 固有能力だけで役割を固定しない。
- 特定人物を使わないと取得不能になる重要報酬を置かない。
- ランダム加入順はあっても、主要キャストの永久取り逃しを作らない。
- 好きな人物を使うことが、分析用の捨て試合やおつかいにならない。

人物ごとの強弱はあってよい。全員を同じにしない。ただし、装備・技能・指揮役によって「この人物を中心に強い構成を作る」余地を残す。

## 8. 全員をどう使うか

常時戦闘するのは4人までとし、取得した仲間全員は遠征へ同行する。

待機人物は、単なる倉庫にしない。

候補:

- 戦闘を外れるとHPを回復する。
- 一人だけ後方支援能力を選ぶ。
- 戦闘間に装備を調整・修理する。
- 次の敵の一部情報を明らかにする。
- 連戦で前衛と交代する。
- 後半の複数小隊・二正面で実戦へ出る。

ただし後方支援専用キャラクターは作らない。全員が前衛4人の候補であり、休息時にも役割がある。

## 9. アートワークを後から追加するための設計

### 9.1 人物単位の安定ID

キャラクターの機能を装備データへ埋め込まず、characterIdを中心に保存する。

後から次をcharacterIdへ接続できる。

- 立ち絵。
- 顔アイコン。
- 表情差分。
- 戦闘中の小さなアニメーション。
- 台詞。
- テーマ色。
- 装備表示位置。
- 物語イベント。

### 9.2 戦闘イベント

戦闘エンジンは、数値結果だけでなく人物の出来事を保存する。

- onSkillStart
- onKill
- onActionRefund
- onChainContinue
- onChargeStart
- onChargeInterrupted
- onProtectAlly
- onLowHp
- onAllyDown
- onVictory
- onEquipmentTrigger

後から、処刑役が五連続で敵を倒したときの表情、守護役が仲間を庇ったときの台詞、準備を止められた砲術役の反応などを付けられる。

物語は戦闘と無関係な文章量ではなく、実際に起きた構築結果へ人物が反応するところから追加する。

### 9.3 装備のアートコスト

人物は8〜12人程度に抑え、立ち絵と表情を重点的に作る。多数の装備・技能は、原則としてアイコン、色、短いエフェクトで表現する。

これにより、大量の固有キャラクターを作らず、少人数への愛着と大きな構築空間を両立する。

## 10. キャラクター化の失敗リスク

| 失敗 | 回避 |
|---|---|
| 人物が装備スロットの入れ物になる | 外せない固有能力とwillを一つ持たせる |
| 固有能力が強すぎて編成固定になる | 共通動詞へ接続し、同じ役割を別人物・装備でも供給する |
| 好きな人物が弱く使えない | 4技能と2装備で役割を拡張できる。追いつき手段を持つ |
| 仲間が増えてベンチになる | 全員同行、休息・後方支援、後半の複数小隊 |
| 指定キャラコンボ待ちになる | 人名を条件にした技能を作らない |
| 人物が多すぎて誰にも愛着が湧かない | 初期6〜8人、完成でも8〜12人程度に抑える |
| ストーリーが戦闘と分離する | 戦闘イベントと構築履歴から人物反応を作る |
| アート待ちで実装が止まる | 最初は色・名前・一文will。characterIdとイベントだけ先に固定する |
| ランダム加入で好きな人物を逃す | 永久取り逃しを作らず、加入順または出会い方だけ変える |

## 11. R2の規模案への反映

R2の「機体フレーム6種」を、次へ置き換える。

- 初期キャラクター6〜8人。
- 各人に固有能力1個とwill。
- 共有アクティブ技能12種。
- 共有リアクティブ技能12種。
- 装備12〜18種。
- 指揮効果4種。
- 実戦は4人。
- 取得した全員が遠征へ同行。
- 第二小隊は物語とシステムの進行後に開く。

組み合わせ爆発は、人物数を大量に増やすのではなく、少人数の固定個性と多数の技能・装備の積から作る。

## 12. 既存実装の扱い

frontier/の参照コアは引き続き教材として保存する。

ただし、ram、echo、capacitorなどの機体名や「小隊を機械として扱う」データモデルを、本編UIへ直接持ち込まない。

将来の純粋エンジンは、次の汎用語彙を使う。

- actor / character
- activeSkill
- reactiveSkill
- equipment
- party
- actionPoint
- reactionPoint
- combatEvent

世界観固有の名前はコンテンツデータと表示層へ置く。これにより、人物や世界観を変更しても戦闘規則を再実装せずに済む。

## 13. 次の設計課題

次はキャラクターの名前や物語本文を書く段階ではない。

1. 6〜8人の固有willと固有能力。
2. 共有12アクティブ、12リアクティブ、12〜18装備。
3. 少なくとも六つの一般エンジン。
4. どの人物も複数エンジンへ参加できる対応表。
5. 戦闘イベントから将来の表情・台詞を付けられる契約。

この五つを同時に設計する。

キャラクターの可愛さを後付けの見た目にせず、「誰が、何を信じ、どんな強さを作り、戦闘中に何をしたか」が機械的にも記録される土台を先に作る。
