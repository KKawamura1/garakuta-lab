## 2. 根城 — 帰る場所

R11 §2.4 は「詰所へ器材を返したあと、5人は自分たちの根城へ帰る。廃屋を直した家。
拾ってきたもので少しずつ増えていく。**日常の場面と設定の厚みはここに置く**」と
書いていた。R12 の時点で、この家は**どこにも無かった**。画面は「灰の中」か
「詰所（ギルド）」しかない。

### 2.1 二つの層

`ecology/content/homestead.mjs` に二つを置いた。

- **家にあるもの（FIXTURES、9件）** — 会話ではない。進行に応じて増える。
  直しかけの家、帳簿と目録、体調の記録、朝の火、棚、二冊の帳面、返す物の籠、
  壁の写し（設計図が3件貯まると出る）、空いた席
- **日常の場面（SCENES、6件）** — 一行送りの会話。条件を満たした順に**一つずつ**出る

**引かない。**同じ進行なら同じ順で同じ場面が出る（`nextHomesteadScene` は
「条件を満たす、まだ見ていない最初のもの」を返すだけ）。既読印は `storyFlags` に
押す（`homestead:<id>`）。一度見た場面は根城の画面から読み返せる。

### 2.2 名簿を根城へ移した

R12 §7.6 は「名簿がギルド画面のタブに埋まっている。そこまで見に行くかは分からない」を
未確認事項として残していた。**答えは、置き場所を変えることにした。**

精算の次のボタンを「根城へ帰る」にして、遠征のたびに一度必ず通る場所にした。
名簿はその画面の中にある。ギルドのタブ（「根城」）からも同じ画面が開く。

精算の締めの一行（R12 §4.B）が既に「器材を詰所へ返し、それから根城へ帰る」と
書いていたので、**文が先にあって画面が無かった**状態を解消した形になる。

### 2.3 行数の上限を、ここでは持ち込まなかった

R9 §7 の「1断片2〜6行」は Stage の断片（opening / join / stageEnd / 幕間）の縛りで、
**学習順を壊さないための上限**である。根城は戦闘と学習の外にあるので、同じ上限を
持ち込む理由が無い（作者判断）。`story.test.mjs` では 3〜12行を固定してある。

R12 §4.5.6 が「足りなければ、次に触るのは行数の上限そのもの」と書いていた通りの
場所で、**join を厚くするのではなく、根城を厚くする**という選び方をした。

## 3. 図鑑 — 会った敵の記録

R8 §3.2 は ProfileState に「図鑑」を挙げていたが、R12 の時点で未実装だった
（`app.js` の `codex` は装備の未入手一覧であって図鑑ではない）。

### 3.1 三層に分けた

| 層 | 開く条件 | どこにある |
|---|---|---|
| 狙い（`ENEMY_TARGETING`） | 一度でも会った | 戦闘前の敵カード / 図鑑 |
| 噂（`ENEMY_LORE`、R12 §4.B） | 一度倒した | 戦闘前の敵カード / 図鑑 |
| **図鑑の節（`ENEMY_CODEX`）** | **5体倒した** | 図鑑だけ |

**会っていない敵は名前も出さない**（R12 §4.E-1 と同じ線）。

`ENEMY_CODEX` は20体ぶん。**噂を繰り返さない**——実装中に一度、噂をそのまま
一行目に書いてしまい、画面で同じ文が二段に並んだ。`story.test.mjs` に
「図鑑の節が噂を繰り返していない」を固定してある。

**灰殻が何なのかは、ここでも説明しない**（R11 §2.1）。書いたのは観察と、台帳の
書き方と、拾い屋の側の折り合いの付け方だけである。

### 3.2 数え方

`profile.bestiary` に `{ seen, defeated }` を持つ。**同じ戦闘に何体いても、その敵種は
一戦で一回**（個体数で数えると群れの敵だけが極端に早く開く）。会ったことは
遠征を捨てても消えない——**負けても取り消されない**、というのがこの記録の意味である。

Profile の schema が一欄増えるので、`contract-snapshot.json` を作り直した。
差分は `freshProfile.bestiary: {}` の一行だけで、他の凍結値は動いていない。

## 4. 台詞量（R12 §5.3 への答え）

R12 は幕の断片でスミを4→6行、レイを3→7行にしたうえで「**まだ薄い**」と残した。
根城の場面がその続きである。

| 人物 | R12 時点 | いま（Stage 断片 ＋ 根城） |
|---|---:|---:|
| シキ | 26 | 26 ＋ 5 = 31 |
| ナズナ | 21 | 21 ＋ 6 = 27 |
| カイ | 15 | 15 ＋ 7 = 22 |
| **スミ** | **6** | **6 ＋ 8 = 14** |
| **レイ** | **7** | **7 ＋ 10 = 17** |

薄かった二人だけを厚くした。`story.test.mjs` に下限を固定してあるので、
減らす変更をしたら落ちる。

置いた場所の分担は R12 のままにしてある。**join は新入りの紹介だけ、関係は幕間、
日常は根城。**

## 5. 世界の声の残り

R12 §4.B が三か所（敵カード・設計図・精算）へ載せたあと、**必ず止まるのに全文が
システム文だった画面**が三つ残っていた。

- **報酬画面** — 「持てるだけ持って帰るのが拾い屋ではない」など4文を戦数で回す
- **野営治療** — 「戻せるのは、いま受けたぶんだけ」（R11 §4 のナズナ）
- **敗北画面** — 「退がるのに理由は要らない。進むほうに理由が要る」（R11 §2.2）

**会話ではない。**誰かの台詞にすると R9 §7 の断片の勘定に入るので、地の文として
置いた。決定性も守っている（戦数と到達戦数から引く）。

生成装備には拾われ方の一行を付けた（R8 §3.1「偶然性の主語は装備」）。
**品そのもの（affix の本数と耐久）から決まる**ので、同じ品なら同じ一行が出る。
効果の言い換えは書かない（それは readout の仕事）。

## 6. main の取り込みで直したこと

この作業の前段として、main（`codex/shorter-combat-character-gating`）を取り込んだ。
main と R12 は「Campaign で登場していない人物を出さない」という同じ問題に、
別々の答えを実装していた。

- main … `progression.mjs` に `availableCharacterIds` を足し、engine 側で解放を決める
- R12 … `app.js` に `metCharacterIds` を足し、画面側で解放を決める

**engine 側を唯一の規則にした。**`metCharacterIds` は `availableCharacterIds` を読んで、
現在の同行者を足すだけになった。画面側で二つ目の判定を持つと、いつか片方だけずれる。

main の補給タブ・タイトルへボタン・freeRoster の人数調整は残した。ギルド見出しの
「PER CHARACTER / n / 8」と「未登場の仲間は…」は R12 §4.E-1 に合わせて消した
（**まだ会っていない人の数を割らない**）。
