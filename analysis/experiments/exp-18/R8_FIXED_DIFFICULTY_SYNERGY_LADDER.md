# EXP-18 R8 — 固定難易度パックとコンボ発見ラダー

作成日: 2026-08-31（UTC）  
対象: EXP-18 Phase B 完了後の戦闘構築、難易度0〜5、Phase C着手前  
状態: 設計提案。コード変更・作者プレイによる支持はまだない。  
前提: [R4 創発的ルール生態系](./R4_EMERGENT_RULE_ECOLOGY_AND_LONG_TERM_EXPANSION.md)、[R6 長期進行](./R6_LONG_TERM_PROGRESSION_PROCEDURAL_LOOT_AND_BLUEPRINTS.md)、[R7 実装順序](./R7_IMPLEMENTATION_SEQUENCE_AND_PARALLEL_CONTENT_EXPANSION.md)、[A9 Phase B実装結果](./A9_PHASE_B/RESULT.md)。

## 0. 結論

現状は「選択肢が無い」のではなく、**単体で強い技能・装備を役割ごとに配るだけで十分で、複数要素を一つの機関としてつなぐ必要が薄い**。作者が考えた大溜め構成も、現行の実測では最良の素朴な役割配分に対して約1.09倍に留まる。さらに、4パック中3パックをseedで選ぶため、遠征ごとの差は「一系統だけ欠ける」4通りしかなく、難易度を上げても学ぶ構築言語がほぼ同じである。

次を採用する。

1. 難易度0〜5のcampaignではパックをランダムにしない。難易度ごとに固定する。
2. 現在の4パックから2つを使い、全6組を難易度0〜5へ一度ずつ割り当てる。
3. 各難易度には一つの正解ではなく、**設計された相互作用の道を2本以上**と、設計者が答えを固定しない余白を置く。
4. 技能・装備は `発生源 → 変換器 → 利得先` の共通イベントでつなぐ。特定の技能名・人物名を鍵にしない。
5. 各利得先には発生源を2つ以上、各発生源には利得先を2つ以上用意し、部品の一つを別物へ差し替えられるようにする。
6. 敵は想定コンボの鍵穴にせず、その難易度の相互作用が単体強化より有利になる圧力をかける。
7. seed乱数は、固定された世界の中での敵順・報酬・装備rollへ残す。パック乱数は難易度20後のFree / Endlessへ移す。
8. Phase Cの生成装備へ進む前に、まず難易度0〜1だけを実装し、人間が相互作用を発見して次の仮説を持つか確認する。

この変更は、R4の「完成セットを同時に納品しない」を捨てるものではない。**閉じた三点セットは作らないが、相互作用が生まれる接続面は意図して設計する**、という修正である。

## 1. 現状診断

### 1.1 単体強化が勝つ理由

現行contentには大溜め、急かす、準備の螺旋、行動権装備、撃破時AP等の接続候補がある。しかし次が重なっている。

- 通常攻撃と汎用回復だけでも十分な出力があり、条件付き技能をつなぐ必要がない。
- 条件を満たしたコンボも、多くは「同じ一発を早める」「小さい量を足す」だけで、仕込み人数・RP・技能枠に対する超過利得が小さい。
- activeは不成立ならskipして次へ進むため、下位に技能を足すことがほぼ不利益にならない。枠を全部強い技能で埋める方が、専門化して枠を絞るより弱くなりにくい。
- 固定装備には、同じruleで耐久だけが違う系列が多い。選択が「どのイベントをつなぐか」より、同じ効果の強い版を取る比較になりやすい。
- 現在のパックは主に分類箱で、パック同士の境界に「このeventを出す側」「読む側」という契約が不足している。
- 難易度0〜5は主にbudget・mutation・round・補給を変えるが、使用パックが難易度と結びつかないため、前難易度の強い汎用構成をそのまま使いやすい。

### 1.2 ランダム3/4パックの限界

`PACKS_PER_MANIFEST = 3` かつ全4パックなので、可能な語彙集合は4通りだけである。各遠征で75%のパックが残り、baselineも常在する。これは事故防止には良いが、次の二つを弱める。

- 難易度を越えたときに「今度は別の理論で組む」という大きな切替が起きない。
- 設計者が敵・報酬・boss lawとパックの接続を調律しにくい。何が出るか分からないため、どの構成にも通る薄い圧力へ寄りやすい。

乱数が必要なのは世界の文法ではなく、**固定された文法の中でどの部品がいつ来るか**である。

## 2. 目標体験

難易度を一つ進めたとき、プレイヤーに次が起きる。

1. 開始画面で使える2パックと敵の圧力を見て、「今回は何をつなげられるか」を予想する。
2. 単体で強そうな技能を並べた構成では、途中までは進めても完走できない。
3. 戦闘ログか敗北から、二つのeventがつながる可能性に気づく。
4. 少なくとも一人を発生源、別の一人を変換器または利得先として組み替える。
5. 連鎖が画面上で明確に発火し、以前の構成では越えられなかった局面を大きく越える。
6. クリア後に「自分の構成は○○を△△へ変えていた」と一文で説明できる。
7. 次の難易度ではパックの組が変わり、同じ完成構成は使えないが、eventを読む考え方は転用できる。

重要なのは、設計されたコンボ名を当てることではない。**入力・変換・出力を自分で発見し、別の部品へ差し替えること**が遊びである。

## 3. Campaignの固定パックラダー

現在の4パックを次の記号で表す。

- E: 刃と撃破 (`pack_edge`)
- C: 手当てと余剰 (`pack_care`)
- W: 防壁と隊列 (`pack_wall`)
- T: 行動権と準備 (`pack_tempo`)

4種類から2種類を選ぶ組はちょうど6通りある。これを難易度0〜5へ一度ずつ置く。

| 難易度 | 固定パック | 主に学ぶこと | 前難易度から残る言語 |
|---:|---|---|---|
| 0 | C + W | 被害を集め、受け、回復し、余りを再利用する | 導入。最も因果を追いやすい |
| 1 | W + E | 防御の種類と隊列を読み、守りを攻撃機会へ変える | W |
| 2 | E + T | 準備へ手数を集め、撃破から次の撃破へつなぐ | E |
| 3 | T + C | AP / RP / 回復を循環させ、手番を必要な人物へ渡す | T |
| 4 | C + E | HPを危険にさらす攻撃と回復を一つの往復にする | C |
| 5 | W + T | 位置・未使用資源・防壁を手番へ変える | 既習2系統の未見の組。capstone |

難易度0→4は一つ前のパックを一つ残す。既知の言語を足場に一つだけ新しい言語を学ぶ。全6組を一度ずつ通る都合で難易度5だけ直前と共通パックが無いが、WもTも既に学習済みであり、**既知の二要素を初めて接続する最終問題**として使う。

### 3.1 manifestの扱い

campaign用manifestはseedからpackを選ばない。

~~~ts
type DifficultyScenarioDef = {
  id: string;
  rank: 0 | 1 | 2 | 3 | 4 | 5;
  enabledPackIds: [SkillPackId, SkillPackId];
  enabledEquipmentFamilyIds: EquipmentFamilyId[];
  enemyFamilyIds: EnemyFamilyId[];
  actBossIds: [EnemyActorId, EnemyActorId, EnemyActorId];
  regionLawIds: string[];
  pressureTags: string[];
};
~~~

- rankは固定scenarioを一つ参照する。
- seedはencounter内の許可された編成、報酬順、装備rollを決める。
- 使えるパック、装備family、主要敵family、boss lawは遠征開始前に全て表示する。
- Blueprint持込はR6どおりmanifest外でも機能する。ただし持込枠が少ないので、過去の完成機関を丸ごと輸入できず、一つの「外国語」を今回の2パックへ接続する役目になる。
- 難易度0〜5クリア後にFree Expeditionを解禁し、そこで現在のrandom manifestを再利用する。campaignの学習順と、長期の組合せ変化を分ける。

## 4. コンボを作る共通文法

### 4.1 `発生源 → 変換器 → 利得先`

強い構成は、固有名詞ではなく共有eventの経路として記録する。

| 役割 | 意味 | 現行例 |
|---|---|---|
| 発生源 | 後段が読める事実・状態・余りを作る | `excess_healing`、`actor_moved`、`damage_blocked`、`actor_defeated`、`preparation_started` |
| 変換器 | あるevent / resourceを別の価値へ変える | 急かす、受け返しの集中、救急の小袋、拾い直し |
| 利得先 | 集めた価値を大きな結果へ変える | 大溜め、範囲攻撃、止めの一突き、強い回復・防壁 |
| 制動・代償 | 無料循環と万能化を止める | RP、AP、HP、耐久、round / battle limit、位置、準備時間 |

単体で働くというR4の原則は維持する。ただし価値配分を次のようにする。

- 単体: 採用理由はあるが、汎用の最良行動を常に上回らない。
- 二部品: 条件を意識すれば、単体強化より明確に得をする。
- 三部品以上: 敵圧力と合えば、素朴な役割配分を大きく越える。ただし別の敵圧力では代償が出る。

### 4.2 閉じたレシピを避ける接続条件

各難易度の設計レーンは、次を満たす。

- 一つの利得先へ到達する発生源が2つ以上ある。
- 一つの発生源を読む利得先または変換器が2つ以上ある。
- 想定構成から少なくとも一部品を同じ役割の別部品へ交換できる。
- 同じeventを技能・装備・人物signatureのうち二領域以上が扱う。
- 発生源と利得先を同一装備一個へ閉じ込めない。高rarityの複数rule装備でも、チーム側の別eventがあるほど強くなる形にする。
- 敵は特定SkillIdを要求せず、速度・対象数・guard・block・位置・継続時間・resource pressureのいずれかを変える。

この2×2以上の接続を、**open engine**と呼ぶ。設計者が用意するのはレシピではなくopen engineの地形である。

### 4.3 「全部載せ」が常に得になる問題

activeは条件不成立時にskipするため、枠へ追加することが弱くなりにくい。content調整だけで「強い技能を全部載せる」を止められない場合、技能数とは別に小さい装備容量を導入する。

~~~ts
type SkillLoadoutCost = 1 | 2;
type ActorSkillCapacity = {
  active: number;
  reactive: number;
};
~~~

- 狭い条件の橋渡し技能は原則cost 1。
- 広く強い汎用技能はcost 2。
- slot数3〜4はUI上の上限として維持し、capacityは強い技能を何個積めるかの上限にする。
- 第4枠の永続投資は維持する。必要なら後でcapacity投資を別にするが、Phase B直後に同時実装しない。

これは即時採用ではない。まず固定パックとcontent再配分を測り、それでも「枠を埋めるほど常に得」が残る場合のmechanics pack候補とする。

## 5. 難易度0〜5の設計された接続面

以下の「設計レーン」はUIへ完成レシピとして表示しない。content review、balance fixture、敵設計の参照点である。各難易度で2本を成立させたうえで、探索が別のevent経路を見つける余地を残す。

### Difficulty 0 — C + W: 被害の流れを作る

設計レーン:

1. 身代わりで被害を一人へ集める → 被弾後の受け流し／防壁 → 手当て・応急手当 → 余剰治療を別人物へ渡す。
2. 衝撃に備える／初手の構え → `damage_blocked` → 受け返しの集中 → 次の回復または防壁を強める。

敵圧力:

- 単発の重い攻撃と小さい分散攻撃を混ぜる。
- どの攻撃をblockし、どれをHPで受けるかが見える。
- 時間切れは緩くし、最初は因果を読む余裕を置く。

想定外の余白:

- 回復を増やす以外に、被害を誰へ集めるか、barrierをいつ壊すか、RPを防御と余剰治療のどちらへ使うかで別構成が生まれる。

### Difficulty 1 — W + E: 守りを攻撃機会へ変える

設計レーン:

1. block → 受け返しの集中 → 単発攻撃または範囲攻撃の一撃を増幅する。
2. 位置替え → 踏み固め／移動後の集中 → 行・列・後衛狩りで配置価値を回収する。

敵圧力:

- 高guardの前列と、後列の支援敵を同時に置く。
- 単発・多段・貫通のどれか一つだけが常に正解にならないよう、block chargeとguard量を分ける。
- row / columnの両方に一度は価値が出るが、どちらかを必須鍵にはしない。

### Difficulty 2 — E + T: 仕込みと撃破連鎖

設計レーン:

1. AP追加／号令／急かす／準備の螺旋 → 溜め突き・大溜め。投入した手数とRPが、単なる斬撃連打より大きな一発へ変わる。
2. 傷口を開く／HPを削る → 止めの一突き → 拾い直し／仕留めの鈴 → 得たAPで次の対象へ移る。

敵圧力:

- 制限時間のある高価値対象と、撃破連鎖に使える小型敵を混ぜる。
- 全体を一発で薙ぐだけ、bossへ単発を積むだけの双方に代償がある。
- 準備を完全無効にせず、急いで完成させる、守る、別対象から先に倒すの三経路を残す。

### Difficulty 3 — T + C: 手番と治療の循環

現行contentだけではこの接続が薄いので、最初のbridge contentが必要である。

設計レーン:

1. healing_applied／excess_healing → RPまたはAPへ変換 → 号令・行動権の循環 → 必要な人物がもう一度行動する。
2. APを一人へ集めて重症者を連続治療 → 余剰分を別人物へ渡す → 余ったRPを別の手番変換へ使う。

追加候補:

- 「自分の回復で余剰が出たとき、RP1を払い、回復対象へAP1。round 1回」のreactive。
- 「APを受け取った人物の次のutility後追撃を強める」装備rule。

敵圧力:

- 同時に全員を削らず、治療対象が時間で移る。
- 波または準備攻撃で「誰へ次の手番を渡すか」を問う。
- 回復量だけを積むとround制限に負け、APだけを回すと損傷に負ける。

### Difficulty 4 — C + E: 危険と回復の往復

現行contentには回復と攻撃を強く往復させるeventが不足するため、一系統だけmechanicsを追加する。

設計レーン:

1. HPを代償にする高威力攻撃 → 応急手当の対象になる → 余剰治療を別人物へ渡す。
2. 実ダメージまたは過剰ダメージ → 小回復へ変換 → 回復eventを別の反応が読む。逆方向には、余剰回復を次の攻撃のmarkまたは増幅へ変える。

追加候補:

- recoil attackを一つの共通costとして追加する。
- `damage_applied` の実量をhealへ変えるreactive、または `excess_healing` を次のdamage増幅へ変えるruleを追加する。
- 両方を一度に追加せず、まず片方向だけで測る。

敵圧力:

- 防御だけではround制限、攻撃だけでは自己損傷で崩れる。
- 回復無効や吸収無効は置かない。速度、継続、対象順でsoft pressureを作る。

### Difficulty 5 — W + T: 盤面を資源機関にする

設計レーン:

1. 位置替え／敵による移動 → 踏み固め・移動後集中 → AP / barrierのどちらへ変えるか選ぶ。
2. 号令でAPを配る → 使い切る人物と、静観レンズ／カイのsignatureで未使用APを防壁へ変える人物を分ける → 次roundの手番または防御へつなぐ。

追加候補:

- `barrier_broken` または `block_spent` をAPへ変えるreactive。ただしRP1、round 1回を持たせる。
- `actor_moved` を読む装備は、同じ集中付与の耐久違いを増やさず、AP・block・barrierの別出力へ分ける。

敵圧力:

- row攻撃とcolumn攻撃を予告し、空き枠と位置替えの価値を出す。
- 短期の大打撃と長期の資源枯渇を幕ごとに入れ替える。
- 位置固定を完全禁止せず、厚い防御で受ける、先に倒す、動いて変換するの三経路を残す。

## 6. パックと装備contentの作り直し方

### 6.1 4パックの密度を揃える

現行はEへ攻撃技能が多く、C / W / Tはutility・reactive寄りである。固定2パックにすると、この偏りがそのまま難易度間の火力差になる。各パックを少なくとも次へ近づける。

- active 4〜6。うちoffense 3以上。
- reactive 4〜6。
- passive 0〜2。
- 発生源、変換器、利得先を各1つ以上。
- 自パック内で閉じる道1本、他パックへ開くeventを2種類以上。

offenseは単純な別倍率にしない。Cなら与ダメージと回復、Wならblock / barrier / position、TならAP / preparation / markを攻撃eventへ接続する。

### 6.2 content review表

新技能・装備ごとに次を記録する。

| 欄 | 記録内容 |
|---|---|
| 単独価値 | 相方なしで何をするか |
| event出力 | 何を発生させるか |
| event入力 | 何を読むか |
| 代償 | AP / RP / HP / 耐久 / 位置 / 制限 |
| 自パック接続 | 同じパックの別候補2つ |
| 他パック接続 | 別パックの候補2つ以上 |
| 代替部品 | 想定レーンの何と交換できるか |
| 苦手圧力 | どの戦場で単体最良でなくなるか |

「想定相方は技能X」だけの行は不合格とする。

### 6.3 装備

単純装備は比較基準として一部残してよいが、報酬の主食にしない。

- 同じruleで耐久だけが1 / 3 / 4と違う系列は、rarity表現へ寄せ、別装備三品としてpoolを薄めない。
- 装備familyを各difficulty scenarioへ固定し、使える技能eventを読む品が十分出るようにする。
- 一品が発生源と最大利得先を両方持つ自己完結装備を量産しない。
- Phase Cの生成装備は、affixへ `source / converter / payoff / stabilizer` role tagを持たせる。
- 複数rule品は原則として異なるroleを組み合わせる。単純に同じ出力を二倍にしない。
- Blueprint持込品はmanifest外で動くが、その一品だけで前difficultyの完成構成を再現しない。

## 7. 敵と難易度の役割

パック固定だけでは、結局一番強い単品を積む問題が残る。敵は、相互作用が必要になる**breakpoint**を作る。

各scenarioは次を持つ。

- 素朴な役割配分が到達できる地点。
- 二部品の接続で越えられる最初の壁。
- 三部品以上のopen engineで安定して越えられるboss。
- 別の性能ベクトルでも越えられる第二・第三経路。

敵を想定コンボ専用鍵にしない。

- 「準備を使わないと倒せない」ではなく、短いdeadline、高い単体耐久、小型敵の存在で準備と撃破連鎖の価値を上げる。
- 「回復禁止」ではなく、損傷の対象と時点を変え、回復先と手番配分を問う。
- 「移動必須」ではなく、行・列予告とguard配置で、移動・貫通・先行撃破のいずれも成立させる。
- boss lawは遠征開始時に見せ、少なくとも三つの対応方法をcontent reviewへ記録する。

rankの数値上昇は残してよいが、同じscenario内の調律に使う。rankが変わる主な体験差はpack pair、enemy pressure、boss lawである。

## 8. 発見を画面へ返す

コンボが内部で起きても、作者が因果を読めなければEXP-18以前の失敗を繰り返す。

### 8.1 戦闘前

- 「有効パック」「主なevent」「敵の公開法則」を一画面で見せる。
- 完成レシピや推奨人物は出さない。
- 技能・装備に `発生: 余剰回復`、`反応: 余剰回復` のような入出力チップを出す。
- 装着画面で、現在の小隊が出しているeventと、それを読むruleの件数を表示する。0件の入力は警告するが、自動装備はしない。

### 8.2 戦闘中

- event chainを同じ色または線で短く表示する。
- 例: `身代わり → 被弾 → 受け流し → 手当て → 余剰治療`。
- AP / RP / HP / 耐久を何点使い、最終的にdamage / heal / barrier / actionを何点増やしたかをまとめる。
- 同じruleの連続発火は折り畳むが、起点と最終結果は隠さない。

### 8.3 戦闘後

- 「最も長い連鎖」「最も結果を変えた連鎖」「未使用だった入力」を一件ずつ出す。
- 発見済み連鎖をcodexへ保存する。名称はプレイヤーが付けられるようにする。
- 設計者が用意したコンボ名を解除するのではなく、実際のevent pathを保存する。
- 敗北時は、あと一部品で接続できる場合にevent名だけをhintとして出してよい。完全な装備表は出さない。

## 9. 機械検査

面白さは人間が判断する。機械は「単体強化だけで十分」「想定レーンが実際は足し算」「一つの万能構成が全scenarioを支配」を検出する。

### 9.1 scenario固定

- 同rank・異seedで `enabledPackIds` が一致する。
- rank 0〜5で全6 pairが一度ずつ現れる。
- 各パックは3回現れる。
- campaignで未指定packが混入しない。
- Free / Endlessのrandom manifestとcampaign saveを混同しない。

### 9.2 素朴な基準と設計レーン

各scenarioに、探索を使わない固定buildを置く。

1. 単純役割配分の全探索。
2. 設計レーンAのfull buildと、発生源・変換器・利得先を一つずつ外したablation。
3. 設計レーンBの同じ比較。
4. 前scenarioの代表buildを、使用可能技能だけ残してbaselineで穴埋めしたtransfer build。

最初の調律目標:

- 素朴な最良buildは序盤を越えられるがbossを安定完走しない。
- full buildはtarget scenarioを完走できる。
- full buildから接続の中核一つを外すと、耐久倍率または到達戦数が明確に落ちる。
- AとBは技能・装備fingerprintが異なる。
- transfer buildが新scenarioをそのまま完走しない。

固定値の候補として、full buildが最良ablationを20%以上、素朴な最良を50%以上上回るかを診断表示してよい。ただし数値を見る前にscenarioごとに登録し、funの合格証にはしない。

### 9.3 未知コンボ探索

現在の「強いpairを数える」方法は、同じruleの耐久違いや探索ノイズを別コンボとして数える。今後はSkillIdのpairではなく、event pathでclusterする。

~~~text
preparation_started
  -> advance_preparation
  -> preparation_completed
  -> damage_applied
~~~

- pathは長さ2〜5のevent / effect型列へ正規化する。
- 同じruleで数値・耐久だけが違う装備は同じclusterにする。
- 成功buildの主要path、消費資源、最終出力、ablation差を記録する。
- 設計レーンA / Bと異なるclusterを「未知候補」として人へ返す。
- 本数だけをGateにしない。再現性とevent列を確認する。

### 9.4 支配性

- 全6scenarioの成功buildで、同一技能・装備が採用率70%を越えたら診断する。
- baselineだけで全scenarioを完走したら失敗。
- 一つのBlueprintを持ち込むだけで全scenarioの代表buildが同じになる場合は失敗。
- 新敵が一packを完全無効化する場合は失敗。
- 「高rarityへ交換」だけで勝率が単調増加し、event fingerprintが変わらない場合は装備content失敗候補。

## 10. 人間評価

難易度0と1を1〜2遠征ずつ遊び、次を見る。

支持信号:

- 開始時に二つ以上の技能・装備を挙げて「これがつながりそう」と予想する。
- 敗北後に、数値を上げる以外の変更を行う。
- 戦闘後に自分のevent chainを一文で説明できる。
- 設計レーンと異なる代替部品を一つ以上使う。
- 難易度1で、難易度0の完成構成を再現しようとせずWの知識だけを転用する。
- クリア後に別の接続を試したい、または次の固定pairを見たいと言う。

失敗信号:

- 係数またはrarityの大きい順に装着し、完走する。
- pack pairを見ず、全難易度で同じ人物・同じ優先順になる。
- 連鎖は発火しているが、何が起点で何を得たか説明できない。
- 設計レーンだけが唯一解で、部品を一つ変えると全て成立しない。
- 敵が特定技能の所持検査に見える。
- 敗北後の選択が永続鍛錬または難易度低下だけになる。

## 11. 実装順序

Phase Cへ直行せず、次の小さい順で進める。

### Step 0 — 現状固定

- mainのcontent / engine / difficulty versionを記録する。
- 現行の素朴な最良、作者構成、event fingerprint、各pack pairの代表値を保存する。
- 既存のrandom manifestをFree用として残せるfixtureを作る。

### Step 1 — 固定scenarioの器だけ

- `DifficultyScenarioDef`を追加する。
- 難易度0と1だけを固定pairへする。
- 技能・装備・敵の数値はまだ変えない。
- 同rankでseedを変えてもpackが変わらないことを確認する。

### Step 2 — Difficulty 0 content

- C / Wの密度を最低限揃える。
- 現行語彙だけで設計レーン2本を成立させる。
- 敵はencounter層だけを調整し、unit / rankの数値と同時に動かさない。
- 機械検査後、作者が一遠征遊ぶ。

### Step 3 — Difficulty 1 content

- Wを維持し、Eとの接続面だけを追加する。
- D0のW技能を上位互換へせず、D1で意味が変わるようにする。
- 作者がD0の知識を転用しつつ、同じ完成構成を捨てたか見る。

### Gate — Phase Cへ進む条件

次を満たすまで生成装備を量産しない。

- 作者がD0 / D1のどちらかでevent chainを一つ説明できる。
- 素朴な役割配分が最良のままではない。
- 設計レーンの少なくとも一つに代替部品がある。
- 戦闘後表示から起点・代償・最終利得を追える。
- 次に試す別構成が作者の言葉で残る。

満たした後、D2、D3、D4、D5を一つずつ追加する。D3〜D5で必要な新event / cost / effectはmechanics pack一系統ずつに分ける。

### Phase Cへの反映

生成装備は固定scenarioを薄めるのではなく、接続面を広げる。

- affix familyはscenarioごとに固定する。
- source / converter / payoffの出現比率をmanifestへ記録する。
- 報酬4候補が全て同じroleにならない。
- 一遠征中に、最低一つの発生源とそれを読む候補が到達可能であることを決定的に検査する。
- ただし毎runで完成engineを保証しない。baselineで進み、途中取得で計画を変えられる範囲にする。

## 12. R4・R6・R7への修正点

この票が採用された場合、次を新しい判断とする。

| 既存記述 | 修正 |
|---|---|
| R4 §3.3「完成セットを同時に納品しない」 | 閉じた固有名詞セットは禁止を維持。open engineの接続面と2本以上の設計レーンは意図して作る |
| R6 §5.2「最初は4パック中3つを有効」 | campaign難易度0〜5は固定2パック。random 3パックはFree / Endlessへ移す |
| R6 §13.2 Difficultyは主にmodifier | rankは固定scenarioを参照し、pack pair・enemy pressure・boss lawも明示差分にする |
| R7のcontent wave | 単品数ではなく、pack密度とcross-pack event接続を受入条件へ追加する |
| Phase C生成装備 | D0 / D1でコンボ発見が人間支持されるまで量産しない |

維持するもの:

- 人物名・特定技能名・特定装備名をengine条件にしない。
- 各要素は相方なしでも最低価値を持つ。
- baseline攻撃・回復・防壁を残す。
- hard counter、属性鍵、不可視乱数を使わない。
- 同じ入力から同じevent列を返す。
- 機械検査をfunの証明にしない。

## 13. 採用しない代案

### 単純に敵をさらに強くする

素朴な構成もコンボ構成も同率で苦しくなる。コンボの超過利得が小さい問題は直らない。

### 全技能を弱くし、特定セットだけ極端に強くする

相方を引くまで死んだ選択肢になり、作者がレシピを当てる所持品検査になる。

### パックを毎戦変える

12戦の途中で学習と構築がリセットされ、遠征固有の機関を育てる感覚が残らない。パックは一遠征中固定する。

### 難易度ごとに正解buildを一つ事前登録する

初回のパズルにはなるが、既知後のreplayを失う。登録するのは最低2本の設計レーンとevent接続条件までにする。

### 先にPhase Cの生成装備を大量追加する

現在の単体強化中心の文法を数百品へ増幅し、原因分離と作り直しを難しくする。まず少数の固定contentで相互作用の質を支持させる。

## 14. 最終的に目指す状態

難易度は、敵の数値が増えるだけの階段ではない。

> 難易度を一段進むたび、使える二つの言語が変わる。  
> プレイヤーは設計された接続面を手掛かりに、自分の機関を発見する。  
> 前の完成品は持ち込めないが、eventを読む知識は残る。  
> campaignで六つの接続を学んだ後、random manifestと生成装備が未知の組を作る。

この順なら、序盤には設計された手応えを置き、後半には開発者も知らないコンボを見つける余地を残せる。
