# エージェント代理プレイ：手順と事前登録

## 目的

人間の初見は1設計につき生涯1回しか使えない。この希少資源を節約するため、AIエージェントに同じルールを同じ情報条件でプレイさせ、**候補設計の順位付けに使える代理指標**が成立するかを調べる。

目標は感情語の再現ではない。狙うのは**認識状態の軌跡**、すなわち「何を予想し、何に困り、何で評価が変わったか」の系列である。感情の強度は自己申告させず、行動とログから機械計算する。

## 情報条件

エージェントが見るもの（人間のUIと同じ範囲）:

- 現在のHP・修復材・戦闘番号
- **次の敵だけ**の名前・HP・攻撃・装甲・特徴文
- 駆動列5枠と予備部品、それぞれの効果説明文
- 直前の戦闘の全巡回ログ、部品別の働き、余った資源
- 報酬候補3個

見せないもの:

- 将来の敵の数値、乱数シードの内部状態
- 敵の`rage`・`heat`係数の数値（特徴文でのみ示唆される）
- 部品の内部実装、勝てる配置の探索結果

## 禁止事項（総当たりの防止）

学習ログ#14が示したとおり、全配置を列挙できる主体は「隠れた正解を当てるパズル」の不快さを体験しない。したがってエージェントには次を禁じる。

1. `core/` `agents/` 以下のソースを読むこと
2. 戦闘結果を試算するスクリプトを書くこと
3. セッションファイルを直接編集すること
4. 同じ意思決定点をやり直すこと

エージェントは `agents/session.mjs` のCLI出力だけを見て、1回ずつ決める。

## 手順

```bash
node agents/session.mjs rules
node agents/session.mjs start  --session=<path> --seed=<n> --player=<id>
node agents/session.mjs act    --session=<path> --json='{"type":"place","partId":"p3","slot":2}'
node agents/session.mjs act    --session=<path> --json='{"type":"battle","prediction":"ギリギリ","worry":"装甲","worryText":"..."}'
node agents/session.mjs finish --session=<path> --json='{"replay":3,"bestMoment":"...","pivot":"あった","runStory":"..."}'
```

戦闘の直前には必ず勝敗予測と現在の最大の不安を、報酬取得時には必ず理由と認識更新の種別をコミットさせる。**結果を見た後で「驚いたか」を聞かない。** 驚きは予測と結果の差として機械計算する。

## 対照

同じコアを、認識トレースを持たない2つの機械方針でも走らせる。

- `naive`：予備部品を先頭から5枠へ入れ、以後動かさず、報酬は常に候補1を取る
- `local`：現在の敵だけを見て、入替と隣接交換を3回まで山登りする（GATE v2の局所探索プレイヤー相当）

`local` は全敵の内部数値を参照する。人間相当の情報条件ではなく、機械的最適化の下限・上限を示すための対照である。

## 事前登録された予測

エージェントを走らせる前に記録する。結果を見てから基準を動かさない。

- **P1 勝敗と面白さの分離**：認識指標（`problemChainRate`・`reinterpretationRate`・`deadTime`の少なさ）が、勝ったランを一律に高く評価しないこと。人間ログでは勝利は再プレイ度に対して −0.75 だった。勝ちを高く評価する指標は、面白さではなく強さを測っている。
- **P2 死に時間の検出**：無傷のまま圧勝予測が続いて終わるランに `dead_time` 警告が立つこと。ARC 0.1の装甲2枚ランで人間が「勝ち確定してからが長い」と記録した区間に対応する。
- **P3 単一ゲートの検出**：ARC 0.1の人間3ランでは感情の大半が装甲へ集中した。エージェント走行でも `single_gate` または `single_worry` の警告が過半のランで立ち、出力集中の首位が防御系部品に偏ること。偏らなければ、この指標は人間の観測を再現していない。
- **P4 代理としての下限**：エージェントの `problemChainRate` と `reinterpretationRate` が `naive` を明確に上回ること。`local` を大きく下回る場合、認識トレースの質が機械的最適化以下であり、代理として使えない。

いずれも合成得点にはしない。P1が破れた場合、指標の再設計からやり直す。

## 現時点の限界

人間の実ランに対する完全な遡及テスト（同じ意思決定点で同じ情報を与え、予測と不安を照合する）には、D1のイベントログのエクスポートが要る。リポジトリ内には集計済みの `analysis/emotional-arc-observations.json`（22ラン分の要約）しかないため、今回検証できるのは構造側の半分だけである。エクスポートが手に入り次第、同じCLIで人間の行動列を再生し、予測の一致率を測る。

## 第3回の事前登録：既知条件のエージェントは、退屈を検出できるか（P6）

第1回・第2回で、エージェントの再プレイ度は8ラン中6件が有効で 3,3,3,3,4,4、標準偏差0.47だった。
一方、作者は同じ盤面（ARC seed 14）に1を付け、「いつものパターンに持ち込めた回」「勝ち確定してつまらない」
と記録した。**エージェントは、人間が最低評価を付けた盤面を3と評価した。** 順位付けの道具としては、この時点で失格である。

原因の仮説は「エージェントが支配戦略を知らないから」である。作者は装甲支配を知っていて、
それを綺麗に実行できたために退屈した。初見のエージェントは同じ盤面で苦戦し、面白がった。

そこで `node agents/session.mjs brief` で全部品・全敵・全数値を先に見せ、戦略を立ててから遊ばせる条件を作る。
検証は **ARC seed 14**、つまり作者が1を付けた既知の盤面で行う。

- **P6-a 支配線への到達**：brief条件のエージェントが、防御部品（即席装甲機）を最終構成に入れて勝つ。
  初見条件では4体中1体しか入れなかった。3体中2体以上が入れれば到達とみなす。
- **P6-b 退屈の検出**：brief条件の再プレイ度が、同じ盤面の初見条件（3, 3）より低い。
  中央値が2以下なら検出とみなす。3以上のままなら、brief では熟練の退屈を再現できていない。
- **P6-c 決着点の前倒し**：申告する決着点が、初見条件（第6戦・第5戦）より早い。作者の申告は第3戦だった。

いずれも合成得点にしない。**P6-b が破れた場合、「全情報を先に見せる」では熟練条件を作れないと判断し、
記憶の持ち越し（同じ設計を複数ラン遊ばせる）へ切り替える。**

brief条件でも禁止事項は変わらない。ソースは読ませず、戦闘の試算スクリプトも書かせず、全配置の列挙もさせない。
渡すのは、ゲームが本来プレイヤーへ提示しうる情報だけである。
