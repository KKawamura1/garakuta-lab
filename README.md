# ガラクタ・ラボ

iPhoneのSafariからホーム画面へ追加して遊ぶことを想定した、静的PWAのゲームデザイン試作です。

現在のトップ版は **ARC 0.1**。最初に最も面白かったOBS 0.1を既知の状態で再試験し、面白さが初見の新鮮さだけか、期待・再評価・方針転換の構造として再現するかを調べます。ルールと数値はOBS 0.1へ戻し、任意の戦闘前予測と終了時の物語・再試行動機だけを追加しています。

プレイ版: https://garakuta-lab.pages.dev/

**いまの本命「法則機関 / LAWS 0.1」: https://garakuta-lab.pages.dev/play/**

**1つの良い問題ではなく、問題を生む機械。** 中核（5枠・部品ごとの作動周期・枠で決まる位相・
決定的・正確な予告・等級）は RELAY 0.1 から引き継ぎ、変えたのは一点。

**毎ラン、法則を2つ引く。** 法則は1行で書ける規則で、機関の動き方を変える（全14種）。
組が変われば最適な並びも変わるので、覚えた型は前提から崩れる。
そして**記録は組ごとに持つ**ので、新しい組には常に未達成の記録がある。

出してよい組は事前に検証してある。生成条件（詰みを作らない／締まっている／順序が効く）に加えて、
**最上位の等級が1ランで踏破されないこと**まで確かめた組だけが `core/law-table.json` に載る。
**「出してよい問題か」の判定が、設計時の作業ではなく機械の部品になっている。**

現在 14 組が合格（84 の記録枠）。経緯は [`analysis/ROUND11_LAWS.md`](./analysis/ROUND11_LAWS.md)。

## 開発方針

完成仕様を固めるためのリポジトリではなく、面白さの仮説を試すための実験場です。小さな差分や後方互換性より、プレイ可能な節目を残しつつ大胆に作り直すことを優先します。

企画の目的・面白さの定義・禁止事項・評価原則は [`DESIGN_CHARTER.md`](./DESIGN_CHARTER.md) を最上位の外部記憶とします。実装や数値調整より先に参照します。

## 試作で検証すること

- 欲しい部品を待つより、来た部品の並べ方を考える方が楽しいか
- 部品単独でも働きつつ、共通資源を通じて予想外の相互作用が生まれるか
- 短いオート戦闘から、次に直したい箇所が分かるか
- 雑に強いレア部品を引いた喜びと、即興構築を両立できるか

## 仕様

- HTML / CSS / JavaScriptのみ
- Pages Function + D1へプレイ記録を自動保存（失敗時は端末内キューから再送）
- セーブは端末内の`localStorage`
- Service Workerによるオフライン対応
- ラン終了時のプレイテスト回答・最終構成を端末内に保存
- ランレポートのコピーとスクリーンショット用表示
- プレイ中の感情マーカーと、各選択・戦闘処理を含むイベントログ
- 終了時に最終戦の部品別実績・余剰資源・見送った報酬を表示
- Apple Developer ProgramおよびApp Store配布は不要

## 保留中のゲームデザイン仮説

部品本体と2種類の補助効果を独立に抽選し、組み合わせで個体差を作る案を将来検証する。
たとえば「部品10種 × 副効果A 10種 × 副効果B 10種」とし、基本部品の読みやすさを保ったまま、
同名部品でもランごとに違う使い道が生まれるかを見る。現段階では認知負荷と報酬評価への影響が未検証のため実装しない。

試作から得た抽象的な学び、実験履歴、次に比較する大胆な別案は [`DESIGN_LEARNINGS.md`](./DESIGN_LEARNINGS.md) に記録する。

感情の落差仮説の既存ログ分析と構造代理評価は [`analysis/EMOTIONAL_ARC_HYPOTHESIS.md`](./analysis/EMOTIONAL_ARC_HYPOTHESIS.md) に記録する。

## 公開方法

HTTPSで配信できる静的ホスティングへ、このフォルダをそのまま置きます。公開後、iPhoneのSafariで開き、「共有」→「ホーム画面に追加」→「Webアプリとして開く」を選びます。

Cloudflare PagesではD1データベースを`PLAYTEST_DB`という名前でbindingし、`migrations/0001_playtest_observations.sql`を適用します。`functions/api/runs.js`が同一オリジンからの記録を受け取ります。
