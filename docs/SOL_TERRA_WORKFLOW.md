# Sol / Terra 分業と仮説検証の運用

更新日：2026-08-24

この文書は、ガラクタ・ラボをGPT-5.6 Sol、GPT-5.6 Terra、作者で進める際の共通ルールです。
目的は、Solのトークン消費を抑えつつ、戦略判断の質と実験の再現性を保つことです。

## 最終目的

作者自身が、中身を知った後もiPhoneで繰り返し遊びたいゲームを作る。

仮説検証、関門、実験数、分析文書、機械評価は手段であり、成功条件ではありません。
強制されたプレイテストによる疲労を、ゲーム自体の面白くなさと混同しないようにします。

## 役割分担

| 担当 | 主な仕事 | 担当しないこと |
|---|---|---|
| **Sol** | 現状診断、戦略、次の仮説、実験設計、事前登録、結果の最終判定 | 通常の実装・デプロイ・ログ集計。サブエージェントの起動 |
| **Terra** | 実装、テスト、デプロイ、ログ取得、事実の集計、文書更新 | 面白くなるまで独自に仕様を足すこと。事前登録後の閾値変更。最終判定 |
| **作者** | 実際に遊ぶ、リアルタイムの反応、自発的な再プレイの有無を報告 | 検証のために同じ版を必要以上に遊び続けること |
| **Sol（結果受領後）** | 生データを事前登録へ照合し、継続・修正・棄却・別系統への移行を決める | Terraの要約だけを根拠に判定すること |

## Solの使用ルール

- Solは戦略上の関門でだけ使う。毎回リポジトリ全体を読ませない。
- **Solからサブエージェントを起動しない。**
- 通常は必要最小限のreasoning effortを使い、Max / Ultra相当の大規模な委任を常用しない。
- 実装、デプロイ、定型検査、ログの整理はTerraへ渡す。
- コードをSolが読むのは、結果の矛盾、計測バグ、設計判断に関わる疑いがあるときだけ。

## 目的・不変条件・HOWの分離

Solは実験票を、次の3層に分ける。

1. **目的**：何を知りたいか、どの因果機構を確かめるか
2. **不変条件**：後から変えてはいけないゲーム仕様、成功基準、公開条件
3. **委任するHOW**：実装、探索、テスト、証拠整理の方法

Solは目的と不変条件を明確にするが、HOWを必要以上に固定しない。Terraは目的を満たす範囲でHOWを変更でき、変更理由と同値性を記録する。

Terraは高価な実装・探索の前に、自分で短い反証レビューを行う。Gateが恒真・恒偽でないか、目的と違う代理指標になっていないか、量化や状態比較に矛盾がないか、既知の良い例・悪い例を正しく分けるかを確認する。問題を見つけたら、字面どおりの実行を続けず、反例・影響・修正案を返して停止する。

Terraが変えてよいのはHOWであり、仮説、ゲーム仕様、成功基準、事前登録済み閾値、公開可否ではない。境界が曖昧なら、安価な診断までは進め、結果を変える変更の前で停止する。

## 実験の進め方

1. Solが目的・不変条件・委任範囲を含む実験票を作る。
2. Terraが反証レビューを行い、問題がなければ最小実装・テスト・デプロイを行う。
3. 作者は原則として1〜2ランだけ遊ぶ。
4. 可能なら24時間、再プレイを強制せず、自発的に開きたくなったかを見る。
5. Terraが生データを含む結果パケットを作る。
6. Solが事前登録と照合して判定する。
7. 同じ系統の修正は原則最大2回。反応が出なければ凍結し、別系統へ移る。

細かなA/Bテストを長く続けず、必要に応じて異なる面白さの核を並行探索します。
現在の版は比較基準として凍結でき、すべてを一つの本命へ積み上げる必要はありません。

## 主要な評価信号

強制プレイ後の5段階評価だけを主要指標にしません。特に次を重視します。

- 翌日、頼まれていないのにもう一度開きたくなったか
- 終了後すぐに「別の引きならこうしたい」が浮かんだか
- ランを固有の経緯として説明できたか
- ラン中に既存構成を大きく壊したか
- 新しい取得物によって古い部品の評価が逆転したか
- 「今回はこういう変な機械になった」と振り返れたか

勝率、詰み、勝てる並びの幅などの機械評価は、壊れた候補の足切りと説明に使います。
面白さや再プレイ欲の代理判定には使いません。

## Solが作る実験票

```markdown
# EXP-XX 実験名

## 問い
何が面白さを生むか。

## 仮説
なぜこの変更で面白くなると思うか。

## 変更
今回だけ変えるもの。

## 維持
比較のため残すもの。

## 最小実装
作る範囲と、作らない範囲。

## 成功信号
どんな発言・行動が出れば支持か。

## 失敗信号
何が出たら捨てるか。

## 中止条件
バグ、理解不能、所要時間超過など。

## Terraの完了条件
テスト、デプロイ、版表示、必要なログ項目。
```

Terraへの依頼は「面白くなるまで改善する」ではなく、
**実験票どおりに最小実装し、成功・失敗の両方を観測可能にする**とします。

## Terraが作る結果パケット

```markdown
# EXP-XX RESULT

- コミット・公開版
- 実際に変更したもの
- 実験票からの逸脱
- プレイ本数、シード、所要時間
- 行動ログの主要値
- 作者の発言・自由記述（原文）
- 面白かった瞬間
- 退屈・面倒だった瞬間
- 大きく組み直した回数
- 24時間以内に自発的に再度開いたか
- バグ・計測上の疑い
- Terraによる事実要約
```

**最終結論だけをSolへ渡さない。**
作者の原文、主要な行動、実験票からの逸脱、計測上の疑いを残します。
Terraの解釈と観測事実を分け、支持・反証の最終判定はSolが行います。

## Solへ渡す最小コンテキスト

毎回リポジトリ全体を再読させず、原則として次だけを渡します。

1. `analysis/CURRENT.md` — 現在地、支持・反証、候補系統
2. `analysis/experiments/EXP-XX.md` — 今回の実験票
3. `analysis/experiments/EXP-XX_RESULT.md` — 結果パケット

これらと記録が矛盾した場合だけ、関連コード、D1ログ、過去の実験文書まで広げます。

## 現在の戦略上の注意

現在のlaws系は「異なる問題」を生成していますが、プレイヤーの主な動詞は
「5枠を並べ替え、予告を見る」に固定されやすい状態です。

細かな調律を続けるだけでなく、当初の目的である次の体験へ戻る候補も試します。

- 来た材料によって既存部品の意味が変わる
- ラン途中で構成を大きく壊す
- 方針転換の履歴が残る
- 最後に、そのラン固有の変な機械ができる

現在のRELAY / laws / SKIPは、その比較基準として保持します。


## 現在の実装担当運用（2026-08-24、従来記述より優先）

情報共有の相手を増やさないため、常に **Sol＋実装担当＋作者** とし、レビュー専用エージェントは追加しない。本文中の「Terra」は、特記がない限り「実装担当」と読み替える。

- 現在の実装・検査担当はGPT-5.6 Terra
- Lunaの試用は終了し、今後の担当から外れた。Terraを追加したのではなくLunaから置き換えた
- Sol＋実装担当1名＋作者の構成を維持し、サブエージェントや別レビュー担当は追加しない
- Solは因果機構、成功基準、変更禁止事項、公開条件を指定し、実装・探索・テストのHOWは原則として委任する
- Terraは目的との矛盾を先に探し、HOWは改善してよい。仮説、ゲーム仕様、閾値は独自変更せず、要求トレーサビリティと証拠を返す
- 人間テスト前には [HUMAN_TEST_RELEASE.md](./HUMAN_TEST_RELEASE.md) を必ず満たす

モデル合否はゲームの面白さと分ける。正しい実験が面白さ1でも工程が正しければLuna合格。未確認のまま作者へ渡す、無断逸脱、標準UI・ログ欠落、証拠矛盾などを工程失敗とする。

作者がチャット間で仕様を転記しないよう、受け渡しは原則として `analysis/experiments/exp-XX/Rn_....md` のURL一つにする。回答は同じ実験フォルダの `An_.../` に保存し、作者は回答URLだけをSolへ返す。
