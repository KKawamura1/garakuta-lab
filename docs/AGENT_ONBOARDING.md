## 2. 現在の認識

- 目的は作者自身の持続的な再プレイです。ゲート通過、勝率、完走、エージェント評価は目的ではありません。
- 既定の比較版は /play/ のSKIP 0.4 / laws-0.5です。
- 最新のSCRAPLINE 0.7は機械的には完走・イベント保存できましたが、作者はfun 1〜2/5、因果不明と評価しました。
- 「溶解車を取れば勝てる」「弾が先回りする」などの挙動を、作者が説明できないなら、まず説明可能性を直します。新しい車両・敵・数値を足す根拠にはしません。
- 既存の不採択版を小修正で延命するか、別の短い因果コアへ移るかは、次の実験票で決めます。

## 3. 証拠の強さ

1. 作者の自由記述、プレイ中の発言、実際の行動列
2. D1/exportの完了ランと画面に表示された版・build
3. 再現可能な機械検査、構造ゲート、payload検査
4. エージェントの代理評価、勝率、探索数
5. 実装者の意図や事後解釈

作者の評価が低いときに、機械スコアを理由に成功へ戻しません。逆に、機械検査の失敗が実験条件そのものの不成立なら、ゲーム仮説の反証とは分けて記録します。

## 4. 新しい実験の必須記載

- 作者に持たせたい具体的な問い
- 主ループ一つと、補助ループは多くても一つ
- 変更するもの、維持するもの、複雑性の予算
- 同じ場面で生きる二つ以上の方針
- 材料→選択→相手/物/画面/音の変化→結果の因果
- 作者が見る差分と、結果後に残る次の問い
- 成功信号と停止信号
- 到達性、勝敗、決定性、ログ、版識別の機械検査
- 作者テストのサンプル数、自由記述、主要行動、D1/exportの照合
- 公開する場合の390×844、リロード、D1、export、版表示の確認

## 5. 実装・検査の順番

1. 票と対象commitを固定する。
2. 高価な探索の前に、恒真・恒偽・構造的反例・fixtureの古さを確認する。
3. 最小の証人で、仕様とコードが同じ意味を見ているか確認する。
4. 機械検査を終了コードで判定する。出力にPASSと書かれているだけでは合格にしない。
5. 公開が必要ならHUMAN_TEST_RELEASE.mdの全項目を閉じる。
6. 作者のテスト後、行動・回答・感情マーカー・版・完了状態を一緒に読む。
7. CURRENT/LEDGERへ短い結果を追加し、詳細は個別票・ログへ残す。

## 6. してはいけないこと

- 数字を見た後で閾値・分母・対象範囲を変える。
- 完走率・勝率・イベント数を面白さの代理にする。
- 作者の代わりに、作者が面白いと感じたことにする。
- 実験票なしに仕様・敵・報酬・数値を追加する。
- 古いRESUME、README、時系列要約だけを根拠に現在のキューを決める。
- 未確認の公開条件を作者のプレイで埋める。
- 既存の失敗作、成功作、未成立の証拠を削除する。

## 7. 作業完了時の記録

変更した版、build、schema、seed、対象commit、検査コマンドと終了コード、未確認項目、作者テスト結果を記録します。現在の判断と詳細な証拠を同じ文書へ詰め込まず、CURRENT/LEDGERは索引として短く保ちます。
