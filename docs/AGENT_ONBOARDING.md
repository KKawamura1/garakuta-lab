## 2. まず固定すべき現在認識

- まだ作者にとって再プレイしたいゲームは証明されていない。
- 高い勝率、構造ゲート、エージェントの fun 評価、コンテンツ量は、作者の fun/replay の代わりにならない。
- RELAY、MUTATE、GRAFT の局所的な発見・再解釈は資産だが、持続する replay ではない。
- NIGHT-EATER、TOMORI、EMBERLINE、KINDLING の現行版は、それぞれを小修正しながら延命する対象ではない。
- 次は「文章を長くする」「数値を難しくする」「要素を増やす」より、具体的な因果コアを作る段階である。
- 「途中の選択」「育成」「物語」「質的変化」は方向として未反証のものもある。現行実装の失敗と方向全体の反証を混同しない。

## 3. 過去の実験を再利用する方法

過去の結果を、次の四種類に分類してから引用する。

### 設計証拠

作者の自由記述、プレイ中の行動、感情マーカー、D1 の生データ。作者が「意味が分からない」「次にやりたい」と書いた場合、実装者の意図や代理スコアより優先する。

### 構造証拠

到達性、勝敗処理、seed の再現、import、ログ送信、版識別。これはゲームが意図した条件を実装できたかの証拠であり、面白さの証明ではない。

### 代理証拠

エージェント評価、探索回数、勝率、解の狭さ、グレード。仮説の一部を説明する材料にはなるが、作者の replay を合否判定しない。

### 運用証拠

GitHub Actions、Pages、D1 export、キャッシュ、stamp、UI バグ。設計結果と混ぜない。実験条件が成立していなかった場合は、まず「未検証」として台帳に戻す。

## 4. 新しい実験を始める前の質問

1. 今回、作者にどんな問いを持たせたいか。
2. その問いは、画面の具体物・行動・結果に結びついているか。
3. 同じ場面に、少なくとも二つの生きた方針があるか。
4. 初手で完成しないか。後の状況が既存の選択を再評価させるか。
5. 結果は数値だけでなく、相手、物、画面、音、行動の変化として返るか。
6. 失敗したとき、作者が次に変えることを言えるか。
7. 何が実装されなかったら、仮説は未検証になるか。
8. 何をもって続行・改修・凍結するか。
9. 作者に見せる版、seed、導線、ログ収集が追跡可能か。

この質問のどれかに答えられない場合、まず実験票を整理する。実装を始めない。

## 5. 現在の推奨プロトコル

### フェーズ A: 1〜3分の因果コア

- 具体的な相手 1 人、目的 1 つ、問題 1 つ。
- 具体的な材料 3 つ程度。
- 2 つ以上の生きた選択。
- 材料→選択→相手/画面/音の変化→結果を可視化。
- 終了時に「自分の選択が何を変えたか」を要約。
- 通常プレイでは seed を隠す。診断用の固定 seed は別に記録。

成功の目安は、作者が 20 秒以内に因果を説明し、使わなかった選択を試す理由を言い、失敗なら次の変更を自発的に言い、2 回目を促されずに望むこと。これは機械的な合格点ではなく、作者テストの観測項目である。

### フェーズ B: 10〜20分への拡大

フェーズ A を通過した場合だけ、場面、素材、相手の状態、未見の分岐を増やす。増やすのは主ループを支えるものに限る。新しい要素が既存の意味を再評価させないなら追加しない。

### フェーズ C: 演出・物語・コレクション

アート、アニメーション、音、物語、収集、エンディングの拡張は、因果コアの結果を強くするために使う。因果が伝わらない状態で、雰囲気や文量だけを先に増やさない。

## 6. seed と比較

作者の通常プレイでは、seed や推奨遊び順を見せない。作者がランダムに見えること自体が体験上重要だからである。

一方、検証では次を分ける。

- 診断: 固定 seed、固定版、同じ状態を再現する。
- 本番作者テスト: seed を隠し、1〜2 ランの自由な選択を見る。
- 比較: 必要なら同じ作者に別条件を見せるが、先に条件名や面白い順を教えない。

seed は難易度の答えでも、面白さの証明でもない。seed ごとに優劣を後付けして、面白い seed を標準にすることはしない。

## 7. 実装・公開・ログのチェック

実装後は、設計検証と運用検証を分ける。

- Node/import、到達可能性、勝敗、公開 E2E、版 stamp を確認。
- [HUMAN_TEST_RELEASE](HUMAN_TEST_RELEASE.md) の条件を満たすまで URL を作者テストに渡さない。
- 作者テスト後は、感情マーカーだけでなく自由記述、実行行動、seed、版、完了状態を export する。
- D1 は直接見られない場合がある。現行の ChatGPT/OpenAI 経路は [D1_LOG_ACCESS](D1_LOG_ACCESS.md) と [EXPORT](EXPORT.md) に従う。通常は GitHub Actions の export を使い、dispatch が見えなければ成功済みの export job を rerun する。
- UI の入力残り、同じメモの重複、最終ログ消失、古いキャッシュ、公開版とローカル版の差を確認する。
- ログの不整合が見つかった場合、設計評価の前に「測定エラー」として記録する。

## 8. 変更を残す方法

- 失敗作も成功作も削除しない。
- 新しい実験票に、今回の仮説、変更点、維持点、成功/失敗条件、複雑さ予算、参照した過去の失敗を書く。
- 実験後は LEDGER に一行を追加し、詳細は個別票・生ログにリンクする。
- 既存文書が Claude 向けであっても、消さない。ChatGPT/OpenAI の現行経路は新しい節として追記する。
- main の現在地を変えたら、PROJECT_MEMORY、CURRENT、LEDGER のどこかに反映する。古い RESUME の「次にやること」だけを更新して現在の正史にしない。

## 9. 迷ったときの中止条件

次の状態では、難易度・文章・報酬・素材を足す前に止まる。

- 作者が誰/何/なぜを説明できない。
- 選択肢が全て同じ結果に見える。
- 画面に正解が表示され、探索が検証になる。
- 初期配置や初手で、その後の選択が無意味になる。
- 失敗しても次の変更が思いつかない。
- 毎回違うが、毎回同じ判断になる。
- 構造ゲートは通るが、作者の自由記述が明確に否定している。
