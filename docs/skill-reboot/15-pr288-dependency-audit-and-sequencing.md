# 武器技能移行のPR分割・切替手順

更新日: 2026-09-24  
対象: PR #288「武器技能ロードアウトの基盤を実装」の再編と、その後のdevブランチへの実装  
仕様の正本: mainへマージ済みの [武器カタログ](./11-weapon-catalog.md) と [解決順監査](./12-resolution-order-audit.md)

## 目標と固定条件

10武器×19節＝190節の実装を、レビュー可能なPRに分けてdevへ順番に入れる。共通システムとUIを先に作り、個別技能の大部分は後で実装する。新規コードは旧技能の定義・ID・レベルに依存させず、ゲーム本体の切替時に旧経路を早期に撤去する。

- プレイヤー技能は武器別registry、敵技能は実際に使う定義だけの別registryに置く。
- 各人物の初期取得は代表武器2本のRとA1から導出する。合計20節を切替時までに正しく動かす。医療具A1など、種別をアクティブに決め打ちしない。
- 主軸アクティブ1つ、優先列で排他的に選ぶリアクティブとターゲット、成立するものをすべて適用するパッシブ、取得予約、装備packと技能packの分離を維持する。
- 旧セーブは移行しない。現行versionの保存・再読込と、異なるversionの明示的な拒否を検査する。
- preview・本番・replay・検証は同じengineイベントを読む。未知のevent/effect/predicate等はvalidator errorにする。
- PR #288の既存実装は移植元と監査材料として扱い、丸ごとdevへマージしない。既に照合済みの戦槌・格闘具38節も、移植先の共通機構が変われば再監査する。

## ブランチとPRの運用

1. 最新mainから`dev`を作る。最終的にdevからmainへ統合するまで、mainは既存ゲームの基準とする。
2. 各作業ブランチはその時点のdevから作り、原則として**一つのPRをdevへマージしてから次のPRを作る**。同時進行が必要なら直前PRのブランチをbaseにしたstacked PRとし、前段のマージ後にbaseをdevへ直して差分を確認する。PRの比較先をmainにして巨大な累積差分をレビューしない。
3. 各PRには目的、変更した境界、移植元のPR #288のcommitまたはファイル、依存先、削除・置換した経路、検査結果、未確認点を書く。次のPRが依存する公開APIや保存形式を明記する。
4. PR #288は分割中も参照可能なDraftとして保持する。移植と全190節の照合が完了し、差分の扱いを確認した後に閉じる。履歴を消すためにforce pushしない。
5. 本手順のdev向けPRは、既存AGENTS.mdの「main向けPR」という通常運用に対する、この移行作業に限る作者指定の例外である。各PRの試験・preview・文書更新の規則は引き続き守る。

dev上で一時的に旧経路が残る準備段階でも、新規モジュールから旧skill ID、旧level map、旧tree、旧packの形を参照しない。橋渡し用のadapterが必要なら境界・削除予定PR・テストを明記し、切替PRで消す。二つの技能エンジンを恒久的に維持しない。

## 依存台帳と検査基準

最初のPRで移行台帳を作り、各PRで更新する。旧ファイル・概念ごとに「参照元（import、ID、保存データ、UI、replay、CI、preview、運用文書、Issue）」「置換先」「撤去するPR」「確認方法」「未確認点」を記す。単なるimport検索だけで削除可と判定しない。削除後に未知の依存が見つかったら台帳へ戻し、対応する境界とテストを修正する。

検査対象を次の二層に分ける。

- **仕様メタデータ190節:** ID、武器、位置、種別、前提、表示文、初期20節との対応をカタログから同期・検査する。生成可能な情報を武器moduleに重複して手書きしない。
- **実装済み技能だけの実挙動:** 行動・反応・効果の定義とテストを追加した節だけruntime registryへ公開する。未実装節を取得・pack・戦闘で使わせない。未実装を汎用攻撃や無効果で「実装済み」に見せない。UIには未実装状態を明示し、切替前のfixture表示と実ゲームの取得可能表示を区別する。

各PRのテストは変更した境界を直接検証する。既存ゲームを変更しない準備PRでは既存の主要検査を保ち、切替後は`node ecology/check.mjs`と`bash analysis/check-all.sh`を通す。画面変更では画面smokeと実際のブランチpreviewのモバイル確認を行い、実行できなければ未確認理由をPRへ残す。contract snapshotとcontent contract versionは、対象PRごとに差分と更新判断を示し、最後にまとめて直さない。

## 実装順とPRの境界

以下の番号は依存順であり、一行が大きすぎる場合はさらに機構単位に分ける。各PRはマージ時に検証可能な状態を保つ。

| 段階 | PRの範囲 | 完了条件 |
|---|---|---|
| 0 | mainとPR #288の起動、チュートリアル、遠征、保存、画面、CIの基準を記録。依存台帳、試験の対応表、190節の仕様メタデータ同期・検証 | 旧経路と削除候補の参照元、代替試験、未確認点が追える。既存試験が失敗する場合も基準状態として記録 |
| 1 | 敵技能をプレイヤー技能から分離。新しい武器registry/schemaと未実装節の扱いを導入 | 敵が使う定義だけで敵戦闘が動き、未実装プレイヤー技能は取得できない。既存プレイヤー戦闘はこの段階では維持 |
| 2 | 共通の解決順を小分けに導入。例: 基礎hitと自己位置、基礎対象とターゲット、攻撃前、hit/対象確定、効果量、反応窓、攻撃後。event/effect/predicate、状態・費用・有限性も使用する機構ごとに追加 | 機構ごとの決定論・境界・優先順をテストで確認。新しい機構は実際に使う代表ケースを持つ。新経路は旧技能定義をimportしない |
| 3 | 主軸と優先列のロードアウト、取得・前提・予約、武器/装備pack、run/profile保存をそれぞれ小PRで追加 | 新しい状態だけで取得から保存・再読込まで検証できる。旧version拒否を確認 |
| 4 | 新技能ツリー、ロードアウト、予約、技能説明、戦闘予測などのUIを仕様メタデータと固定fixtureで先行実装。画面単位で分割 | 190節の表示構造と操作をレビューできる。予測と本番の経路を分岐させず、未実装節は取得可能に見せない |
| 5 | **初期20節とゲーム本体の切替**。必要なら20節の実装準備を複数PRに分け、最後の切替PRで実際に使用する | 5人の初期取得、起動、戦闘、チュートリアル、遠征、取得・予約、保存・再読込、replay、UI・予測が新経路で通る。同じPRで直接置き換わった旧tree、level、player skill、旧pack経路とadapterを撤去 |
| 6 | 残り170節を原則1武器1PRで追加。戦槌・格闘具の既存監査も移植先で確認 | 各節の仕様、実装、動作検証をカタログ順に記録。武器横断の新しい汎用機構が要る場合は先に小さな共通機構PRを入れ、完了済み技能への影響を再監査 |
| 7 | CI・運用・文書・履歴の独立した整理、全190節の最終通読と回帰、devからmainへの統合 | 実装済み190節と仕様190節が一致し、全ゲーム経路・試験・リンクを確認 |

段階2は「schema、engine、UI、replayを一つの巨大PRで完成させる」という意味ではない。公開するeventを増やすPRではschema、validator、engine、表示・replay、テストをそのeventに必要な範囲で一緒に更新する。共通機構の設計変更が起きたら、台帳から利用技能を抽出し、監査済みの印も必要に応じて戻す。

## 旧経路の切替・削除条件

旧実装の撤去を最後の掃除に回さない。ただし代替のない経路や試験を先に消さない。切替PRに含める対象と、別PRで撤去できる対象を台帳で分ける。

- **切替PRで消す:** 旧プレイヤー技能tree、skill level、旧active/passive/reactive定義、旧packの技能経路、旧IDへの参照、仮adapter。実際に残存参照を検索し、未知のID・event等で起動時または検証時に失敗することを確認する。
- **置換と同じPRで更新する:** 保存、初期ロードアウト、戦闘、取得予約、UI・replay、contract snapshot、およびそれらに直接依存するテスト。削除した検査が何を覆っていたかを対応表に残す。
- **代替を確認してから扱う:** `.github/workflows/ecology-trial.yml`、`analysis/ecology-trial.mjs`、`analysis/ecology-tutorial-trial.mjs`。Issue #178は両trialの実行を完了条件に含むため、同等の新試験を通すか、Issueの完了条件を明示的に更新する。`analysis/check-all.sh`から外れた旧チェックも対象範囲ごとに置換先を記録する。
- **独立した整理PRに回す:** 実行経路と無関係な古い設計文書や検討履歴。削除前にREADME、他文書、Issue/PRの参照を調べる。現状の`docs/skill-reboot/README.md`にはPR #288で削除された旧v3・research文書へのリンクがあるため、リンク切れを解決するまで削除を完了としない。

切替PRの判定は「旧ファイルが減った」ではなく、新経路だけで実ゲームの主要操作が通り、旧実装への参照がなく、旧経路の検証範囲が新しい試験または更新済みの要求へ移ったことで行う。

## 武器PRと最終統合の完了条件

武器PRには、その武器の未実装節、実挙動テスト、カタログとの節ごとの照合、影響する共通機構の回帰、該当するsnapshot差分を含める。各節について対象、trigger/window、費用、回数/上限、状態段数、hit・防御・移動・準備の順序を確認する。[既存の190節監査台帳](./14-pr288-implementation-audit-2026-09-24.md)は移植元の証拠として使い、dev上の確認結果を別に追記または新台帳に記録する。

devからmainへの最終PRでは、全190節がruntime registryに揃うこと、仕様メタデータと実挙動のIDが一致すること、5人の開始状態から全ての取得経路が辿れることを自動検査する。チュートリアル、遠征、保存・再読込、予測と本番、replay、ブラウザーpreview、CI、試験対応表、Issue #178、文書リンクを再確認する。未確認項目は成功扱いにせず、原因と後続対応を明示する。
