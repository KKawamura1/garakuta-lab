# PR #288 実装の依存棚卸しと分割順

更新日: 2026-09-24  
対象: PR #288「武器技能ロードアウトの基盤を実装」  
仕様の正本: PR #287でマージされた docs/skill-reboot/11-weapon-catalog.md

## 目的と基本方針

PR #288を、10武器・190節の一括実装と一括整理にしない。隠れた参照先や検証経路を先に可視化し、新しい経路への置換と、その経路に直接依存する旧実装の撤去を同じ移行単位で行う。

順序は次のとおり。

1. 依存関係と削除候補を棚卸しする。
2. 新しい経路と置換テストを用意し、対応できた旧経路を同じPRで撤去する。
3. 共有基盤が安定してから武器単位の内容PRへ分ける。
4. 動作に関係しない文書・履歴の整理は、参照を解決してから別途行う。

「整理をすべて先に実行」もしない。稼働中の経路を置換より先に消すと、比較基準や検証手段まで失うためである。

## 既に決まっている制約

- PR #287のカタログを技能仕様の正本とする。
- プレイヤー技能は10武器190節、敵技能は別registryで管理する。
- 各人物の初期技能は、代表武器2本のRとA1（合計20節）から導出する。
- 旧セーブ・旧技能レベル・旧pack経路の移行は行わない。現行versionと一致しない保存データは読み込まない。
- 旧仕様との互換を理由に旧コードを残さない。ただし、現行のゲーム進行・表示・検証に必要な経路は、代替が通るまで削除しない。

## 依存棚卸し表

削除・置換する各ファイルや概念について、次の行を作業台帳に記録する。

| 対象 | 確認する依存先 | 削除・移行の完了条件 |
|---|---|---|
| 旧技能tree、skill level、active/passive/reactive定義 | import元、UI、初期ロードアウト、戦闘処理、取得予約、pack、enemy registry | 新registryとロードアウトで初期戦闘から取得・表示まで通る。旧IDへの参照が残らない |
| 保存形式・run/profile state | 読み書き、version検査、予約・取得状況 | 現行形式を保存・再読込でき、旧versionを仕様どおり拒否する |
| 遠征・チュートリアル・ブラウザー試験 | workflow、check-all、preview、運用手順、Issueの完了条件 | 同じ利用経路を覆う新しい試験が通るか、対象Issueの条件を明示的に更新する |
| 正本・生成物・snapshot | カタログ、同期script、registry、contract snapshot | 正本から生成される項目と手書きの挙動定義が明確で、差分を項目単位で確認できる |
| 設計文書・履歴 | README等からのリンク、Issue/PRからのリンク、現行方針との競合 | リンク切れと現行方針との矛盾を解消する。履歴として必要な文書は残す |

依存確認には、ソースのimport検索だけでなく、コンテンツID、保存データ、画面、replay、CI、デプロイ、運用文書、GitHub Issuesからの参照を含める。

2026-09-24時点のPR差分には、次の削除が含まれる。武器別分割より前に代替と参照を確認する。

- docs/skill-rebootの旧v3・research文書が複数削除されている一方、同ディレクトリのREADMEには削除対象への参照が残っている。文書を保持するか、参照を置き換えてリンク切れを解消する。

これらはPR差分上の確認項目であり、この文書だけで削除可否を確定しない。

## 実装と分割の順序

### 1. 変更前の基準を記録する

現行mainとPR #288で、ゲームの起動、チュートリアル、遠征1回、保存・再読込、画面遷移、CIの結果を記録する。既存のE2Eが起動できない場合も、失敗を基準状態として残す。

### 2. 移行台帳と代替テストを先に用意する

依存棚卸し表を旧ファイル・旧機能ごとに埋める。削除が想定される画面や進行経路の代替テストを、旧テストを削除する前に追加・実行する。旧セーブ互換は対象外とし、現行保存の往復と旧versionの拒否を分けて検証する。

### 3. 共有基盤を移行する

schema、event/effect/predicate、解決順、戦闘処理、skill registry、取得・予約、保存、UI、replayの共通境界を一つの基盤層として安定させる。旧処理を撤去する場合は、直接の置換実装と回帰テストを同じ変更に入れる。削除後に見つかった参照は、場当たり的に復活させず台帳へ追加し、どの層の置換が必要か判断する。

### 4. 代表技能で基盤を検証する

初期ロードアウトに必要な20節を含めて起動・進行できる状態を作る。戦槌・格闘具は既存の38節監査をパイロットに使い、対象拡張、多段、反応優先、防御、追撃などの共有規則を確定する。共通規則が変わった場合は、影響する技能とテストへ戻って再確認する。

### 5. 武器内容を段階追加する

共有engineに変更のない武器を、原則として1武器1PRで追加する。初期のR/A1以外の技能、武器module、挙動テスト、仕様照合、該当するcontract snapshotを同じPRに含める。新しい汎用機構が必要になった場合は、その機構を共有基盤へ追加してから武器内容を載せる。機構と技能を一つの武器PRで同時に増やし続けない。

PR #287のカタログから生成するweapon-specificationsと、weapon module内の実挙動定義の責任範囲を明示する。生成可能な名前・表示文・tree metadataを手作業で重複保持しない。contract snapshotは全武器完成後に一括更新せず、各移行PRの対象差分を確認して更新する。

### 6. 独立した整理を行う

ランタイム・CI・運用の依存がない文書や検討履歴だけを、別の整理PRで削除する。各削除前にrepository内のリンク・Issue・PR参照を確認し、残す価値のある判断履歴は現行資料へのリンクを付けて保存する。

## 各移行PRの完了条件

- 対象と削除理由、参照元、置換先、未確認点がPR本文または台帳にある。
- 旧経路の削除後、起動時・検証時に未解決のimport、ID、未知のevent/effect/predicateがない。
- 全190節のregistry対応、分類、前提、初期取得、表示用文の整合を自動検査できる。
- node ecology/check.mjs と bash analysis/check-all.sh が通る。
- ゲーム進行や画面変更のPRでは、該当する新しいブラウザー試験とpreview確認を行う。実行できない試験は未確認としてPRに残す。
- contract snapshotの差分とcontent contract versionの判断が説明されている。
- 共通機構に変更がある場合は、その機構を使う完了済み技能を台帳から特定し、再監査する。

Issue #178の試験条件とREADMEのリンク切れは、依存棚卸し後に個別の解決先を確定する。
