# スキル体系再設計 — 設計憲章と再開手順

## 目標体験

「今回は何を拾ったか」を見て育成方針を決め、技能・配置を一手変えたとき、意外な味方が得をする。第1シナリオからこの体験を成立させ、後続シナリオは旧技能の使い道を増やす。

技能数そのものを成功指標にしない。選択が変わる理由、成立を味わえる戦数、既存技能への新しい接続を数える。

## 採用基準

1. 各テーマは単独で使える入口、共有状態を作る技能、それを別用途へ変える技能、利益を回収する技能、代償を持つ。特定ID同士だけを照合する専用コンボを作らない。
2. 各入口は第1戦後に選べる。核は第4〜6戦までに成立し、少なくとも残り半分で試せる。最深部の到達だけを成長にしない。
3. 状態は少数に絞り、複数テーマから作れて複数テーマで使える。新語を増やす前に既存の隙・集中・防壁・受け構え・位置・実被害の意味を検討する。
4. 強い技能はAP/RP・準備・対象範囲・防御放棄・HP負担等で何かを諦める。Lv増加で代償を消さない。単純上位互換の別名技能を増やさない。
5. 同じ技能でも誰に習得させるかで役割が変わる。キャラ別専有ツリーへ自動変更しない。ゴウ/ツグミだけの序盤でも、後の仲間専用に見える入口を使えるようにする。
6. 取得不可逆・装着数無制限・オンオフと優先順位・戦闘前完全予測を前提に案を作る。これを変更する案は別の設計判断として明示する。
7. 反応に全てを集めない。APを使う決断とRPで支える判断を分ける。反応連鎖には見える終点が必要。
8. 攻撃/回復などの量の成長と、Lv前提で得る用途の拡張を両立する。前提Lvは通行料ではなく、その技能を使って進む期間になるように置く。
9. 後続シナリオは単なる高威力解放ではなく旧技能の再解釈。初登場テーマの完成に次シナリオを必須としない。
10. 自動戦闘なので手動タイミングを要求しない。条件・対象・発火順が、予測と短い説明で把握できる技能にする。

## 最初に比較する案

SPは全員に通常勝利2、幕ボス3（4/8/12戦）の案を基準とし、全戦2・全戦3と比較する。最終戦前の使用可能SPは24対22対33。最終戦報酬をビルド完成の予算に含めない。初期SP0と無料初期技能を別勘定にする。

技能Lvは全技能一律10・一律威力12%から、技能の役割に応じた小さな上限とLv2/3/5前提へ再検討。数値は暫定。付与SPだけを増やして深さ10の通行料を維持することは避ける。

ツリー表示はテーマによるまとまりを優先する案を検討。現在の行動/反応/常設タブ、同種前提、x=10という制約を変える場合は提案と現行を混同しない。スマホで全ノードを同時表示する必要はない。

## 新鮮さの検証

- 同じ2人・同じSPで異なる勝ち筋が少なくとも3つある。
- ある低レア装備を拾うと、まだ使っていないSPの配分が変わる。装備なしでも各入口が動く。
- 新テーマ1つで、旧テーマ2つ以上に新しい使い道が増える。
- 特定組合せが不成立でも代替の発生源がある。
- 敵が少ない/多い、高guard/多段、前列/後列圧力の違いで有利不利が入れ替わる。
- 無限ループ、敵を残す回復稼ぎ、全常設取得が一律正解、RP不足で技能が飾りになる状況を反証する。

面白さは設計レビューだけでは確定しない。仮実装後、作者の実プレイによる判断を独立した関門として残す。

## 再開手順

1. AGENTS.md、親Issue #165、同ブランチの本ディレクトリを読む。
2. mainと調査基点の差分を確認。並行作業の実装を巻き戻さない。
3. 現状監査・体系案・成長例・反証レビュー・実装計画の有無を確認し、欠けている成果から続ける。
4. 設計書は専用branchへcommit。実装着手時は最新mainから専用worktreeを作る。
5. GAME.md/ARCHITECTURE.mdへ未実装案を書かない。設計採用時のDESIGN.md/HISTORY.md更新と実装時の現行仕様更新を計画する。
