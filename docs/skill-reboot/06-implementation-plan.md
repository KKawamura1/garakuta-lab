## 定義とvalidator

候補となる定義の関心事は、安定ID、表示名、テーマ、種別、解放Stage、最大Lv、Lvごとの量、前提（skillIdと必要Lv）、取得費、発火条件、対象、費用、効果、回数制限。実際の型とモジュール分割は実装時に現行schemaへ合わせる。

- 同種前提の現在の制約を変えるなら明示的な仕様変更とし、UIとvalidatorを同時更新。
- 任意の「前提達成」を所持だけで判定しない。Lvを要求するなら取得API、画面、保存復元で同じ判定を使用。
- オフにした技能は取得Lvを保持するので、派生取得条件を失わない。
- 未解放Stageの前提を要求して入口が死ぬ構造を拒否。
- 前提の循環、必要Lvが最大Lv超過、存在しないIDを拒否。
- 最終戦後のSPを引いても取り切れるルートがあることを確認。
- 最初の無料技能を前提予算から差し引く。全員が無料習得するものと個別の初期技能を混同しない。
- 新skill IDと旧skill IDを意味が違うまま使い回さない。旧セーブ・Blueprint・リプレイのcontent versionを黙って読み替えない。

## 発火と資源

各新しい挙動について、既存event/predicate/cost/effect/target relationで表せるかを棚卸しし、表せないものだけ拡張する。文字列名だけ新しいeventを足すことを目的化しない。

表せない場合は schema / validator / engine / event列 / UI / replay を一組で変更する。整数比とround-half-up、用途別のseed key、Profile/Run/Battle分離、previewと本番の共通経路を維持する。

各コンボの代表ケースは、発生源、消費者、状態の残量、AP/RP残量、連鎖の停止理由を記録する。敵を残すことで次戦へ持ち越すHP・補給・装備状態が良くならないことを、単なる最大連鎖数とは別に確認する。

## 試験を増やす場所

| 対象 | 確認する実際のリスク |
|---|---|
| 成長 | 勝利commit/ロード/再試行でSPが二重付与されない。加入人数と無料初期技能が正しい |
| 前提 | Lv不足、Stage不足、オンオフ、同一前提の共有、循環や未知IDを正しく扱う |
| 反応 | RP枯渇、複数購読者、対象死亡、状態を先に消費されたときの発火順 |
| 連鎖 | AP授受の往復、自傷と回復、準備加速、多段hitごとの過剰発火、装備併用 |
| 共通経路 | 同一入力の予測と本番が結果・イベント列とも一致 |
| UI | 必要Lv/取得費/解放理由をiPhoneで読め、優先順位とトグルが実戦へ反映 |

既存の必須検査は `node ecology/check.mjs` と `bash analysis/check-all.sh`。画面変更なら tutorial/trial を追加。公開物変更はstampを更新し、通常CI後に公開先E2E。設計書だけのPRでは実戦バランスを検証したと書かない。
