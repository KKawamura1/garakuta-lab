# ブランチプレビューを見て引き下げた評価

更新: 2026-09-29。状態: **一画面試作の観察。35–38は未採用。** [Cloudflareブランチプレビュー](https://codex-expedition-engine-desi.garakuta-lab.pages.dev/docs/skill-reboot/frontier-prototype)で実際に出発・一巡送り・一手送り・高速再生を操作した。デプロイ済みの最終HTMLで表記も確認。画面幅は1363×936で、手元のCloud Browserは390×844前後へ切り替える操作を提供しなかった。**iPhone幅の目視確認は未実施。**

## 起きたこと

五人のAを全て選び、最初の強化をゴウにした一回の巡路で、一巡後ナギが防壁2を実際に使い、返り火1を得た。次のヒバナの基礎攻撃2が3になり、そのヒットで先頭の敵を倒すと、次隊の敵が後ろへ現れた。高速再生では通常行動68回、敵反撃13回で第12隊を突破。終点で首領をゴウの8が倒し、ゲンゾウの写し8が後ろの縫い手を倒した。ゴウとゲンゾウの強さ、守りからヒバナへの受渡しは規則どおりに画面へ出た。

ブラウザ確認中に「第2巡なのに一巡目」と表示されたこと、ログが新しい行から並んで原因と結果を逆順に読ませたことを発見した。巡数を修正し、ログを時間順・末尾表示へ変更。一巡送りが巡の途中から常に五人分進むのも、今の巡の終わりで止まるよう修正。最終デプロイのCIとCloudflare更新は成功した。

## 見ていて残る不満

**これだけでは、まだバチバチに面白くない。** 初回の「防壁→返り火→矢」は説明できる。しかし全体を高速で流すと、60以上の行動がただの小さなテキスト更新になる。最後の「8を打つ→8を写す」は予想外ではなく、育成後に何度も見る定番。画面が文字とHP数値だけなので、五人が生きて動いている感覚も弱い。これは試作の演出不足だけでなく、**同じA/Bと同じ五人順のまま行動形態が繰り返される**ルール側の弱さかもしれない。

基本敵列HP1.2倍、ゴウから固定巡回で強化する216通りの敵順をPythonで調べると、全Aが210/216、全Bも216/216、速攻寄りのヒバナB・ゴウA・ゲンゾウA・ツグミA・ナギBが216/216。つまり試作の標準難度だけを見れば、**何を選んでもだいたい勝ち、既に安全な全Bもある**。この場合、技能を選ぶ意味は勝敗でなく、何人でどんな姿で進むか、何巡速いか。その道筋を見たいと思えないなら、三枠補充と返り火を積んでも「勝つまで緑探し」を「勝った動画を一回見て終わり」に変えただけ。

他方、射手と後衛にも攻撃する首領を混ぜた比較列は強くなりすぎ、限られた守備・火力構成が有利になった。現段階の難度調整は**基本列では易しすぎ、複合列では数値境界に依存しすぎる**。敵固有の解答技能を足して埋めない。

## 次の棄却基準

1. iPhone実機に近い幅で、三敵・五人・返り火と先見一体が一画面に収まり、初見の人が一巡の因果を言えるか。ログを読まないと分からなければ発火の絵を作る。絵でも分からなければ規則を減らす。
2. 一回目の勝利後、同じ人が自発的にA/Bを一つ替えて二回目を走らせるか。勝利時間だけを記録するスコア付けで無理に誘導しない。
3. 全Aと全Bがどちらも突破するなら、**途中の三敵への対応、受けた被害、発火した役割**が違っていて面白いか。ビルドの差がログの係数だけなら失敗。
4. 一度安全構成を見つけた後の三遠征で、次敵の予告を見たいか、戦闘を見るより高速を押したいか、成長を予約するとき一分以上楽しく悩めるか。この三つが揃わなければ『灰』の核にならない。

作業の次段階はUIの磨き込みを先に決めることではない。**ヒバナ→ゴウ→ゲンゾウ以外の形で、ツグミとナギがいて初めて連破が伸びる一場面**を技能効果だけで示す必要がある。今の返り火は小さな増幅にはなるが、十枚だけで長く遊べるという主張には足りない。この案を残すなら一つの新技能か共通規則でその場面を作り、同じ敵列で代替経路があることを検証する。作れなければ三枠補充も捨てる。
