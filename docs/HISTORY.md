# 歴史的経緯 — なぜ今の形になったか

いま実装がこうなっている**理由**だけを残します。当時の実験記録
（`analysis/experiments/exp-18/` の R1〜R14 と A1〜A9、`PROJECT_MEMORY.md`、
`analysis/CURRENT.md` など）は削除しました。原文が要るときは Git 履歴を辿ってください
（`git log --diff-filter=D -- analysis/experiments`）。

## 1. EXP-18 に至るまで

ガラクタ・ラボは、作者一人が遊ぶゲームを何本も試作した場所です。EXP-18 以前の
プロトタイプと運用資料は現行ツリーから整理済みです。繰り返し観測されたのは次の点でした。

- 固定問題とデザイナー指定の組み合わせは、一度理解すると再プレイ理由を失う。
- 数値・勝率・解の存在・構造ゲート・コンテンツ数は、面白さの代理にならない。
- 内部で多数の計算が起きていても、因果が追えなければ「何も分からない」になる。
- 一つの万能な部品が全状況を支配すると、後続の報酬と判断が消える。
- ランダムな内容が毎回違っても、プレイヤーの判断が同じなら再プレイ性は増えない。

ここから抽出した一般設計メモが `docs/RULE_ECOLOGY.md` です（個別ゲーム仕様ではありません）。

## 3. 効いている判断の理由

### 3.1 難易度 rank をやめて Campaign Stage にした（R8）

現行 content の実測で、作者の凝った構成は素朴な役割配分に対して約1.09倍にしかならず、
仕込んだ AP・RP・人物・技能枠に見合う超過利得が出ていませんでした。seed が4 pack 中
3 pack を選ぶ方式では毎回75%の語彙が残り、学習順や旧技能の再解釈を設計できませんでした。
そこで Stage ごとに pack 構成を固定し、**新 pack と選ばれた過去 pack の接続**を設計する
方針へ変えました。数値倍率で難度を作る案は、同じ理由（判断が増えない）で撤回しています。

### 3.2 初期4 Stage は累積、Stage 4 以降は回転（R9 §2）

有効 pack 数の式は R8（`1 + ceil(sequence/2)`、過去 pack を回転）と R9（`sequence + 1`、
累積）で違います。**黙って片方へ寄せず、両方の式をコードに残し、Stage 定義が
`ladderMode` でどちらを名乗るかを宣言します**（`ecology/content/campaign-stages.mjs`）。
初期4 Stage は累積を採りました。理由は、前の技能がまだ使える／新しい人物が古い pack を
別目的で使う／新 pack は以前の価値を一つだけ変える／全部理解しなくても進める、の4点です。

影響として Stage 3 の有効 pack が3から4へ増えたので、core / full の二段で相殺しています
（新 pack はその Stage では入口だけ）。また R8 は Stage 3 を B（連撃と刻印）にしていましたが、
HP 持ち越しがある以上、回復の意味を Stage 3 までに見せる必要があるため C（手当てと余剰）を
採りました。その結果 `pack_barrage` は Campaign から外れています。

### 3.3 攻めの軸を2本にした（R11）

「5人のうち3人が守り役では多すぎる」という作者の指摘を測ったところ、原因は配役ではなく
**数値系が守りに2軸（防壁 `focus`・軽減 `guard`）、攻めに1軸（`might`）しか持っていなかった**
ことでした。攻撃28件が全部 `might`。R6 §4.4 は「支援役にも technique 攻撃を付けられる」と
宣言していたのに、実装は片側だけだったのです。**`focus` を「技の威力」へ格上げして、
宣言のとおりに実装しました。**

続く「腕力の技と集中の技の違いが分からない」には、名前や属性ではなく**位置の規則**で
答えました。**腕力で伸びる攻撃は後列から出すと 40% まで落ち、集中で伸びる攻撃は落ちない。**
engine への追加はこの一点（`effects.mjs` の `afterRearFalloff`）だけで、人物固有の分岐は
足していません。これで人物の設計がそのまま隊列の設計になり、カイは「前で落ちるか、
後ろで火力を捨てるか」の二択を背負います。

その二択を軸に加入順を組み替えました。**Stage 1 でカイが問題を持ち込み、Stage 2 で
スミがそれを解く。問題を出してから、その解決を渡す。**

同じときに `ecology-campaign-smoke` を削除しました。**隊列を一度も変えず**、装備の
配り先も技能点の使い方も選ばない120通りで「Stage 2 が12戦通せない」と言っていましたが、
隊列は R11 で中心のメカニクスになったので、測っている内容自体が smoke として成立して
いませんでした。閾値を下げて通す代わりに検査そのものを外し、Stage 0〜3 の build 到達
可否は作者が遊んで判断します。（スミの腕力を上げれば通りましたが、「攻撃を持たない
庇護役」という設計が壊れるので採りませんでした。）

### 3.4 Free mode と3人を削除した（R12）

ストーリー上まだ公開していない情報を画面へ出さないため、編成の「後で加入する仲間」、
ギルド投資の未加入者タブ、Stage 選択カードの加入者名、遠征開始画面の未解禁 pack、
技能ツリーの manifest 外ノードを塞ぎました。来歴を持たない同業者3人（トキ / ヨリ /
アカリ）を編成画面に並べておくと、未公開の加入者と区別できず物語の先が割れるため、
Free mode ごと削除しています。付随して Free mode 補助の
`ecology-expedition-smoke.mjs` と `ecology-decision-space-smoke.mjs` も消しました。

旧 difficulty rank は画面から到達不能になりましたが、`newRun` の `difficulty` 欄と
`composeEncounter` の rank 引数は残してあります（Campaign は 0 固定）。

### 3.5 根城と図鑑（R13）

R11 が「日常の場面と設定の厚みはここに置く」と決めていたのに、どこにも無かった画面です。
名簿はギルドのタブに埋まっていたので、遠征のたびに一度必ず通る根城へ移しました。
図鑑は R8 §3.2 が ProfileState に挙げたまま未実装だったものです。**engine には一行も
足していません**（Profile に `bestiary` の一欄が増えたので contract-snapshot を作り直しました）。

### 3.6 予測を中心に据え直した（R14）

作者の指摘は「次のステージの完全な戦闘予測が得られる、というのがこのゲームのキモ」でした。
R8 §11 は exact preview を「無料・副作用なし・実行と完全一致」と定義していましたが、
**置き場所を「戦闘前の最終確認」画面にしか作っていませんでした。**組み替えの手は
キャンプのタブにあり、一手触るたびに進んで、見て、戻る。中心のはずのものが往復の先に
ありました。

- 予測をキャンプ全タブの上端へ常設。計算経路は増やさず、実行と同じ道を通す。
  毎 render で戦闘を1回走らせるので入力の署名で memo している（engine は決定的なので
  結果は変わらない）。
- **予測が別の盤面を走らせていた不具合を直した。**灰の門は12戦の梯子に属さないのに、
  画面は `composeEncounter` を固定で呼び、目の前にいない敵で試算した結果を出していた。
- 巻き戻す前の一戦では予測を出さない（読めても直せない予測は脅しにしかならない）。
- **技能を取り直し不可に。**予測が完全だと、技能の出し入れは賭けではなく最適解探しの
  作業になる。装備は従来どおり自由（都度の調整はそちらへ寄せる）。
- **偵察を廃止。**次の一戦が完全に読める以上、先の幕を1つ前倒しで覗く枠に値段がつかない。
- engine への追加は `startingHp` 一点だけ（減少量を出す側が passive の max_hp 補正規則を
  再現しなくて済むように）。

R6 §17.2 は「reset は使った点をそのまま戻す。遠征の途中で組み替えられないと、報酬で
得た技能が死に札になる」と言っていました。**この懸念は残っています**（GitHub Issue #102）。

### 3.7 人物を作り直し、題を `One Battle Ahead` にした（R13）

R11 の5人（シキ／ナズナ／カイ／スミ／レイ）を、ゴウ／ツグミ／ナギ／ヒバナ／ゲンゾウへ
差し替えました。全員が観察者で、全員が感情を抑制し、望みが抽象的で、体格と声量が揃い
すぎている——というのが差し替えの理由です（設計は
`analysis/CAST_REBOOT_TWELVE_TOMORROWS.md`）。

**engine の id は据え置きました。**`lancer` が受け役、`guardian` が遊撃役になり、id の
語義と中身は一致しません。id は技能・pack・contract の対応を保つ鍵であって役割名では
なく、改名は公開済み ID の引っ越しになるためです。代わりに、id を前提にしていた場所
——roster の役割・図像・既定配置・初期技能、Stage の問いと学習目標、docs——を全部
洗い直しました。

**pack の解禁順は動かしていません。**`campaign-stages.mjs` の検査が「sequence 0 以外は
primary_offense pack が残っていること」を要求し、campaign の primary_offense は
`pack_edge` 一つしか無いので、edge を後ろへ動かせません。**直したのは問いのほうです。**
問題は Stage 0 で既に出ている（主火力のツグミが一番柔らかく、ゴウは受け1）という形に
読み替え、Stage 1 は「誰が前に立つと、誰が振り抜けるか」、Stage 2 は「隊列を動かして、
何を得るか」に変えました。

**初期技能は数値の傾きで選び直しました。**旧 roster は R11 の数値向けのままで、
腕力16のナギに腕力依存の主力2枠、受け3のヒバナに受け役一式、集中6のゴウに集中依存の
防壁が入っていました。ゴウの active を一本だけにしてあるのは、Stage 0 に腕力で読む
技能が `steady_cut` しか無いからです（`strike` は枠を使わず必ず出る）。

**題を `One Battle Ahead` にしました。**検討の全文は `analysis/TITLE_STUDY.md` にあります。
決め手は尺度で、戦闘予測が見せるのはちょうど一戦先の確定結果であり、"one" が
「二戦先は見えない」という上限まで同時に言っている点です。日本語の副題は付けません。

### 3.8 チュートリアルで人物を掘るのをやめた（R15）

R13 は Stage 0 の会話に兄の失踪を置いていました（`stage_0_opening` の「お兄さんの記録が
出てから睡眠一時間減、朝食半分、脈が二」と、`stage_0_act2` の「ゴウは少し長く喋った。
ツグミは帳面に何も書かなかった」）。**開幕の一枚が喪失の場面になり、ゴウが最初から
寡黙な人物として読める**というのが作者評価でした。設定上のゴウは「声がでかい。ガサツで、
口が上手くて、調子がいい」であり、**別人になっていました。**

Stage 0 の8断片を、二人の**調子**だけを渡すものへ書き直しました。ゴウは減らず口で押し、
都合が悪くなると逸らし、押し切られると「へいへい」で流す。ツグミは早口で被せ、
丁寧語のまま容赦なく数を突きつけ、流されると「もう！」で丁寧語が剥がれる。
兄・記憶の速さ・言い過ぎた後悔は**全部外しました。**

**ゴウを素直に折らないことにしました（作者指摘）。**初稿は開幕を「……はい」で締めて
いましたが、**大男が急にしおらしくなる理由が読み手に無く**、しかも直後に一分で立って
先に行くので**言行が一致していません**でした。「へいへい」は口だけ合わせて従わない返事
なので、そこでやることと合います。**対等に見えるのは、折れる側がいないからです。**
`character-lore.mjs` の `warden.figure` も同じ形へ直しました（設定と台詞が食い違うと、
R13 で起きた乖離がそのまま再発します）。素直になるのは巻き戻したあとの
「……ああ。今日は、三分待つ。」**一度だけ**にしてあります。

**厚み（行数）とは別に、深さの勾配を置くことにしました**（`dialogue.mjs` 冒頭）。
望み・秘密・過去・後悔は五人が揃ってから出します。まだ誰のことも知らない読み手に
重さだけを渡すと、人物の調子が沈み、**後で沈んだときに意味が出なくなる**からです。

**兄の伏線は Stage 0 から消えました。**ゲンゾウが Stage 3 で「お兄様は、ご存命ですよ」と
出す側は動かしていませんが、**そこまでの助走がいまどこにも無い**状態です
（GitHub Issue #118）。名簿の `warden.field` / `warden.will` には残っているので、
読みに行った人だけが知っている形になっています。

### 3.9 冒頭戦闘を「他者手当て」の学習にした（R15）

冒頭は、ゴウを前列に置いても受け1の細かい被害で瀕死になり、並べ替えが「ツグミ死亡」から「ゴウ瀕死」へ変わるだけだった。敵のHP・攻撃順・seedを変えず、ツグミの初期 `triage` だけに `not_self` を付け、自分以外の味方を被弾量の50%だけ回復するようにした。既存の `emergency_treatment` は自己防衛として残したので、ツグミを前列に置くとゴウを救えず、後列に置くと自分をつなぎながらゴウを支えられる。隊列と役割の因果を一戦で見せつつ、RP1・chain1の被弾連動なので anti-stall も崩さない。さらに、巻き戻し時に `run.formation` を `PROLOGUE.formation` へ戻し、失敗配置を引き継ぐようにした。何も変えずに勝てる抜け道を塞ぎ、「一手直して勝つ」を画面でも成立させる。


### 3.10 冒頭の軽口を、関係の良さが先に立つ形にした（R15追補）

R15 の開幕は、ゴウの「見てんじゃねえよ」とツグミの「見るのが仕事です」、さらに過去の
負傷数を一息で突きつける応酬によって、**親しい二人の軽口より拒絶と詰問が先に読める**
状態でした。作者評価は「ゴウもツグミも、やや嫌な人物に見える」でした。

三分待たない筋と、ゴウが「へいへい」で流す性格は維持しています。そのうえで、ツグミは
校正の三分を診察に使おうとする世話焼き、ゴウは名前を呼んで観察眼を認め「先生」と頼る側へ
言い換えました。ツグミも「隠すのが下手」と笑って返します。**棘を抜くのではなく、棘を
向けられるほど近いことを先に見せる**変更です。戦闘へ入る理由、敗北、巻き戻し後の
「今日は、三分待つ」、勝敗条件は変えていません。


### 3.11 初戦の初期資源を空にし、勝利報酬を全員配布に戻した（2026-09-05）

R6 の当初仕様に合わせ、1戦目は技能点0・固定初期装備0から始めるようにした。通常戦の勝利時は技能点1を現在の編成全員へ自動で付与し、報酬候補から技能点カードと配布先の選択を外した。プロローグは遠征外として、活動資金と技能点の報酬を発生させない。Blueprint の明示的な持込品は、出発前の選択として残している。
### 3.12 冒頭の正解配置を余裕のある勝利にした（2026-09-05）

§3.9 で「一手直して勝つ」は成立したが、実際にはツグミを後列へ動かしてもゴウとツグミのHPが大きく削られ、位置変更の成功体験が細かった。敵HPだけを下げ続けると初期配置まで勝ってしまうため、通常戦の敵定義を変えず、prologueだけ敵HPを60%、攻撃（might / focus）を50%に調整した。初期配置はツグミが2ラウンド目に倒れる敗北を残し、正解配置は4ラウンドでゴウ167/300、ツグミ70/110を残して勝つ。位置だけを変える操作と「予測で確認して直す」ループを保った、チュートリアル専用の調律である。


### 3.13 装備を一つの呼称へ統一した（2026-09-05）

固定装備と手続きで組み上がる装備を報酬画面で分けると、プレイヤーには装備が二種類あるように見える。現行の報酬候補を装備2件と補給1件に固定し、画面・設計図・目利きの説明ではすべて「装備」と呼ぶことにした。装備の rule の完全開示、決定性、Blueprint への保存、持込時の復元は残している。過去の保存や検査を読めるよう、固定定義と generatedEquipment の内部形式は互換用に保持するが、通常プレイの報酬や装備画面では提示しない。

### 3.14 技能を54本足し、状態を3つ増やした（R16）

作者の要望は「面白い技能をたくさん」でした。**数だけ増やすと、同じ技能の係数違いが
並ぶ**——それは R6 §17.1 と R9 §4.2 が繰り返し禁じてきた形です。だから増やす前に、
**engine が既に持っているのに content が一度も使っていない語彙**を数えました。

| 使っていなかったもの | R16 で使い始めた技能 |
|---|---|
| `history_count`（content 全体で1箇所だけ） | 二の太刀・散らし斬り（同じ相手を続けたか）、静かな一手（このラウンド殴られたか） |
| `swap_positions` を**敵に**使う | 引きずり出す（敵の前後を入れ替えて後列へ刃を通す） |
| `timing: "interrupt"` を player 側で | 衝撃を殺す（飛んでくる数字を削る）、差し込む号令、出鼻を挫く（宣言そのものを消す） |
| `status_added` / `status_removed` を読む | 隙に応じる、目を離さない、刻印の残響、怯みを回す、裂傷の余波 |
| **敵の** `preparation_started` / `_advanced` | 溜めを読む、溜めを崩す（`interrupt_preparation` も初使用） |
| `status_stacks_scaled` | 積もる刻印（隙の段数そのものがダメージ量になる） |
| `lose_hp` コスト | 痛みを分ける（自分のHPで仲間の傷を買う） |
| `max_hp` スケール | 意地の壁（術力ではなく体で張る） |

**状態を3つ足したのは、相方が「隙」と「集中」しか無かったからです。**この2つだけを
相方にすると、新技能はどれも「隙を付ける／集中を得る」の言い換えになります。

- **怯み（staggered）** … 持ち主が**出す**ダメージが1段につき8軽くなる。
  倒さずに相手を細くする軸で、攻め手側から守りを作れるようになりました。
- **守勢（warded）** … 持ち主が**受ける**ダメージが1段につき8軽くなる。
  防壁（総量を吸う）・受け構え（回数を止める）に続く**三つ目の守り**です。
  減る量が固定なので**細かい多段に強く、大技には薄い**——既存の二つと三つ巴になります。
- **裂傷（bleeding）** … ラウンド終わりに一度だけ、1段につき12を**受け無視で**刻む。
  受けの厚い相手へ通る細い線です。

守っていること:

- **engine と schema の語彙は1つも増やしていません。**54本すべてが既存の event・
  effect・predicate・target で書けています（`analysis/ecology-contract-smoke.mjs`）。
- **完全上位互換を作っていません。**数字が大きいものには必ず、条件（1ラウンド目だけ・
  HP50%以下だけ・同じ相手を続けたときだけ）か代償（自分に「隙」・自分のHP・
  反応権2・戦闘1回きり）が付いています。
- **anti-stall。**戦闘防壁（ラウンドで消えない）を配る2本は、開幕2ラウンドに限りました。
  v1 schema では active に limit を書けないので、round で閉じるしかありません。
  裂傷も round で消えるので、待って積み上げる形にはなりません。

### 3.16 装備の等級を item / effect の二軸へ広げた（R17）

装備がほぼ毎回「補給より少し強い」だけになり、補給を選ぶ理由が消えていました。
一方で、10以上の Stage を各12戦・複数周回する前提なら、すべての drop を当たりにするのではなく、
大半はその遠征中に使える、少数だけ長期採用できる、という山が必要です。

そこで旧4等級を ID として残したまま、`mythic` と `oopart` を追加しました。item rarity は
rule 数・affix 予算・耐久・発動上限を広げ、各 payoff は別々の effect rarity を持ちます。
一つの item に最高品質を必ず一つ置き、残りは下位品質も混ぜるため、オーパーツでも
「基礎効果は遺物、効果1はオーパーツ、効果2は希」のような組み合わせが生まれます。
continuous effect は品質に応じて 100% / 115% / 135% / 160% / 195% / 240% に伸びます。
drop weight は 55% / 28% / 12% / 4% / 0.8% / 0.2% とし、何百個かに一つの偶然を残します。

既存 Blueprint の descriptor・定義・来歴は捨てず、新 generator version で新規品だけを差別化します。
生成に失敗した pool はこれまでどおり 50 attempt 後に診断 error とし、補給への単純な退避を
報酬設計の前提にしないことを狙います。

### 3.22 取得済み技能を無制限に装着し、順番と一時停止を保存する（R18、2026-09-05）

技能点を使った取得は一度だけで、忘却や払い戻しはできない。取得済みの行動・リアクティブ・常設は人数や枠数を理由に装着できなくならず、行動とリアクティブの順番は loadout に保存する。同じ条件を待つ同じ仲間のリアクティブは、その並び順で上から発火する。

装着済み技能には一時停止を保存できる。「誰を伸ばす？」でオフにした技能は取得状態や前提を失わず、戦闘と exact preview の BattleInput からだけ除外される。旧 save にこの欄が無い場合は全技能を有効として読み込み、技能の旧第4枠投資は購入不可のまま履歴だけを保持する。

### 3.23 技能ツリーを tier の格子から、派生の森へ（R19 / issue #137、2026-09-05）

それまでのツリーは「系統（攻撃／指揮／支援／守り／基礎）× T1・T2・T3」の格子だった。
節は tier ごとの箱に並ぶだけで、**どの節がどの節から派生したのかは画面に出ていなかった**。
前提は節を開かないと読めず、開いても名前が一つ書いてあるだけで、そこから先に何が生えるのかは
分からない。AP を払う行動と RP を払う反応が同じ箱に混ざるので、どちらの資源を伸ばす話なのかも
読めなかった。123 節まで増えた時点で、取得方針が立たなくなっていた。

ツリーを `requires` から組んだ森へ置き換えた。座標は手で書かず
`ecology/content/skill-tree-layout.mjs` が組む（x = 前提からの深さ、y = 行）。手で書くと
`requires` を直したときに黙ってずれるためで、代わりに座標が満たすべき決まり——座標重複・
x 列違反・線の交差・循環・分岐数不足——を `validateSkillTreeLayout()` と
`analysis/ecology-skill-tree-smoke.mjs` が全節と Stage ごとの部分森の両方で見る。

系統は種別（行動 / 反応 / 常設）の三つのツリーへ分け、画面上のタブで切り替える。種別をまたぐ
前提は普通の派生に混ぜず、**橋渡しの節**として明示する（反応ツリーの左端に「橋渡し ← 斬撃」が
立ち、そこから反撃たちが生える）。節を押すと前提ルートと派生先だけが強調され、開いた説明の
「前提」「派生先」は押せるので、iPhone でも横スクロールせずにルートを辿れる。節の上には
種別・消費（AP / RP）・対象または発動条件・深さ・分岐の数が出る。

既存の取得・装着・並べ替え・オン／オフ・AP/RP 消費は変更していない。

### 3.24 技能レベルと、x=1〜10 の深さ（R19 / issue #137 の残り、2026-09-05）

3.23 では「スキルレベル制と x=3 / x=5 / x=10 の大分岐は content 側の再設計なので入れて
いない」と書いた。**それでは設計を検証できない**（作者判断）ので、content と統合を同時に
進めることにし、各 content ファイルの冒頭にあった「ここを触ってよいのは X 担当だけ」の
分業規定を削除した。

**技能レベル。** 同じ効果の上位互換を別技能として増やす代わりに、一つの技能を段階的に
上げる。解禁は Lv1、そこから 1点ごとに 1段（最大 Lv10）。1段につき連続量（damage /
heal / barrier とその増減）が 12% 上がり、AP・RP・段数・回数・耐久は変わらない。連続量を
持たない技能（位置替え・号令・隙を刻む など）は「レベルなし」と画面に書き、点を払わせない。
上限は手で書かず、定義が連続量を持つかどうかから引く（`content/skill-levels.mjs`）。
engine は技能 ID で分岐せず、`ally.skillLevels` の表に載っている技能の連続量へ係数を掛ける
だけである（`effects.mjs` の `afterSkillLevel`）。**Lv1 は係数 1.0 ちょうどで掛け算そのものが
起きない**ので、レベルを知らない入力・保存・replay の結果は1バイトも変わらない。
`BATTLE_SCHEMA_VERSION` を `ecology-battle-4` へ、content contract を 12 へ上げた。

**深さと分岐。** 節を tier（0/1/2）の平面から、`requires` の入れ子で書く森へ置き換えた。
字下げがそのまま x（前提からの深さ、1〜10）になり、手で座標を書かない。x=1 が入口、
x=3 が1回目の役割分岐、x=5 が2回目、x=10 が最終到達点である。**技能も pack も1本たりとも
増減していない**（123 節のまま）。値段は 1節 1点に揃え、x=10 まで 9点——遠征1回で配られる
技能点とほぼ同じ——にした。

**届かない到達点を作らない。** 行動ツリーと反応ツリーには、最終 Stage までに実際に取り
切れる x=10 の道を一本ずつ通した（行動は「捨て身の一振り／手負いの突撃」、反応は「溜めを
崩す」）。`analysis/ecology-skill-tree-smoke.mjs` が、x=3 / x=5 の分岐・x=10 の複数到達点・
campaign からの到達可能性・宣言した座標と組み直した座標の一致を、全節と Stage ごとの
部分森の両方で見る。

**取得済み技能の前提も取得済みにする。** ツリーが一本道になったので、starter が x=5 の節
なら、そこまでの道も一緒に開く（`initialUnlockedSkills` が前提の閉包を取る）。線を辿れる
ようにしたのに、線の途中が欠けているのは嘘である。

### 3.26 種別をまたぐ前提（橋渡し）を廃止した（2026-09-05）

3.23（R19）は種別（行動 / 反応 / 常設）をまたぐ前提を「橋渡しの節」として明示する形を
試した。実際に説明すると「橋渡し ← 手当て」が何を意味するのか一目では読めず、

前提をまたいでいた9箇所を、同じ種別の中の別スキルの派生として繋ぎ直した

`guarded_opening` 系は反応の `mend` 配下、`steady_hands`・`first_blood`・`mark_reader`・
`opening_guard`・`held_breath` は常設の対応する `foundation_*` 配下）。深さ（x）と
費用は変えていない——橋渡しの直下の子は元々 x=2 だったので、同じ種別内の根の直下へ
繋ぎ直しても座標は一致する。

`skill-tree.mjs` から `from()` を削除し、種別をまたぐ前提そのものを書けなくした。
`skill-tree-layout.mjs` の橋渡し表示（bridge anchor）と、`app.js` / `styles.css` の
橋渡し用UI（「橋渡し ← X」の節・押すとツリーを切り替える導線）も削除した。
`analysis/ecology-skill-tree-smoke.mjs` に、種別をまたぐ前提が無いことを見る検査を足し、
自己検査（末尾）で実際に検出できることも確かめている。

### 3.27 巻き戻したあとの一戦を、本編第1戦として commit する（2026-09-05）

R11 §5 は「巻き戻したあとの勝利は本編1戦目」と DESIGN.md 6.4 の文面では既に書いていた
（「戦闘1後の観察」）が、`app.js` の実装は `prologueActive` が真のあいだ全部（本当に
負ける一回・巻き戻したあとの一回の両方）を「遠征外」として扱っていた。その結果、
巻き戻して勝っても持ち越し HP が commit されず（次戦は毎回全回復）、技能点も報酬候補も
出ないまま、そのあと別途フルスペックの本編第1戦（「灰の入口」）をもう一度戦わされていた。
実際に遊んだ作者から「巻き戻ったあとの一戦が1戦目として扱われていない」と指摘され、
文面どおりに直した。

**本当に負ける一回だけ**は `startPrologue()` が `simulate` action を経由せず直接
`simulateBattle` を呼ぶので、run を一切変更しない。**巻き戻したあとの一回**は通常の
`camp → battlePreview → simulate` を通るので、`simulate` handler から `prologueActive`
の特別扱いを外し、勝てば `recordEncounterCleared` / `grantRunSkillPointsToAll` /
`commitBattleResult` を通常戦と同じ経路で呼ぶ（encounterIndex は最初から 1 なので、
新しい index を発行する必要はない）。結果画面・報酬画面をそのまま出すため、
`prologueActive` を落とすのは `advanceAfterReward`（報酬を受け取り、次の戦闘へ進む瞬間）
まで遅らせた。ここで落とすまでは `currentEncounter()` が「灰の門」を指し続けるので、
結果・報酬画面のタイトルも正しいまま出る。

これにより、フルスペックの「灰の入口」を初回プレイでは戦わなくなった（2周目以降は
`prologue_seen` フラグにより従来どおり第1戦として出る）。功績・活動資金は
`recordEncounterCleared(run, 1)` が `expeditionEncounter(1)` の `kind`（"normal"）から
引くので、実際に戦った敵構成と無関係に、通常の第1戦クリアと同額になる。

補給チュートリアル（DESIGN.md 6.2）の表示条件は変えていない。`shouldShowSupplyTutorialAfterReward`
は encounter 1 の勝利を見ているだけなので、その勝利が巻き戻したあとの一戦へ前倒しに
なったことで、案内も自動的に「最初の敵を倒した直後」（＝本編第1戦の報酬を受け取った
直後）へ前倒しになる。

あわせて、`prologueActive` のあいだは画面ヘッダーの「安全に撤退する」導線を出さないように
した（`shell()`）。以前はチュートリアルの最中でもこのボタンが出ており、隊列を直しきる前に
遠征を放棄できてしまっていた。`abandon-run` / `back-title` の action handler 側にも同じ
条件の早期 return を足し、ボタンを消すだけでなく経路そのものも塞いだ。

`analysis/ecology-tutorial-trial.mjs` を新しい経路（巻き戻して勝った直後に結果・報酬画面が
出て、そのまま補給チュートリアルへ続く）に合わせて更新した。

### 3.28 技能ツリーの派生線を、インデントの目分量から実座標の直線へ（2026-09-05）

R19（3.23）で座標（x=深さ・y=行）は `requires` から機械で組むようになったが、画面は
その座標を**使っていなかった**。節を縦一列に並べ、前提の深さぶんだけ左に空白とレールを
足す、ファイラーの階層表示と同じ描き方だったため、兄弟が増えると「どのレールがどの節へ
つながっているか」を目で追う以外に手段が無く、作者本人から「どこと繋がっているか非常に
分かりにくい」と指摘された。横スクロールも `min-width` を少し超えるだけで、深い列を
押し込めて縮める方向に働いていた。

`ecology/content/skill-tree-layout.mjs` が既に持っている x・y をそのまま CSS Grid の
`grid-column` / `grid-row` に渡し、列を固定幅（`--tree-col-width`）にした。列を縮めない
ことで、深いツリーほど横スクロールで実際に場所を取る（これが「広く場所を取る」の実体）。
前提→派生の線は、`layoutSkillTreeConnectors()` が render() の直後に前提節と派生節の
実際の位置（`offsetLeft`/`offsetTop`、スクロール量に左右されない）を測り、列の間の余白へ
直角線の SVG `<path>` を引く。選択中の強調（前提ルート＝青・派生先＝緑・それ以外＝淡）も、
インデントのレールではなくこの線自体の色で見せる。

**ハマった点**: `<svg>` に `position:absolute; inset:0` だけを指定しても広がらない。
`width`/`height` を明示しない `<svg>` は既定で 300×150 の内在サイズを持ち、置換要素の
absolute 配置はその内在サイズを優先するため、`inset:0` は無視される（Chromium で確認）。
`width:100%; height:100%` を明示して初めて forest 全体を覆う。

古い `.tree-row` / `.tree-rails`（rail・elbow）は削除し、`.tree-cell` + `.tree-lines` に
置き換えた。座標を組む `skill-tree-layout.mjs` 側（x・y・requires からの森の組み方、
`validateSkillTreeLayout()` の検査）は変更していない。`analysis/ecology-tutorial-trial.mjs`
の「派生の線が引かれている」検査を、レールの elbow 数から `.tree-lines path` の数へ
合わせて直した。

### 3.29 技能ツリーの y、最初の子は親と同じ行を継ぐ（2026-09-05）

3.28 で座標を実線へ結んだ直後、作者から「1つ目の派生を1段下げる必要はない」と指摘された。

```
A-|              A---B---D
  -B-|             |-C---E
     -D               |-F
  -C-|
     -E
     -F
```

左（旧）は、枝分かれしていない一本道（A→B→D）も律儀に1行ずつ下げていたため、
「まっすぐ伸びる一本」と「実際に分かれる場所」が画面上で区別できなかった。右（新）は
最初の子が親と同じ行を継ぐので、一本道は文字どおり一本の水平線になり、行が増えるのは
実際に枝分かれした瞬間だけになる。

`skill-tree-layout.mjs` の `walk()` を直した。`y` を「訪れた順の行番号」ではなく、
外側の可変カウンタ `nextY` から引く値にし、**最初の子だけ親の `y` をそのまま渡し、
二人目以降の子だけ `nextY++` で新しい行を取る**。同じ親の子を再帰で処理する間、
`nextY` は前の兄弟の部分木が使った分だけ既に進んでいるので、次の兄弟は自然に
「前の部分木の直後」から始まる。根も、根どうしで行を共有しないよう `nextY++` から引く。

**「部分木がどこまで使ったか」の数え方が変わった。**旧実装は `y + descendants.length`
（部分木の節数）で部分木の終端行を出せたが、最初の子が行を増やさなくなったので、
節数と行数がもう一致しない。代わりに、部分木が実際に使い切った最終行 `maxY` を
子から親へ畳み込んで求める（配列は親が子より先に入っているので、逆順に読めば
子の `maxY` が先に確定している）。`validateSkillTreeLayout()` の「線の交差」検査も、
最初の子は `child.y === row.y` を許し、二人目以降は `child.y` が前の兄弟の `maxY + 1`
から始まることを見るように直した。

座標を CSS Grid にそのまま渡す `app.js` 側（`grid-column`/`grid-row`）と、実位置を測って
線を引く `layoutSkillTreeConnectors()` は無改修で動く——同じ行を共有する2枚が並ぶだけで、
CSS Grid は列さえ違えば同じ行番号を複数のセルへ割り当てられるためである。ただし
`align-items` の既定値 `stretch` のままだと、同じ行に「選択中で説明が開いた高い節」と
「短い節」が並んだときに短い方まで伸びてしまい、`layoutSkillTreeConnectors()` が測る
中心もズレる。`.skill-tree-forest` に `align-items: start` を足して、各節が自分の
自然な高さのまま上寄せで並ぶようにした。

### 3.30 技能ツリーの線、カード中心ではなく丸印（.node-icon）を測る（2026-09-05）

3.29 を見た作者から「同じ行のはずなのに横線がずれていないか」と指摘された。実際にずれて
いた。原因は `layoutSkillTreeConnectors()` が線の高さを**カード全体の中心**（`offsetHeight`
の半分）で決めていたこと。カードの高さは中身しだいで変わる——分岐バッジ「分岐2」が
付く節と付かない節、バッジが1行で収まる節と2行に折り返す節があり、同じ行を継ぐ最初の子
どうしでも高さが違えば中心もズレる。3.29 で最初の子の `y` を親と揃えても、揃うのは
座標（行）だけで、カードの見た目の中心まで揃う保証は無かった。

線の基準をカードの中心から丸印（`.node-icon`、直径27pxで全節に共通）の中心へ変えた。
丸印はボタンの左上に固定の位置にあり、`align-items: start`（このパッチで `center` から
変更）と合わせれば、右側の説明文が1行だろうと2行だろうと、カード先頭からの位置が
動かない。`layoutSkillTreeConnectors()` は `getBoundingClientRect()` で forest 原点からの
相対位置を測るよう書き直した（`offsetTop`/`offsetLeft` は測る要素の `offsetParent` に
依存するが、丸印は `.tree-cell` の子孫なので `offsetParent` が変わる。`getBoundingClientRect`
の差分ならどの階層の要素でも forest 基準の座標に落とせる）。

これで、同じ行を継ぐ節（＝最初の子として直線で繋がる節）は、カードの高さが違っても
丸印どうしが必ず同じ高さに並び、線がまっすぐになる。

### 3.32 装備に最低保証と規格外品を入れた（R21、2026-09-05）

### 3.33 予測と本番の入力を、呼び出し側でも一本にした（issue #148 続き、2026-09-06）

作者から「予測と結果が合っていない気がする。技能レベルの強化が効いていないのでは」
という報告があり、調べ直した。

**直接の原因はすでに直っている。**PR #156 まで、本番の戦闘は `app.js` が
`makeExpeditionBattle` を直接呼んで組み立てており、そこに `skillLevelsFor` が無かった。
技能レベルは予測にだけ乗り、本番の戦闘には乗らない——「予測と結果が合わない」と
「レベルを上げても強くならない」が、**同じ一つの欠落から同時に出ていた。**
現在の main では両方が `simulateExpeditionBattle` を通っており、手元の通しでも
序盤〜第3戦の予測と結果画面のHPは一致する。

問題は、**そのずれが engine 側の検査を一つも鳴らさなかったこと**である。ずれていたのは
engine でも `playable-battles.mjs` でもなく、`app.js` の**呼び出し2箇所のあいだ**だった。
共有関数を一本化しても、呼び出し側が違う options を渡せば同じことが起きる。そこで:

- `app.js` に `expeditionBattleOptions()` を置き、**予測（`previewNextBattle`）も本番
  （`simulateExpeditionBattle`）も、この一つの戻り値をそのまま渡す。**本番が足してよいのは
  結果を変えない `simulationOptions: { captureReplaySnapshots: true }` だけにした。
- `analysis/ecology-screens-smoke.mjs` が、その2箇所が同じ組み立てを通っていること、
  本番が余分な戦闘入力を足していないことを見張る。
- 予測 cache の鍵に `runUnlockedSkills` を足した。技能レベル表は取得表を辿って
  組まれる（`runSkillLevelsFor`）ので、**レベルだけを鍵にすると取得表が動いた回に
  古い予測が残る。**鍵が数えるべき欄も同じ smoke が見張る。
- `content/skill-levels.mjs` の `LEVELED_EFFECTS` と、`effects.mjs` で
  `afterSkillLevel` が実際に掛かる effect 型が一致しているかを
  `analysis/ecology-skill-catalog-smoke.mjs` が見張る。この表がずれると
  「Lv だけ上がって何も強くならない」技能が黙って生まれる——ファイル自身が
  「同じ表でなければならない」と書いていたのに、見張るものが無かった。

**もう一つ、報告の「効いていない」側には、直っていない理由がある。**戦闘予測の帯が
出すのは各人の残 HP と減少量、勝敗、ラウンド数だけで、**攻撃側の伸びは、倒すのに要る
ラウンドが変わらなければ一切表に出ない。**手元の実測（Stage 0 の2人編成、12戦分 ×
装着中の技能）では、1点ぶんの Lv1→Lv2 で帯が動いたのは 36件中3件、序盤の第1戦・
第2戦では一度も動かなかった。engine の側では確かに効いている（`steady_cut` を
Lv1→Lv10 で一撃 65 → 135）。つまり**戻せない技能点を払っても、ゲームの中心の
読み物が「何も変わらない」と言う。**

**当座の対処は、倍率を添えることではなく、説明文の数字そのものを動かすことにした**
（作者指摘）。「確かな斬り」は Lv 1 で「腕力130%の一撃」、Lv 2 で「腕力146%の一撃」と
書かれる。別行に「×1.12」と添えると、読み手が本文の 130% と掛け算する手間が残る。

### 3.33.1 変動量と固定量を、定義の側で分けた（作者指摘、2026-09-06）

最初の実装は、**書かれた数字のどれがレベルで伸びる量かを、あとから推し当てていた。**
説明文の % を集め、定義から引いた係数と一致するものだけを書き換える——「HP30%以下の敵へ
腕力200%」なら 200 だけを伸ばす、という具合である。動きはするが、係数と発動条件がたまたま
同じ数（「HP50%以下の敵へ腕力50%」）になった瞬間に決められなくなる。作者の指摘は
**「初めからスキル定義を変動量と固定量に分けておく」**で、そちらが本筋だった。

分け方はこうなった。

| | 何か | どこに書くか |
|---|---|---|
| 変動量 | その技能の damage / heal / barrier / 増減の amount。レベルで伸びる | **定義だけ。**説明文は `{amount}` と書いて指す |
| 固定量 | 発動条件の閾値、後列減衰、段数、耐久、AP / RP | 説明文に文字で書く |

現行 content を数えたら、**レベルで伸びる量を持つ57技能すべてが、それをちょうど一つしか
持っていなかった。**だから本文は「どの量か」を選ぶ必要すらなく、置き場所だけ書けばよい。
差し込み口は `{amount}`（変動量ひとつぶん）、`{total}`（× 段数）、`{hits}`（段数）の三つで、
**単位（% か素の数）は amount 型が決めるので本文は % すら書かない。**

```
steady_cut: "条件も準備もない、腕力{amount}の一撃。武器なので後列から出すと40%まで落ちる。"
              → Lv1「腕力130%の一撃」／Lv2「腕力146%の一撃」／40% は動かない
```

これで三つが同時に片づいた。

- **推し当てが要らない。**どれが伸びる数かは本文の形で宣言されている。
- **数字が一箇所にしかない。**`coefficientBps` を 13_000 から 17_500 へ変えれば説明文が
  「腕力175%」になる。2026-08-31 に6件出た「係数を変えたのに説明文が旧値のまま」
  （大溜めが実際 1000% なのに「400%」と表示していた）は、**書きようがなくなった。**
- **固定量が巻き込まれない。**40% や 30% はただの文字なので、伸ばしようがない。

`analysis/ecology-readout-smoke.mjs` の技能ぶんは、突き合わせから
**「二重に書いていないか」**（`skillTextIssues`）へ置き換えた。二つの場所に同じ数を書いて
一致を見るより、一箇所にしか書けなくするほうが強い。固定量と、装備・passive の
`statBonus` はこれまでどおり突き合わせる（言い回しが単位ごとに変わるため）。
同じ不変条件は `ecology/phase-b.test.mjs` にも置いてあるので、`node ecology/check.mjs`
だけでも捕まる。

移行は機械的に行い、**57件すべてで Lv1 の表示が1バイトも変わらないことを確かめた**
（例外は余剰治療の一件で、「余剰をそのまま回す」は Lv2 以降で嘘になるため
「余剰の{amount}を…回す」＝ Lv1「余剰の100%を」へ書き直した）。
`*_META` の説明文は**そのまま出せる文字列ではなくなった**ので、content contract の版を
`ecology-content-contract-15` へ上げ、凍結を作り直した。

帯の側で伸びを読ませる（与ダメージ・敵の残り・変更前後の差分）のは issue #148 の本体で、
設計判断が要るのでここでは踏み込んでいない。


### 3.37 技能の前提へ Lv を書けるようにし、勝利ごとの技能点を一箇所へ寄せた（issue #168 / #165 段階1、2026-09-07）

issue #165 は技能体系の全面再設計で、専用 branch（`design/skill-system-reboot-20260907`）
に現状監査と成長案がある。**カタログ本体を書き始める前に置くべき土台**が二つ見つかったので、
盤面を動かさない範囲でそれだけを先に入れた（issue #168）。

**一つ目は、前提に Lv を書けないこと。** ツリーの `requires` は技能 ID の配列で、
「その節を取得しているか」しか表せなかった。#165 の成長案は、系統 Lv や列埋めではなく
個別技能の必要 Lv を推奨している（同じ親から Lv1 で開く横枝と Lv3 で開く深い枝を
分けられる）。`{ skillId, minLv }` へ変え、`maxLv` も節へ出した。

判定を増やすときに一番危ないのは、**判定が四箇所に分かれること**である。解禁 API・画面の
「前提待ち」・加入時の無償閉包・保存の復元がそれぞれ独立に書いていると、片方だけが Lv を
見ない形へ簡単に戻る。そのとき画面は「解禁可能」と出して、押すと断られる。
`prerequisitesMet` 一つを四箇所が読む形にした。

無償閉包は「節を配る」だけでなく「要求された Lv も配る」ようにした。節だけ配って Lv1 に
置くと、加入直後から「取得済みなのに前提 Lv 不足で子が取れない」形が生まれる。

検査は二つ足した。**上限 Lv3 の技能へ Lv5 を要求する子**は永久に開かないので落とす。
そして**技能点の予算**を見る。前提の Lv も値段なので、節の値段を足すだけでは「その節に
何点要るか」が出ない。閉包込みで足し、一遠征ぶんの技能点（現在12点）を超える節を落とす。
現行は Stage 0 で最深3点、Stage 2 以降で最深9点だった。**右端まで初周で取り切れることは
要求していない**（#165 の方針。深い終点は後の進行で届いてよい）。

**二つ目は、同じ一戦から技能点が二度出せたこと。** `app.js` が勝利のたびに
`grantRunSkillPointsToAll(run)` を直接呼んでいた。活動資金の撃破分は
`recordEncounterCleared` が `region:index` を鍵に一度きりにしていたのに、技能点だけが
素通しだった。`grantRunSkillPointsForClear` へ寄せ、鍵を活動資金と揃え、量は
種別ごとの表（`SKILL_POINTS_PER_CLEAR`）から引くようにした。画面の「+n」も同じ表を読む。

**量とツリーは動かしていない。**現行の全前提は Lv1、技能点はどの種別も1点のままである。
SP 曲線（boss を2点にする等）と技能カタログそのものは #165 で比較中の未決事項で、
ここで混ぜると「土台の変更で盤面が変わった」のか切り分けられなくなる。
content contract の差分は `skillTreeNodes` の `requires` の形と `maxLv` の追加だけで、
技能の集合・レベル上限・報酬・合成 encounter は 1 バイトも動いていないことを確かめた。
