

## 取得予約（2026-09-12）

遠征中の技能点を、戦闘後に毎回ツリーへ戻って手動で一本道に投入する負担を減らすため、キャラクターごとに
目標技能を1つだけ設定できるようにした。現在のSPだけで、必要な前提の解禁・必要Lv・目標技能の解禁・
目標技能の目標Lvまで完了できる場合は「取得」と表示し、足りない場合だけ「予約」と表示する。
未取得なら目標はLv1、取得済みなら不足Lvを含む目標Lvを選ぶ。未取得の最大Lv1技能はLv1の操作だけ、
取得済み技能にはLv1の操作を出さず、最大Lvまで取得済みならLvXの操作も出さない。
予約は一本道の優先順位を明示するもので、予約した目標へ到達するために必要な前提と必要Lvだけを先に取る。
自動取得した前提はオフ、目標はオンで装着して、意図しない技能が戦闘順へ割り込まないようにする。目標の切り替えと
取消を可能にし、取得済みの技能を目標にした場合は不足Lvだけを自動取得する。経路の表示では、取得済みの前提は
強調せず、未取得の部分だけを水色にする。
勝利したら、現在の編成全員へ技能点を自動で与える。量は通常戦1点・精鋭戦1点・boss戦2点とする。精鋭戦は通常戦との差別化を報酬量では行わず、bossを遠征の到達点として一段重くする。誰に配るかを報酬画面で選ばせると、参加者間の優先順位だけが選択になり、同じ遠征を支える全員の成長が遅れる。プロローグ「灰の門」のうち、**本当に負ける最初の一回**だけは遠征の勝利報酬を発生させない（勝敗そのものが決定的な導入用の演出で、run を一切変更しない）。巻き戻したあとに勝った一戦は、本編第1戦そのものとして技能点・活動資金の対象になる（第1戦は通常戦なので装備の候補は出ない。§8.13）。

AGENTS.md の「守ること」の**理由**と、その具体的な形をここに置きます。数値の一覧は
実装が正本で、ここにあるのは初期設計値と、それを選んだ根拠です。
隊列を直して勝てても、次の戦いへ進むとHPが持ち越される。勝利直後にその事実を見せずにいると、戦闘の学びと遠征の消耗がつながらない。そこで、Stage 0の本編第1戦を初めて勝ってキャンプへ戻った直後に、既存の補給タブを開く。
## 1. 目的
開始補給は**どの遠征でも3個**（`STARTING_SUPPLIES_BASE`）で、永続強化「開始補給」がそこへ加算する（最大 +2、上限5）。導入だけ1個という特例は置かない——表記を残り／総数（3/3）にしたので、Stage 0 だけ分母が違うと最初の遠征で画面が嘘になる（PR #255 / §8.13）。
作者自身が、仕組みを理解した後も iPhone で繰り返し遊びたいゲームを作る。実装量、
検査数、完走率は目的ではなく手段です。

1. 仲間を編成の主語にする。人物には固有の役割、技能、装備の履歴を持たせる。
2. プレイヤーの選択が、敵、資源、次の構成、勝敗へ因果的につながるようにする。
3. ルールは読める形で提示する。次の戦闘の条件と敵の狙いは、開始前に確認できる。
4. 戦闘は決定的に再生できる。同じ入力と seed は同じイベント列を返す。
5. 新しい面白さは、既存のイベント語彙を組み合わせる content の追加から育てる。
6. 遠征内の消耗と遠征をまたぐ成長を分け、再挑戦と長期的な愛着を両立させる。
7. 面白さは作者の自発的な行動で判断する。機械検査は壊れた候補を落とし、観測可能性を
   確認するために使う。


## 2. 不変条件

- 人物は永続し、遠征ごとに消えない。**愛着の主語は人物、偶然性の主語は装備。**
- 同じ入力・seed・content / generator version から同じイベント列を返す。
- 新要素は共有 event、predicate、cost、effect、target relation で接続する。
- 完全上位互換を作らない。作る場合は明確な代償を付ける。
- Campaign Stage は一つ前の clear で順に解禁し、活動資金で買えず、飛ばせない。
- 通常行動には攻撃手段を保証する。技能未装備・全 skill skip 時は通常攻撃、純支援 active
  解決後は威力50%の追撃。明示された準備だけを例外にする。

## 3. pack の設計単位

強い構成は、固有名詞ではなく**共有イベントの経路**として記録します。

| 役割 | 意味 | 例 |
|---|---|---|
| 発生源 | 後段が読める事実・状態・余りを作る | `excess_healing`、`actor_moved`、`damage_blocked`、`actor_defeated`、`preparation_started` |
| 変換器 | event / resource を別の価値へ変える | 急かす、受け返しの集中、救急の小袋、拾い直し |
| 利得先 | 集めた価値を大きな結果へ変える | 大溜め、範囲攻撃、止めの一突き、強い回復・防壁 |
| 制動・代償 | 無料循環と万能化を止める | RP、AP、HP、耐久、round / battle limit、位置、準備時間 |

価値配分の目安: 単体は「採用理由はあるが汎用の最良行動を常に上回らない」、二部品は
「条件を意識すれば単体強化より明確に得」、三部品以上は「敵圧力と合えば素朴な役割配分を
大きく越えるが、別の圧力では代償が出る」。

### 閉じたレシピを避ける

- 一つの利得先へ到達する発生源を2つ以上用意する。
- 一つの発生源を読む変換器または利得先を2つ以上用意する。
- 同じ event を技能・装備・人物 signature の二領域以上が扱う。
- 想定構成から一部品を同じ役割の別部品へ交換できる。
- 発生源と最大利得先を一装備へ閉じ込めない。
- 敵は特定の SkillId を要求せず、初動・対象数・guard・block・位置・継続時間・
  resource pressure を変える。

**設計者が用意するのは答えではなく、複数経路を持つ接続面です。**

### 新 pack は昔の event を読む

新 pack のレビューでは、初登場 Stage／選んだ過去 pack／読む過去 event 2種以上／返す
event 2種以上／見え直す旧技能／設計レーン2本以上／各レーンの交換可能部品／苦手圧力／
あえて設計しない高次接続、を記録します。**旧技能の係数を新 Stage で密かに変えて
「見え直した」ことにしない。**同じ定義のまま、新 pack が event へ価値を与えて評価を変えます。

### 密度と攻撃の供給契約

一 pack の標準は active 4〜6（うち offense 3以上）、reactive 4〜6、passive 0〜2、
equipment affix 4〜6、enemy mutation 2〜3、boss law 1。発生源・変換器・利得先を各1つ以上、
自 pack 内で閉じる道1本、外へ開く event 2種以上。

pack は `primary_offense` / `offensive_hybrid` / `support` の役割を宣言します
（`ecology/content/packs.mjs` の `combatRole`、`campaign-stages.mjs` の manifest ラダー
検査が読む）。全 manifest に `primary_offense` を一つ以上（新規導入 Stage の幕1だけは
十分な攻撃力のある `offensive_hybrid` で代替可）、有効 pack 4以上では二つ以上。

## 4. anti-stall — 時間から HP を作らせない

> 敵を一体残して追加 round を経過させても、補給や遠征中に戻らない治療 charge を
> 消費しない限り、次戦へ持ち越す HP・補給・装備状態は改善しない。

この原則を冒頭の学習にも使う。通常戦の敵定義は変えず、prologue だけ敵HPを60%、攻撃（`might` / `focus`）を50%に抑える。位置だけの読み替えで結果を変えられる余裕を作りつつ、初期配置が勝ってしまうほどは弱めない。Stage 0 のツグミの「応急手当」は、`damage_taken` に連動し、RP1・chain1で、自分以外の味方だけを被弾量の50%回復する。自己回復を許さないことで、前衛ゴウ／後衛ツグミという隊列の因果を作りながら、時間を稼ぐだけの無料回復にはしない。

### 4.1 反応・連鎖の安全ゲート（Issue #175）

anti-stall は「敵が生きているまま待つと持越しが改善しない」を見る。これとは別に、
反応を増やす前に次の六つを機械検査する。

1. AP/RP の `gain_resource` は、行動の AP または有限の支払いと結び付く。監査は
   actor × resource × round の差分表を作り、明示された `resource_spent` を容量トークンとして
   transfer に一度だけ割り当てる。資源を読む rule が資源を返す場合は RP1 と `battle/1` を
   必須にし、直結再生成、同じ spend の二重割当、移送総量が支出を超える入力を落とす。
2. 同じ owner の同じ rule は、同じ chain の同じ trigger では一度だけ。別の技能を
   一律に止めるのではなく、rule ID と owner の組で記録する。
3. `lose_hp` が発生させる `damage_taken` には `event_tag(cost=false)` を明記し、
   被弾回復・反撃・生成装備が自傷支払いを敵の hit として読まない。
4. `excess_healing` の量は同じ `healing_proposed` 配下の `healing_applied` の
   `requested - actual` から来て、同じ overflow が一つの chain で二度消費されない。
   元の回復量を上限として黙って二重利用しない。event trace では overflow の直下の
   `ruleId` を downstream consumer として一意化し、複数 consumer も拒否する。
5. rule の limit は、`limit.owner: actor-instance + rule` で実行主体を宣言し、時間単位
   （chain / round / battle）と有限 count を必ず宣言する。装備でも生成装備でも同じ。
6. chain/battle の安全 cap は診断用の非常口であり、通常の anti-stall の主張ではない。
   持越し HP・物資・装備の検査は `ecology-anti-stall-audit.mjs` に残し、二つの結果を
   混ぜない。

現行の playable pack/tree から termination witness は公開していない。四つの loop witness
（AP の往復、被弾反響、防壁の再生成、準備の自己加速）は fixture 専用として残し、
`chain-safety` smoke の壊れた入力検査に使う。検査は `analysis/check-all.sh` の一部で、
現行定義・代表 trace・生成装備・意図的な壊れた定義をそれぞれ通す。


#### 4.1.1 資源報酬の許可条件と追加手順

\`gain_resource\` を含む定義を資源報酬と呼ぶ。安全ゲートは資源報酬を名前で許可する
一覧にはせず、定義の形と event trace の因果で判定する。新しい定義は、次のいずれかを
満たす必要がある。

- **有限コスト型**: 同じ action / rule に \`spend_action_points\`、
  \`spend_reaction_points\`、\`lose_hp\`、\`consume_barrier\`、\`wear_equipment\` のいずれかの
  支払いがあり、支払いを上回る資源を作らない。味方への transfer もこの条件の対象であり、
  対象が味方であることだけでは許可理由にならない。
- **外部イベントの一回型**: \`round_started\`、\`actor_activated\`、\`actor_defeated\` のように、
  資源獲得そのものでは再発火できない外部イベントに接続し、有限の \`limit\` と、必要な場合は
  対象条件を持つ。例えば \`actor_defeated\` は敵を対象とする条件を必須とする。
- **trace 上の transfer**: actor をまたぐ資源移送は、対応する支払いを event trace の親子
  関係で示す。現在の resource-to-resource transfer は \`resource_spent\` の親を一度だけ
  消費する形で検査する。支払いの証拠がない裸の \`resource_gained\` は許可しない。

現行の許可例は、\`foundation_ap\` / \`foundation_rp\`（round 開始時、battle/1）、
\`first_order\`（round 開始時、battle/1、round 1 の front ally）、\`scavenge_ap\`（敵を倒した時、
round/1）、\`worn_greaves\`（actor 起動時、round/1）である。\`patient_step\` の RP 支払い、
\`rescue_sachet\` の装備支払いは有限コスト型の例である。これらは
\`analysis/ecology-chain-safety-blind-spots.mjs\` の陽性ケースが実際の content 定義を参照して
監査へ渡し、許可されることを確認する。

\`free_defeat_ap\` のように同じ \`actor_defeated\` を読むだけで敵条件も一回性もない定義は、
\`scavenge_ap\` と同じ名前でないからではなく、許可条件を欠くため拒否する。
\`action_resolved\` / \`preparation_advanced\` を起点にした無償 AP も同様である。

許可例を追加する手順:

1. 既存の event / predicate / cost / effect / target / limit の組み合わせで定義し、
   engine や schema の語彙を増やさない。
2. この節の条件に照らして、発火イベント、対象条件、支払い、\`limit.owner\`、
   \`limit.scope\` / \`count\`、再発火できない理由を記録する。
3. \`analysis/ecology-chain-safety-blind-spots.mjs\` の \`allowedResourceCases\` に、実際の
   content 定義を参照する陽性ケースを追加する。ID だけを通す whitelist は作らない。
4. その許可例の条件を一つ外した近似不正例も \`skillCases\` または trace ケースへ追加し、
   監査を修正する前は CI が落ち、修正後は陽性・陰性の両方が通ることを確認する。
| 開始補給 | 3→4 は 12,000、4→5 は 60,000。基礎3・上限5（遠征中は増えない） |

非資源コストを使う actor 間 transfer を新しく追加する場合は、定義の陽性テストだけで
済ませず、対応する支払いを trace で表現できるかを先に確認する。表現できない場合は、
新しい例外名を足すのではなく、監査と event trace の契約を同じ変更で見直す。

## 5. 次戦結果の完全開示

戦闘が決定的で HP が持ち越されるなら、結果を隠すことは主に手計算と再試行を増やします。
作者の記録には「部品入れ替えごとに戦闘を予測するのはストレス」「正確な結果予測がすぐ
出るなら、UI の工夫でもっと面白くなるかもしれない」の両方が残っています。

開示するもの: 勝敗と round 数、各人物の開始 HP → 終了 HP と戦闘不能、消費する補給・
治療 charge・装備耐久、最初に構成が崩れた event、主要 chain、不発技能・対象不在・資源不足。

**失敗条件**（これが起きたら開示の設計が失敗している）

- 終了 HP が増えるまで技能・装備を一個ずつ交換し、event 接続を説明しない。
- 予測更新の待ち時間が構築時間の主部になる。
- preview があるため replay を見ず、何が効いたか分からない。
- 全戦闘を損傷0にする唯一構成が固定される。
- 予測値の微差だけを詰め、新 pack による旧技能の見え直しが起きない。

**対策は予測回数の制限ではありません。**入出力 chip、変更前後の主要 chain 差分、
ablation 表示で「何を変えたから結果が変わったか」を返します。

完全開示があるので、組み替えの自由度に値段を付け直してあります（技能は取得を忘れられないが、
取得済み技能の装着・順番・一時停止と装備は自由：`docs/GAME.md` §4）。

### 5.1 戦闘マップでは現在地と戦闘種別を分ける（issue #203）

12戦のマップでは、**現在地**が「いま押して進む場所」を示し、通常・精鋭・bossは
「その戦闘がどの種類か」を示す。二つは異なる情報なので、同じ強い枠で表さない。
クリア済み・現在地・未到達の3状態を背景と枠で分け、現在地だけに強い金色の枠を使う。
精鋭とbossは小さな記号と凡例で補助し、種別の意味を残しながら現在地と誤認させない。

### 5.2 キャラクター枠は顔を主語にし、情報を下部へ寄せる

戦闘予測と戦闘中の味方枠では、名前と職種アイコンを顔の上へ重ねない。顔そのものを識別手掛かりに
するため、目元を常に見せる。HP・AP/RP・状態は枠の下部へ集め、その部分だけを濃い帯で覆う。戦闘中の
行動内容はその帯のHP等より上へ置き、行動していない通常時は表示欄の高さも畳む。これにより、情報の
可読性を保ったまま、顔をさらに濃く・大きく見せられる。敵枠は既存のアイコンと名前を維持し、敵味方の
読み分けも残す。

## 6. 遠征内の学習順

新 pack を有効にしただけでは触れずに終わる可能性があるので、3幕を学習順に使います。

- **幕1** … 新 pack 単体の意味。第4戦 boss は新 pack 単体と baseline で越えられる。
- **幕2** … 過去 pack との二者接続。敵圧力が単体利用より接続利用を有利にする。
- **幕3** … 高次接続。第12戦 boss は専用鍵を要求せず、初動・継続・対象順・資源の複数軸を問う。

固定 pack が学習順を作り、seed 報酬が同じ文法内での適応を作ります。

### 6.1 初戦は空から始め、勝利時に全員へ配る

新しい遠征の最初の戦闘は、基礎技能点0に、ギルドで購入した永続強化「初期SPアップ」の段階ぶんを加えた状態から始める。固定初期装備は持たせない。出発前に選んだ Blueprint の持込品は、プレイヤーが明示した別の意思決定なので残す。初期SPアップは新しい遠征の開始時だけに効き、途中加入した仲間へ遡って配らない。

勝利したら、報酬候補を選ぶ前に現在の編成全員へ技能点を自動で与える。量は通常戦1点・精鋭戦1点・boss戦2点とする。精鋭戦は通常戦との差別化を報酬量では行わず、bossを遠征の到達点として一段重くする。誰に配るかを報酬画面で選ばせると、参加者間の優先順位だけが選択になり、同じ遠征を支える全員の成長が遅れる。プロローグ「灰の門」のうち、**本当に負ける最初の一回**だけは遠征の勝利報酬を発生させない（勝敗そのものが決定的な導入用の演出で、run を一切変更しない）。巻き戻したあとに勝った一戦は、本編第1戦そのものとして技能点・報酬候補・活動資金の対象になる。

### 6.2 最初の勝利の後に補給を一度使う

隊列を直して勝てても、次の戦いへ進むとHPが持ち越される。勝利直後にその事実を見せずにいると、戦闘の学びと遠征の消耗がつながらない。そこで、Stage 0の本編第1戦を初めて勝ち、報酬を受け取った直後に既存の補給タブを開く。

通常遠征の開始補給は0個へ改め、永続強化「開始補給」は0を基準に加算する。New Game の Stage 0 だけは、チュートリアル用の RunState へ開始補給1を注入する。これは通常遠征の無料分ではなく、導入の一手を成立させるための一個であり、補給を使った後は再挑戦・引き直し・野営治療の有限資源として残りを管理する。

採用した導線は「指定 → 治療を選ぶ → 対象を明示する → 結果と完了状態を同じ画面で返す → 完了まで次へ進めない」である。補給タブを自動で開き、集中治療以外の治療・他タブ・次の戦闘・撤退をチュートリアル中だけ閉じる。単体治療は通常時も対象を自動決定せず、プレイヤーが候補から選ぶ。全体手当だけは生存者全員を対象にする。

#### 6.2.1 他ゲームの導線比較と採用理由（Issue #209）

比較したのは、必須の一手を順番に渡す型、説明だけで任意に戻す型、目的を示しつつ手段を選ばせる型、カードと対象を同時に指す型の四つである。

| 型 | 参照したゲーム | 観察 | 今回の判断 |
|---|---|---|---|
| 手順を固定するスクリプト型 | XCOM 2 | チュートリアル任務の中で、次に取る行動を画面と任務が指定する。基本操作を飛ばさずに通せる一方、長い任務全体を固定すると本編の判断が消える。 | 「必要な一手が終わるまで次へ進めない」部分だけ採用。補給一回の短い導線に限定する。 |
| 説明後に任意へ戻す型 | Pokémon 系の捕獲導入 | 操作を説明した後は通常探索へ戻り、既に知っているプレイヤーは説明を飛ばせる作品・場面がある。 | 今回の要件には不採用。補給を使わず次戦へ進める既存の抜け道が残るため。 |
| 目的を示して手段を選ばせる型 | Into the Breach | 目的と盤面を同時に見せ、プレイヤーが複数の合法手から具体的な一手を選ぶ。 | 「治療が必要」だけで対象を勝手に決めず、負傷者候補を出して対象を選ばせる部分を採用。 |
| カードと対象を同時に指す型 | Hearthstone | 次に使うカードと対象の位置を同じ画面で示し、実行直後に盤面の変化を返す。 | 集中治療の強調、対象ボタン、結果表示を同じキャンプ画面へ置く部分を採用。 |

採用型は、XCOM 2 の短い必須ゲートと、Into the Breach / Hearthstone の明示的な選択・即時結果を組み合わせたものにする。現在のゲームは戦闘中に入力せず、キャンプで有限資源を配分するため、専用の会話や別画面を増やすより、治療ボタンと対象選択を同じ RunState の操作として扱う方が因果を隠さない。通常時までタブを固定すると補給の判断を奪うため、ロックは初回の Stage 0 チュートリアルに限る。

### 6.3 技能は忘れず、装着状態だけを調整する

技能点を使った取得は取り消せず、前提の解禁状態も保持する。一度取得した技能は人数や枠数を理由に装着できなくなることがなく、アクティブ・リアクティブ・パッシブの各欄へすべて追加できる。アクティブとリアクティブは欄の上から順に判定し、同じトリガーを待つリアクティブは同じ仲間の並び順を先に解決する。

「誰を伸ばす？」では、取得と装着を分けて表示する。装着済み技能は一時的にオフにでき、オフ状態は取得や前提を変えず、preview と本番の BattleInput からだけ除外される。これにより、前提として取った技能や現在の問いに合わない技能を保持したまま、RP・AP・判定順への影響を抑えられる。

### 6.4 序盤の巻き戻しは情報を分ける

プレイヤーには敗北と巻き戻りを見せるが、巻き戻し直後のゴウはツグミへその事実を説明しない。
ツグミが違和感を拾う余地を残し、**戦闘1後に彼女自身が到達する。**先に答えを台詞で渡すと、
この観察の一拍が消える。

**到達の手がかりは、言葉尻ではなくゴウの様子である**（R16追補・作者稿）。いつもなら
憎まれ口を叩く人が礼を言う、という一点で足りる。ゴウが漏らした語を数えさせる案も試したが、
**十五歳が急に検事になった。**設定の「丁寧語のまま容赦がない」は、冷たいという意味ではない。

**到達したら、ゴウは認める。**設定は「本当に素直になるのは、流した先で誰かが傷ついたとき
だけ。滅多に無い」であり、ツグミが死んだのだからこれがその一度である（§3.8 の「素直は
『三分待つ』一度だけ」は、開幕で理由なくしおらしくなるのを止めるための縛りであって、
条件が揃った場面まで塞ぐものではない）。そのうえで彼は「台帳にも書かねえ。さっさと帰って、
全部忘れよう」と言う。**外へ出れば遠征の記憶は崩れる**ので、これは嘘ではない。

### 6.4.2 会話の知識は、書く順ではなく人物の側で決める（R16）

6.4 の分離は Stage 0 の巻き戻しだけの話ではない。**書きたい順に情報を置くと、
知識の矛盾と人物の崩れが同時に起きる。**R16 で四件を直し、規約にした。

1. **巻き戻りを覚えているのはゴウだけ。**ツグミは「さっき」を先に言わない。彼女が
   拾えるのはゴウが漏らした語だけで、数えるのも自分の記憶ではなくゴウの口である。
2. **ヒバナの歳は本人の申告。**誰かが先に言えば、それは知り得ない情報になる。
3. **照会は坑の中では返らない。**紙に訊いて紙が返るまで一往復かかる。投げるのが
   Stage 2 の加入場面、返るのが詰所へ戻る stageEnd である。
4. **ゲンゾウはその照会を読んで来た。**十三号室からの二件——記録の無い子と、五年前に
   戻らなかった者——が、彼が戸を叩く理由であり、兄の件と根城の「先日」の根拠でもある。
5. **先見機が読めた内容に、人物は驚かない。**§5 のとおり予測は次の一戦の個体・並び・
   **結果まで**見せる。読んでから入った者にとって、戦闘後に新しい情報は「盤面の外で
   起きたこと」だけである。予測の出ない一戦目（§6.4）だけが、この制約の外にある。

**人物はゲームのシステムを知らない。**腕力・集中・受け・行動権・反応点・隊列・
後列減衰・手番を、誰も一度も言わない。盤面の理屈は規則ではなく観察として言わせる。

これらは `ecology/story.test.mjs` の「誰が何を知っているか」節が検査する。

### 6.4.3 プロローグのあいだは離脱経路を塞ぐ

序盤の一戦（本当に負ける一回・巻き戻したあとの一回のいずれも）は、隊列を一手直せば
勝てることを実際に確かめさせる導入である。この途中でタイトルへ戻る・安全に撤退する
ことができると、直しきる前に離脱して「一手直せば勝てる」を確認しないまま抜けられて
しまう。だから `prologueActive` が真のあいだは、画面ヘッダーの離脱ボタンそのものを
出さない（`abandon-run` / `back-title` の action handler 側でも、万一のため同じ条件で
弾く）。

### 6.4.4 教える一手だけは、押す場所を光らせてそこしか押させない（作者指摘 2026-09-12）

**「最初のチュートリアル、並べ替えてツグミを後ろに下げる部分をちゃんとしたチュートリアルに
してほしい。押すべき場所が光って、そこしか押せなくなる、よくあるチュートリアル」**

旧稿の §6.4.3 は「この一戦を進める操作（隊列・技能・装備の調整、戦闘の開始・再生、
報酬の受け取り）は塞がない」と書いていた。**離脱だけを止めれば足りる**という判断で、
巻き戻し直後の手引きは遠征タブの一段落（「上の『⇅ 隊列』からツグミを後列へ」）だけ
だった。だが**その一段落は、操作を知っている人にしか読めない。**初めて開いた画面には
タブが四枚・盤面が六枠・釦が十数個あり、「⇅ 隊列」がその中のどれなのかを探すところから
始まる。導入の山（一手直すと予測が敗北から勝利へ変わる）へ着く前に、技能ツリーや装備を
一周してしまえる。

だから**教える一手のあいだだけは、押す場所を光らせ、そこ以外を押せなくする。**

- 段は三つ（`⇅ 隊列` → 動かす仲間 → 後列の空き枠）。**段ごとに次の一押しだけを言い、
  その理由を一つだけ添える。**一度に三つ説明しない。
- 錠は**並べ替えの三手だけ**に掛ける。ツグミが後列へ入った瞬間に外れ、盤面も通常へ戻る。
  そこから先は技能も装備もセーブも予測も自由に触れ、`この敵に挑む` は**光るだけで
  塞がない**。**教えるのは一手であって、遠征の触り方を全部禁じるのではない**——配置を
  戻して予測がどう動くかを見る遊びは、この導入の中心なので取り上げない。
- 錠の最中も**盤面の数字（HP・予測・減少量）は沈めない。**この一手の理由はそこに出ている。
- **教える一手は content が持つ**（`PROLOGUE.tutorial` の `characterId` / `row`）。
  光らせる先も錠の判定も同じ選択子から出すので、「光っているのに押せない」枠が構造として
  作れない。

離脱経路（タイトルへ戻る・撤退）を塞ぐ §6.4.3 と役が違う。あちらは**この一戦を抜ける
のを止める**、こちらは**この一手へ導く**。

### 6.4.5 Campaignの会話イベントは再訪でも同じにする

opening / join / 幕の断片 / stageEnd は、初訪か再訪かで本文や演出を変えない。
同じ Stage を繰り返すときも、同じ断片を同じ順で通常の一行送りへ通す。
既読印は Stage 選択カードの解禁情報には使うが、会話イベントの省略条件には使わない。

Stage 0 の序盤の敗北・巻き戻しは、Stage の学習を成立させる専用チュートリアルなので
初回だけ実行する。これは Campaign の通常イベントを初訪／再訪で分ける判断とは別の
進行制御であり、補給チュートリアルも同様に一度だけ表示する。

この方針なら、stageEnd は初回クリア時だけの報酬演出ではなく、Stage を完走するたびに
同じ精算前イベントとして読める。読み飛ばしたい場合は、会話画面の SKIP を使う。

### 6.5 陣営フェーズで一行動ずつ交互にする

行動順を内部の instance ID で横断的に競わせると、完全予測できる戦闘でも
プレイヤーが次の一手を読みづらい。そこで round の AP 回復後、味方が隊列順に
一人一行動、その後に敵が隊列順に一人一行動する。どちらかに実行可能な行動が
残る限り、この二つのフェーズを繰り返す。AP2 は「連続二回」ではなく、次の自軍
フェーズでもう一度動ける権利として扱う。

主キーは陣営→隊列→同位置の内部 ID とし、能力値を行動順から切り離す。これなら戦闘予測と
replay の列を人間が読みやすく、敵の位置と次の味方フェーズを見ながら編成を考えられる。
味方先行はプレイヤー側の恒常的な先手になるため、チュートリアルを含む数値は
実際に遊んで確認する。

## 8. 装備の生成契約

一つの装備は `unconditional stat 1 + trigger -> condition 0〜1 -> cost 0〜1 -> effect 1〜3
-> limit -> durability / charge`。最初の stat は装着中かつ未破損なら常時働き、装備と同じ
rarity の `max_hp / might / focus / guard` のいずれか一つとする。item rarity と effect rarity は
別軸で、前者は組み合わせの幅と品質下限、後者は個々の payoff の量・発動上限を決めます。
不完全な trigger だけ・effect だけ・発火不能・無料無限循環は生成しません。

trigger・condition・payoff は共通の役割タグで照合する。追加 condition は効果量を一段上げる
代わりに最大一つとし、条件数を affix 下限の穴埋めに使わない。これにより、厳しい条件を
重ねた末に無関係な小効果が出る組み合わせを拒否する。

payoff の `tier` は同じ効果へ予算を追加して買う内部強化段階（0〜2）であり、effect rarity
とは別軸である。回復の基準値は tier 0 / 1 / 2 を 3 / 5 / 12 とし、effect rarity の倍率を
適用してから端数を切り捨てる。回復量に個別の上限は置かない。自分の HP を消費する代償と
自分専用の回復 payoff は、一つの装備内で同時に生成しない。

**レアリティは色だけにしない。** 装備全体は格番号（1〜6）と一般的な名称を併記し、
効果は「基礎効果・常時」「追加効果1」ごとに同じ格番号・名称を表示する。常時効果は先頭へ
固定し、追加効果はレアリティの高い順に並べる。同格の効果は元の効果順を保つ。報酬画面ではレジェンダリー以上
だけカード枠と短い発見表示を強める。希少性を強調しても、条件・代償・
数値・発動回数の完全開示は削らない。高位の入手を喜ばせる主役は、派手な隠し演出ではなく、
拾った瞬間に「どの効果が当たりか」を理解できることに置く。

| rarity | 完結 rule 数 | 総 affix 目安 | 追加効果の最低品質 | keystone |
|---|---:|---:|---|---:|
| common | 1 | 1〜4 | common | 0 |
| rare | 1〜2 | 2〜6 | common | 0 |
| epic | 1〜3 | 3〜8 | rare | 0 |
| legendary | 2〜4 | 4〜10 | epic | 0〜1 |
| mythic | 2〜5 | 5〜13 | legendary | 0〜1 |
| oopart | 3〜6 | 6〜16 | mythic | 1 |

common / rare だけは、有限の重い代償（耐久2またはHP15）を同じ rule に持つ場合に限り、
追加効果を item より最大2段高くできる。これは低レアの上位互換化ではなく、短命・危険と
引き換えに build の核になりうる規格外品を作るための例外である。



## 8.5 技能ツリーは、派生を線で見せる（R19 / issue #137）

**節の座標は手で書かない。** ツリーは `requires` から組んだ森で、x（前提からの深さ）と
y（行）は `content/skill-tree-layout.mjs` が決める。手で書いた座標は、`requires` を直した
瞬間に静かにずれる。代わりに、座標が満たすべき決まり——座標重複・x 列違反・線の交差・循環・
分岐数不足——を機械が見る（`validateSkillTreeLayout()`）。

**最初の子だけ親と同じ行（y）を継ぐ。** 二人目以降の子だけが新しい行へ下りる（前の兄弟の
部分木の直後）。枝分かれしていない一本道を律儀に1行ずつ下げると、「まっすぐ伸びる一本」と
「実際に分かれる場所」の区別が付かなくなる（作者からの指摘、2026-09-05）。この組み方から
「同じ列で y が重ならない」「実際に分かれる場所だけが新しい行を生む」「線が交差しない」の
三つが出てくる。あとから座標を直して壊す余地が無い。

**前提は必ず同じ種別の中に置く。** AP を払う行動と RP を払う反応が同じ枝に混ざると、
どちらの資源を伸ばす話なのかが読めない。三つのツリー（アクティブ / リアクティブ / パッシブ）へ分け、
互いをまたいで前提にしない（旧 R19 は種別をまたぐ前提を「橋渡し」の節として明示する形を
試したが、分かりにくいので廃止した。analysis/ecology-skill-tree-smoke.mjs が
種別またぎの前提そのものを検出する）。

**未解禁の節も出す。** ただし manifest に無い節は出さない（R12 の判断は変えていない）。
出ている節には、状態と必要な技能点と前提を必ず添える。

**子は必ず親と同じか後ろの pack に置く。** pack は Stage ごとに増えるので、前提が後の
pack に居ると「画面に出ているのに永久に解禁できない節」になる。順番は
baseline → 構えと手当て → 刃と撃破 → 防壁と隊列 → 行動権と準備 で、同じ pack の中では
core（入口）が先、full が後である。

**届かない到達点を、本編の最終 Stage の到達点として扱わない。** 本編に出ない pack の節は
設計図として明示する。全体の深さと本編の最終 Stage での到達範囲は、`SKILL_TREE_LAYOUT` と
manifest から毎回導出し、`analysis/ecology-skill-tree-smoke.mjs` が検査する。

**取得済み技能の前提は、必ず取得済みである。** starter が x=5 の節なら、そこまでの道も
一緒に開く（`initialUnlockedSkills` が前提の閉包を取る）。線を辿れるようにしたのに、
線の途中が欠けているのは嘘である。

## 8.6 上位互換は別技能ではなくレベルにする（R19 / issue #137）

**同じ行動の「少し強い版」を別の技能として増やさない。**増やすと、同じ条件の技能が並び、
装着順とオン／オフの組み合わせだけが際限なく増える。代わりに一つの技能を段階的に上げる。

**上げるのは連続量だけ。** damage / heal / barrier とその増減に係数が掛かり、AP・RP・
段数・回数・耐久は変わらない。「1段上げたら手数が増える」は、多くの面白い技能より
強くなりやすい（R6 §6.8 が passive で言っているのと同じ理由）。

**上限は手で書かない。** その技能が連続量を持つかどうかで決まる
（`content/skill-levels.mjs`）。手で書くと、効果を書き換えたときに「レベルは上がるのに
何も強くならない技能」が黙って残り、点を払わせておいて何も返さない罠になる。

**値段は深さと同じ通貨・同じ値段（1点）。** 深く伸ばして新しい役割を得るか、いま持って
いる技能を厚くするかを、同じ天秤で選ばせる。払い戻しは解禁と同じで無い。

**Lv1 は掛け算そのものを起こさない。** レベルを知らない入力・保存・replay が、これまでと
1バイトも変わらない結果を出す。

## 8.7 前提は「持っているか」ではなく「Lv いくつか」で書ける（issue #168 / #165 段階1）

技能ツリーの前提は、これまで**技能 ID の配列**だった。「その節を取得しているか」しか
書けないので、深さ（`x`）と分岐の数以外に、取得の順番を設計する手段が無い。
#165 の再設計は、系統 Lv や列埋めではなく**個別技能の必要 Lv**を推奨案に置いている
（同じ親から、Lv1 で開く横枝と Lv3 で開く深い枝を分けられる）。

そこで、前提を `{ skillId, minLv }` にし、`maxLv` を節のデータへ出した。

- **判定は一箇所だけ。**`content/skill-tree.mjs` の `prerequisitesMet` を、解禁 API・
  画面・加入時の無償閉包・保存の復元が共有する。別々に書くと、片方だけが Lv を
  見ない形へ戻り、そのとき画面は「取れます」と出して、押すと断られる。
- **無償閉包は要求した Lv も無償で配る。**加入時に節だけ配って Lv1 に置くと、
  「取得済みなのに前提 Lv 不足で子が取れない」形が加入直後から生まれる。
- **上限を超える要求と、予算を超える節は機械が落とす。**上限 Lv3 の技能へ Lv5 を
  要求する子は永久に開かない。前提の Lv も値段なので、節の値段を足すだけでは
  「その節を取るのに何点要るか」が出ない。`analysis/ecology-skill-catalog-smoke.mjs`
  が閉包込みで足し、一遠征ぶんの技能点を超える節を落とす。
- **右端まで初周で取り切れることは要求しない。**#165 の方針どおり、深い終点は後の
  進行で届いてよい。検査は「一遠征の技能点を全部使っても届かない」だけを落とす。

**issue #176 で、実データが初めてこの形を使った。**「長く守る」が「傷へ盾を Lv3」を要求する。
同じ親から、Lv1 で横（まとめて手当て＝条件付きの面の守り）が開き、Lv3 まで厚くして初めて
深い枝（戦闘のあいだ消えない壁）が開く。**必要 Lv も値段**なので、この節は閉包込みで
初期技能から3点かかる。Stage 3 の「隊列で守る」構成がこの道を通り、第5戦の時点で取り切れる
（`analysis/ecology-stage3-builds.mjs`）。SP 曲線の決定は8.8へ移した。

## 8.7.1 割合で並べる鍵を engine へ足した（issue #176）

庇う・防壁・守勢・回復の宛先は `hp_asc`（残りHPの小ささ）で選んでいた。既存の語彙では
「傷の割合で並べる」が書けない（`hp_percent` フィルタは閾値で切るだけで、並べられない）ので、
`hp_percent_asc` / `hp_percent_desc` を schema・selectors・validator・engine テストへ
一組で足した。値は `hp * 10000 / maxHp` の切り捨てで作るので、**浮動小数は比較経路に
入らない。**同率は既定の `position_asc` → `instance_id_asc` へ落ちる。
どちらの鍵をどこで使うかは 8.7.2。

## 8.7.2 攻撃は残りHP、庇護は傷の割合（issue #176、作者判断）

**狙い先の言葉を二つに分ける。**

- **「最もHPの低い相手」＝残りHPそのもの**（`hp_asc`）。**攻撃の狙い先。**倒し切るための
  狙いは残量で決まる。割合へ寄せると、HPの大きいボスが「弱っている」側に来てしまう。
- **「最も傷ついた味方」＝傷の割合**（`hp_percent_asc`）。**庇護・防壁・守勢・回復の宛先。**
  最大HPが 110〜300 まで開いた隊で残りHPの小ささを使うと、半分まで削られたゴウ（150/300）より
  ほぼ無傷のツグミ（100/110）が庇護され続ける。

**敵の攻撃も同じ規則に従う。**以前は行の先頭固定（`position_asc`）で、実測では

- 2人の Stage 0 で、ツグミを**前列右へ出すと6戦の被害が 0**（後列へ下げると 132）
- 5人の Stage 3 で6戦を通しても、後列右のツグミの被害が 0

だった。**殴られるのは前列左と後列左だけ**で、主火力の既定位置は全ステージで安全地帯である。
前列と後列の選択が「どこに置くと安全か」ではなく「左端を避けるか」になっていて、隊列の話が
成立していない。

残りHPで選ぶようにすると、**紙の主火力は届く場所に居る限り必ず先に狙われる。**武器の敵は
前列が生きているあいだ前列しか狙えない（engine の reach 契約）ので、「後列へ下げれば届かないが、
武器攻撃の威力も落ちる」という R11 §5 の交換がそのまま盤面に出る。直後の実測では、
ツグミを前へ出すと6戦の被害が 0 → 224 になり、第6戦で敗ける。

## 8.7.3 Stage 0 は導入、三構成の検証は Stage 3（issue #176、作者判断）

#165 の関門は「3つの異なる構成が第4〜6戦までに動く」「全構成が同じ主攻撃+回復で倍率だけ違う、
は失敗」である。**これを Stage 0 で確かめようとしない。**2人・1 pack の Stage 0 で三つの構成を
競わせようとすると、盤面を難しくする方向でしか差を作れず、**導入として本末転倒になる。**
最初の2人 Stage は単純に勝てる形にする。

検証は5人と4 pack が揃った Stage 3 で行う（`analysis/ecology-stage3-builds.mjs`）。
三つの分かれ目は「何を主な出来事にするか」に置いた。

| 構成 | 発生源 | 変換器 | 利得先 | 制動 |
|---|---|---|---|---|
| 刃で削る | 当たった一撃 | 受け崩し・貫き突きが受けを無視し、足を払うが怯みへ変える | 怯みは相手が**出す**ダメージを削る | 怯みはラウンドで消える。抜く一撃に手番を先に払う |
| 隊列で守る | 受け構えで止めた拍 | 受けの受け渡しが盾を配り、受け返しの集中が集中へ変える | 止めるほど前列が保ち、止めた拍が別の役割の資源になる | 受け構えは回数。多段に剥がされ、反応点も減る |
| 順番を作る | 行動権と準備 | 背を押すが隊列の最後へ行動権を渡す | 準備1回の大技が毎ラウンド完成する | 渡した側は手番を捨てている。手数は増えない |

**溜め技は技（focus）で伸びる。**腕力50・技術6のゴウが溜めても何も起きないので、
「順番を作る」の溜め手は技術52のツグミである。**渡す先を間違えると engine は黙って弱いだけ**
なので、この検査は「勝ち切れるか」も見る。

**入口の core は「その Stage で実際に鳴る節」だけにする。**一度も発火しない節を入口へ並べると、
点を払った側は何が起きなかったのかを知る手段が無い。Stage 0 から外したのは余剰治療
（回復が全部「直前の被弾量に比例」なので、上限を超える回復が構造的に起きない）と
目を離さない（Stage 0 の敵は隙を付けてこない）と受け流し（技術で伸びる自分用の防壁は、
技術6のゴウにも、狙われる回数の少ないツグミにも噛み合わない）の三つで、どれも pack の
full には残っている。

## 8.7.4 状態の意味は、定義の隣に一度だけ書く（issue #176）

作者から「守勢って何でしたっけ」という問いが出た。技能の説明文には「守勢を1つ」としか
書いておらず、**守勢そのものが何をするかは、どこにも書かれていなかった。**

`content/statuses.mjs` に `STATUS_GLOSSARY` を置き、画面（技能タブと戦闘画面のヘルプ）は
それを並べるだけにした。段数・持続・向きは**定義から引く**ので、効果を変えれば説明も動く。
`analysis/ecology-readout-smoke.mjs` が、全状態に一行があることと、書いた「1段につきN」が
定義の量と一致することを見張る。

## 8.7.4.1 買った節は、鳴らなければ罠である（issue #176、作者試遊）

`content/skill-levels.mjs` は既に「強くならないものへ点を払わせない」と書いている。
**取得についても同じ**で、点を払った節がその Stage で一度も発火しないなら、払った側は
何が起きなかったのかを知る手段が無い。

作者試遊で「余りを溜める」（ラウンド終わりに行動権が余っていたら集中）に疑いが向いた。
実測すると、Stage 3 の8戦で `resource_unused` は反応点で 58 回出るが、**行動権では一度も
出ない。**engine のフェーズは「実行可能な行動が残る限り味方→敵を繰り返す」うえ、技能が
全部不発でも通常攻撃が出せるので、**行動権が余る局面が構造的に起きない。**同じ発生源を
読む affix「余りの」と装備「静観レンズ」も同じ理由で死んでいる（到達可能性そのものは #191）。

**宣言を読むだけでは気づけない**ので、`analysis/ecology-stage3-builds.mjs` が
取得計画の各節を走らせて数えるようにした。rule を持つ節（行動・反応・常設）は、6戦の
あいだに一度は自分の `skillId` か `ruleId` を出さなければ落ちる。能力値だけを動かす常設は
event を出さないので対象外である。**この検査は、私自身が組んだ構成の死に技を落とした。**

## 8.7.4.2 通り道は目的地ではない（issue #230）

8.7.4.1 の「買った節は鳴らなければ罠」を12戦へ広げたとき、検査が**弱い構成を作る方向へ
圧力をかけている**ことが分かった。深い節を買うと前提の節も一緒に買うことになり、前提まで
装着しないと「鳴らない節」で落ちる。ところが 8.7.5 のとおりアクティブは順番に回るので、
**装着を増やすほど主砲の出番が割れる。**検査を通すために弱くする、という形になっていた。

だから**前提として通っただけの節は、その先の節が鳴っていれば「使われた」と数える。**
数えるのは人物ごとで、同じ節でも別の人物にとっては通り道でしかない。レベルまで上げた節は
「使うつもり」なので免除しない（点を払って厚くしたのに一度も出ないなら、それは罠のままである）。

## 8.7.4.3 遠征を通すと、能力値と技能の噛み合わせが効いてくる（issue #230）

12戦の通しで最初に効いたのは、技能の強さではなく**誰がどの技能を装着しているか**だった。

- ゴウは腕力50・技術6。受け崩し（腕力）へ届くまでに前提として買う後衛狩りは**技術**で
  伸びるので、装着するとその拍は7しか出ない。ナギは腕力16・技術30で、逆に後衛狩りが主砲になる。
- ツグミの狙い撃ちは技術×1.25で、ゴウの確かな斬りとほぼ同じ量が出る。**治す人を守りへ
  全部回すと、隊の火力が半分になる。**守る構成が幕3で時間切れになるのはこれが理由である。
- 反応の攻撃線（反撃 → 隙に応じる → 痛みで研ぐ → 意趣返し）は `damage_taken` を起点にする。
  敵の狙い先は残りHPの低い味方なので、**最大HPが一番大きい人物は最後まで狙われず、その人の
  反応はすべて死ぬ。**点の置き場として成立しない組み合わせがある。
- 「痛みを分ける」は発動ごとに HP を30払う。急かすへの通り道として買い、**装着だけしない**と
  決めた瞬間に、同じ構成が第11戦で止まる状態から第12戦の完走へ変わった。

**装備でも技能でもなく「装着したかどうか」で通しの結果が変わる。**#177 の画面は、この
噛み合わせを取得前に読めるようにするためにある。

## 8.7.8 通常のゲームシステムは、文章ではなく形と色で見せる（issue #177、作者方針）

**文字を読ませてよいのは、物語と技能の説明文だけである。**「深く遊びたい人が読むところ」に
文章を置くのはよいが、値段・段・出番・噛み合わせのような**毎回読むもの**を文章にすると、
画面が説明書になる（作者判断、2026-09-09）。

語彙は四つに絞った。**増やさない。**

| 形 | 何を表すか |
|---|---|
| 丸（ピップ） | **払うものだけ**——行動点・反応点・代償のHP |
| 色つきの小チップ | 効果量。`腕 130%` のように、能力値を掛ける前の係数と印を並べる |
| 目盛り | 出番だけ。「装着した本数のうちの一本」 |
| 色 | テーマ（攻撃・守り・支援・指揮・基礎）と能力値（腕力・技術・受け） |

**同じ形に二つ目の意味を持たせない。**初稿では丸が、行動点・反応点・代償HP・条件の有無・
取得状態の五つを別々に表していて、見分けが付かなかった（作者指摘、2026-09-09）。丸は消費へ
譲り、取得状態は鉤（✓）、入切は摘み（スイッチ）にした。

**数で足りるものは数で書く。**段（レベル）は `Lv1/10` の文字にした——ほとんどの節が Lv1 なので、
10個の目盛りに1個だけ塗る形は「読めない模様」になる。量も棒をやめて数にした——長さは
「どちらが大きいか」しか出さず、**節をまたいで比べるには桁が要る。**

**条件は短い薄字で書く。**「ありかなしか」を白抜きの丸で出していたが、**いつ出るのかは
一行の値打ちがある。**「HP50%以下の敵がいるとき」「自分が後列のとき」「被弾したとき」を
技能名の下へ置く。文は `intrinsicPredicates` と対象の絞り込みから組み立てるので、
定義を変えれば表示も動く（手書きの説明文を持たない）。

意味の対応表は、技能画面の折り畳み「記号の意味」に**一度だけ**置く。節や装着行の上には
出さない——出せば結局そこで文章を読むことになる。読み上げには `aria-label` と `title` を
必ず付ける（記号だけでは支援技術に何も伝わらない）。

**効果量のチップは、issue #230 の発見を読み手へ委ねる形に直したものである。**
能力値を掛けた人物別の実数ではなく、技能が持つ係数を能力値の印と一緒に出す。
「腕 130%」なら、ゴウ（腕力50）なら65、ナギ（腕力16）なら21相当になることを、
プレイヤー自身が能力値と掛けて判断できる。技能画面が人物ごとの優先順位を先回りして決めない。

計算は `content/skill-levels.mjs` の `leveledEffectOf` / `skillTextAtLevel` に置いた。
**変動量を出している effect を探すのはそこ一箇所**で、説明文の差し込みと同じ関数を読む
（二箇所で探すと必ずずれる）。詳細欄にはこの人物別の最終値を繰り返さず、技能の説明文だけを残す。

取得コストは取得済みのチェックと同じ実線四角に数字で出す。前提がある未取得節では、
前提を満たすまでのコストを破線四角、その横の `+`、この節の取得コストを実線四角で並べる。

## 8.7.9 装着順の結果は、帯で返す（issue #177）

8.7.5 で「アクティブは順番に回る」を規則として採った。**規則を文で説明する代わりに、
結果を絵で返す。**戦闘後の画面に「出した順番」の帯を置き、人物ごとに、どのラウンドに
何を出したかをテーマの色と印で並べる。動かなかった拍は点線の枠にする。

装着の側にも同じ形を置いた。装着行の「出番」の目盛りは、有効な装着本数のうちの一本を
示す。**装着を増やすほど一本あたりの出番が減る**ことが、増やした瞬間に目盛りへ出る。

## 8.7.5 アクティブは順番に回る（issue #176 の発見 → issue #187 で採択）

作者の報告は「アクティブスキルを2つセットしても、結局片方しか使っていない」。そのとおりで、
`chooseTactic` は**インデックスを持たず**、毎回そのつど上から見て最初に使える一本を返していた。
1番目に無条件の技能を置くと、2番目以降は永久に出ない。

**規則の側を変えた。**`chooseTactic` に**アクターごとのカーソル**を持たせ、現在位置から登録順へ
循環して読む。選んだ技能の次へ進めるので、無条件の技能 A / B は A → B → A と回る。条件・対象・
    勝てば普通に次の一戦へ進み、負ければ普通に再挑戦へ落ちる（専用の出口を作らない）。
カーソルを進めない**（空振りで順番だけが流れると、次に何が出るか読めなくなる）。

カーソルは `state` に持つので、同じ入力からは同じ順番が出る（決定性は保つ）。preflight の
`chooseTactic` はカーソルを進めない——進めると、実際の行動より先に枠を消費してしまう。

条件つき技能の意味も残る。**先頭が条件付きで未達なら後続へ落ちる**ので、「条件が合う拍だけ
出したい技能」は今までどおり書ける。変わったのは「無条件の技能を並べたときに後ろが死ぬ」ことだけ
である。画面側は、技能のルールのヘルプと、装着行の**無条件／条件つき**表示をこの挙動に合わせた。

## 8.7.6 行動の不発も結果である（issue #192）

戦闘ログは HP が変わった場面だけを記録するものではない。敵味方を同じ粒度で追えるよう、
行動の宣言・対象・コスト・開始・解決を残し、行動を取り消した場合は `action_canceled` に理由を
付ける。防壁で攻撃を吸い切った場合は `damage_taken` を捏造せず、
`damage_proposed` → `barrier_damaged` / `barrier_broken` → `damage_absorbed` の因果を残す。
多段攻撃が倒れた対象へ進んだ場合は `damage_skipped` として、再ターゲットせず不発理由を残す。

`damage_absorbed` と `damage_skipped` は反応の起点にはしない記録イベントである。これにより、
ログを詳しくしても「防壁を削ったこと」や「不発したこと」へ新しい反応が連鎖して、戦闘結果が
変わることはない。replay は `schema.mjs` の既知イベントをそのまま履歴へ渡し、盤面では
攻撃の拍にまとめる。

## 8.7.7 防壁の残量をHPとの比率で読む（issue #208）

防壁は数値だけではHPに対する大きさが直感的に分かりにくい。そこで戦闘盤面では、HPバーの上端に灰色の帯を重ね、 `barrier / maxHP` を表示幅とする。最大HPを超える防壁は100%で頭打ちにする。防壁の数値マークは補助として残し、防壁0では帯を描かない。表示はreplay snapshotの `barrier` と `maxHp` から毎拍更新するため、付与・吸収・破壊・期限切れを同じ状態から読める。

## 8.7.8 HP内訳と低HP警告を同じ意味で読む（issue #226）

#221／PR #225で、HPバーは攻撃単位の回復窓を盤面へ出す4区分になった。#226では、情報量を
増やし過ぎずに残りHPと回復窓を同時に読めるよう、次を採用する。

- **区分の意味を固定する。** 緑は現在HPのうち今回の攻撃でまだ回復していない分、濃い緑は
  同じ攻撃で回復した分、赤は回復可能な残ダメージ、黒は確定したダメージである。回復済みの
  濃い緑は次の `action_started` またはラウンド／戦闘境界で緑へ統合し、残った赤は黒へ移す。
  戦闘不能では `recovery_window_closed` と同じ表示拍で赤を黒へ確定する。
- **残りHPの主色へ低HPを統合する。** 生存中の現在HP割合だけを整数 bps で判定し、56%以上は緑、
  26〜55%は黄、25%以下は赤とする。残HP区分は主色、同じ攻撃で回復した区分は主色の薄め、
  まだ回復可能な区分は主色のかなり暗めとする。回復不能区分は常に黒である。HPによってカード枠は
  変更せず、行動・狙い・被弾など既存の枠表示を維持する。戦闘不能は専用の敗北表示とし、枠へ低HP色を
  重ねない。
- **角丸は意味の境界だけに置く。** 区分間の通常の境界は直角、最初に見える区分の左端は丸角。
  赤がある場合だけ赤の右端（赤／黒境界、または赤の外側終端）を丸め、赤が無い場合は黒の手前の
  最後の非黒区分を丸める。全損時は黒区分を外側として丸める。これで、濃い緑を紫の別資源や
  赤を瀕死警告と誤読させず、赤／黒の境界だけを「この攻撃の回復窓の終端」として読める。
- **検査も同じ意味を読む。** `ecology/hp-gauge.mjs` が区分・閾値・角丸対象を純粋関数として
  返し、`app.js` は replay snapshot からそれだけを読む。`hp-gauge.test.mjs` は残りHPの色分け、
  4区分の合計、回復中・確定後・全損時の角丸を確認する。画面の通し検証は、実際のreplay snapshot
  から描かれたゲージが最大HP幅を連続して埋め、各拍で角丸の意味を保つことだけを確認する。

## 8.8 勝利ごとの技能点は、量も冪等も一箇所で決める（issue #168 / #174）

以前は app.js が勝利のたびに grantRunSkillPointsToAll(run) を直接呼んでいた。戦いの種別で量を変える場所が無く、**同じ encounter を二度勝つと二度配れた。**活動資金の撃破分は recordEncounterCleared が region:index を鍵に一度きりへしていたのに、技能点だけが素通しだった。

grantRunSkillPointsForClear へ寄せ、量は SKILL_POINTS_PER_CLEAR（種別 → 点数）から引き、鍵は活動資金と同じにした。画面に出す「+n」も同じ表から引く。

今回の採択は **案b** とする。

| 戦いの種別 | 1勝の技能点 | 位置づけ |
| --- | ---: | --- |
| 通常戦 | 1 | 基本の学習単位 |
| 精鋭戦 | 1 | 通常戦と同じ報酬量。精鋭であることは敵圧力で表す |
| boss戦 | 2 | 幕の到達点として一段重くする |

現行の12戦（通常6・精鋭3・boss3）を全て勝つと15点、最後のboss直前までで13点になる。精鋭戦を2点へは引き上げない。曲線と冪等は progression.mjs の表・鍵に集約し、画面側へ別の数値を置かない。

## 8.9 初期SPアップを永続強化へ置く

META_UPGRADES に starting_skill_points（表示名「初期SPアップ」）を追加する。最大3段で、各段階は新しい遠征の開始技能点を+1する。費用は活動資金から払い、購入履歴と残高は既存の MetaPurchase と同じ ProfileState に残す。未購入時の基礎は0なので、購入後は開始時に1〜3点を持つ。

この値は newRun(profile) が RunState を作るときだけ読み、途中加入した人物へ遡及しない。遠征中に獲得した技能点は従来どおり RunState にのみ置き、Profile へ漏らさない。開始時の選択肢を少し増やしつつ、全ての勝利報酬を一律に増やさないための、上限付きの永続投資である。

将来の追加 Stage では、**通常戦2点・精鋭戦3点**の高難度構成を候補として検討する。これは将来ステージのバランス案として記録するだけで、現行ステージの通常戦・精鋭戦やboss報酬には適用しない。敵圧力、到達点までの必要技能、実際の試遊を確認してから別途決める。

## 8.10 必殺技は新しい技能ではなく、既存技能への変換規則にする（issue #238）

必殺技を「一人一つ持てる強力な専用技能」として作ると、いずれ**必殺技の表**ができる。
表ができれば、そこに載っている技能が最適解になり、通常技能の選択はその前段階へ落ちる。
AGENTS.md が禁じている「固有 ID の相方で面白さを作る」形そのものである。

そこで**必殺技を、取得済みの技能に掛ける変換規則ひとつ**として実装した。ドラクエ10の
スキルアップパネルと同じで、必殺技の中身は元の技能が決める。作者が「これまで見向きも
していなかったスキルが、必殺技になると輝く」と言ったのは、まさにこの形である。

### 規則（`ecology/ultimates.mjs` の soft data）

  1. **単体が全体になる**（自分だけを守る効果は味方全員へ、行・列に広がる効果も全体へ）
  2. **量が3倍になる**（全体化と両立する）
  3. **溜めが消える**
  4. **防壁が戦闘のあいだ残る**
  5. **リアクティブの必殺は反応点を払わない**

**AP・hit 数・耐久・行動権は変えない。**技能レベルが離散量へ掛からないのと同じ理由で、
手数を増やす効果は多くの面白い技能より強くなりやすい（R6 §6.8）。この線引きの副産物として、
「行動権を渡すだけ」「位置を替えるだけ」の技能は必殺技にできない。**必殺にできない技能が
残ること自体が、必殺化が一律の強化装置になっていない証拠**である。

一度は「広さと太さを両立させない（全体化した効果は量を据え置く）」で出したが、作者から
**「ダメージ2倍はしょっぱい。もっと増やしていい。強くしたら当然その分敵も強くするべきで、
到達ステージが増えるのは妥当」**という判断が来たので両立させ、倍率も上げた。敵側の調整は
#189 ほかで受ける。

### リアクティブが弱く見える問題（作者指摘）

「明らかにリアクティブに必殺を切るのがアクティブより弱そう」という指摘は正しかった。
反応は**装着順に上から反応点を払う**ので、下の行に置いた必殺が「点が尽きて出なかった」で
終わることがある。**一戦に一度きりの一手が資源競合で消えるのは、選択ではなく事故である。**
だから必殺だけは点の外に出した（規則5）。防壁が戦闘のあいだ残る（規則4）のも同じ理由で、
守りの必殺が「そのラウンドだけ厚い」で終わると攻めの必殺と釣り合わない。

作者が挙げた「回復の限界突破（受けたダメージを超えて大回復）」は**採っていない**。
engine の回復は「直前の攻撃の実HPダメージが上限」という契約を持っており、それを必殺だけ
破ると、回復窓・過剰回復・HPバーの4区分がすべて例外を持つことになる。上限そのものの再設計は
#221 / #189 の領分なので、issue へ切り出した。

### パッシブは候補にしない（作者方針）

必殺技には**放つ瞬間**が要る。カットイン演出を載せる場所（§8.12）であり、代償を払う拍でも
ある。パッシブは常時効いているので、その瞬間を持てない。

### 「隊で三つ」ではなく「一人一つ」（作者判断で変更）

最初は隊で共有する3回にしたが、作者から**「同じキャラが何度も撃つのはゲームの幅が狭い。
各キャラ1回ずつ（5人なら通しで5回）にしたい」**と来たので、**人物ごとに一遠征1回**へ変えた。
共有の枠だと「一番強い必殺を持つ一人へ全部寄せる」が最適になり、残り四人の指定が死ぬ。

  - **指定（誰のどの技能か）は無料でいつでも変えられる。**ここに値段を付けると、
    「指定を変えると損」が生まれて、ビルドを試す自由が減る。
  - **構えるのは戦闘ごと。**構えても、条件が揃わなければ出ないし、回数も減らない。
  - **回数が減るのは勝った戦闘だけ。**負けて再挑戦した一戦は無かったことになる。

**補給を払って必殺ゲージを貯める案は採らなかった。**作者自身が「装備が減るインセンティブが
働くから微妙」と書いたとおりで、補給は既に再挑戦・引き直し・野営治療の三つで取り合っている。

### 1ラウンド目に出さない（作者指摘）

「必殺技が1ターン目から出るのはなんかキモい」「不発してもつまらない」という指摘への答えは、
**時間ではなく状況で止める**ことにした。全必殺の共通条件を「**隊の誰かがHP70%未満**」にする。

  - 1ラウンド目にはまず出ない。敵の一撃を受けてから切り返す形になる（行動点2の人物なら、
    削られたあとの同じラウンド内で出ることはある）。
  - 「不慮の全滅を必殺で防ぐ」という作者の欲しかった絵が、条件そのものから出る。
  - 序盤の楽な一戦では出ない。それは**要らなかったということ**なので、回数も減らない。
  - **不発を黙って起こさない。**予測が最後まで走らせているので、`previewNextBattle` は
    「この一戦で誰の必殺が出るか」を返す。構えた時点で ✹ と行の印がそれを出す。

### 専用の枠を画面へ置かない（作者指摘）

「UIがダサい（というか邪魔）」という指摘のとおりだった。必殺技はたまにしか触らない操作
なのに、常設の枠を出すと毎回そこを読み飛ばすことになる。触る場所は装着行しかないので、
**その行を長押しすると指定・解除**にした（作者の提案そのまま）。画面に増えたのは、
見出しの小さな菱形（残り人数）と畳んだ説明だけである。

### 操作は長押し一回に畳む（作者指摘 2026-09-12）

初版は「長押しで指定 → 行の ✹ を押して構える」の二手だった。**指定（ビルドの選択）と
構え（一戦に賭ける選択）は概念として別**で、予測も engine もその二つを読む——が、
**操作として分ける価値が無かった。**指定だけして構えない状態には使い道がなく、必殺を
出すたびに毎回二手を要求していた。一人一遠征に一度きりの一手に二手を掛ける理由は無い。

そこで**長押し一回で両方を動かす**（`toggleUltimateForBattle`）。行の ✹ は押す釦ではなく
状態の印になり、行内の当たり判定の取り合い（長押しの親と釦の子）も消えた。model の側は
`setUltimate` / `toggleUltimateArmed` を原子操作として残してある（概念を畳んだのは UI だけ）。

**代わりに、構えている行は光らせる**（作者要望「もっとかっこよく光らせて」）。段は三つで、
**段の差がそのまま状態の差**である——指定＝金の縁、構え＝金が脈打つ、この一戦で本当に
出る（予測が言っている）＝光が走る。放ち終えた行は脈を止めて沈める。文字を足さずに
「構えたか」「出るか」「もう放ったか」が読めるので、行の説明文は増えていない。

### 長押しは、押している時間そのものを見せる（作者要望 2026-09-13）

長押しの唯一の弱点は**いつ入るのか分からないこと**である。押した瞬間は何も起きず、
450ms 後に突然状態が変わる。そこで**押している時間を、行の左から右へ伸びる光の帯**に
した。帯が右端へ届いた瞬間が、必殺が入る瞬間である。途中で離すかスクロールすれば帯ごと
消える（＝取り消しがそのまま見える）。既に構えている行では帯が灰色になる（＝解く操作）。

**帯の長さの正本は JS の長押し判定の定数ひとつ**で、CSS へは `--long-press-ms` として
渡す。二箇所に書くと、いつか「満ちたのに入らない帯」ができる。この帯だけは
`prefers-reduced-motion` でも止めない——装飾ではなく、押している時間の目盛りだからである。

### 必殺の残りは「隊の合計」ではなく「人物ごと」に出す（作者指摘 2026-09-13）

初版は技能タブの見出しに「必殺を残す仲間 ◆◆◇」という隊の合計を出していた。だが
**一人一遠征に一度きりで、隊で分け合う枠でもない**のだから、合計は「あと何回あるか」に
しか答えない。プレイヤーが知りたいのは「**誰の**一回が残っているか」である。

合計はやめ、印は**上端の盤面のセル**——常にその人物ひとりを指している場所——へ移した。
四段あり、残っている（薄い ✹）・構えている（金の ✹）・この一戦で出る（光る ✹）・
もう放った（灰の ✧）を、どのタブを開いていても同じ場所で読める。結果画面の一行も
人数から**名前**へ変えた（「必殺を残す仲間 2 / 3」→「まだ残しているのは ゴウ・ツグミ」）。

## 8.11 必殺技を教える一戦は、巻き戻しではなく予測で教える（issue #240）

#238 で仕組みは入ったが、**どこで覚えるのかが無かった。**Stage 1 から解禁されるだけで、
画面には畳んだ説明があるだけだった。作者の要望は「冒頭の先見機（灰の門）みたいに、
負けそうになって必殺技で切り返す」である。

**灰の門の巻き戻しは使わない。**あの演出が教えているのは「予測という道具がある」ことで、
Stage 1 ではもうその道具を持っている。もう一度負けさせてから巻き戻すのは、同じ教材を
二度やることになる。だから**予測そのものを教材にした**——構えない予測は「敗北」、
構えた予測は「勝利」。帯が変わるのを見てから挑む。

盤面（`ULTIMATE_LESSON`）は engine で本当に走らせて決めてある。構えなければ7ラウンドで
時間切れ、ツグミが落ち、盾兵が残る。構えれば5ラウンドで勝ち、誰も落ちない。**差は必殺
ひとつぶんだけ**で、`ecology/story.test.mjs` が両方を実際に走らせて固定している。

  - **12戦の梯子の中に置く。**灰の門は第0戦（遠征の外）だが、この一戦は第1戦そのもので、
    勝てば普通に報酬へ進み、負ければ普通に再挑戦へ落ちる（専用の出口を作らない）。
  - **手取りは三段**（ナギのセルを押す → 行を長押しする → 遠征タブを押す）。
    初版は二段で、構えた拍に画面が自動で遠征タブへ跳んでいたが、作者から「遠征タブに
    進むのもユーザーに押させてチュートリアルの一部に」と来た。**勝手に動く画面は
    手取りではない**——構えた行をそのまま見せたうえで、次の一手も本人に打たせる。
    四段目に「挑む」を数えないのは同じ理由の裏で、それは錠の外にあり、押す義務も無い
    （配置を戻して予測がどう動くかを見る遊びを取り上げない）。
  - **教える技能は content が決める**（`ULTIMATE_LESSON.tutorial`）。選んだのはナギの
    溜め突きで、**溜めが要るせいで使いにくい技能**が「溜め不要・全体へ・量3倍」になる。
    #238 が狙った「見向きもしなかった技能が必殺になると輝く」がそのまま絵になる。
  - **条件（隊の誰かがHP70%未満）がその一戦の中で自然に満たされる配置**にした。
    条件を教えるための一戦なので、条件が揃わないまま終わってはいけない。
  - **会話は増やさない。**加入の会話（`stage_1_join`）が既にナギの刃を語っているので、
    手引きの札だけで足りる（R9 §7 の断片数を増やさない）。
  - 錠の作りは隊列チュートリアルと共有する（`tutorialGate()`）。**手取りの型を二通り
    作らない。**

## 8.12 必殺のカットインは、拍を一つ増やして作る（issue #242）

必殺は一人一遠征に一度きりで、**その稀さはカットインを載せるために選んである**（§8.10）。
作り方の選択は「拍を一つ増やす」か「既存の `action_started` の拍を長くする」かだったが、
**増やす**を採った。着弾と同じ拍に演出を重ねると、ダメージの数字と立ち絵が同時に出て
どちらも読めなくなる（準備付き行動が準備完了と着弾を別の拍にしているのと同じ理由）。

**engine も schema も触っていない。**必殺は新しい event を持たないので、`buildBeats` は
ID の形（`ult_`）だけを読む。アクティブは宣言の event（`action_started`）があるので盤面が
動く前に置けるが、**リアクティブは宣言を持たない**（`fireRule` は効果だけを出す）。
そこだけは最初の効果で拍を開き、見せる盤面を一つ前にして「効果が乗る前」を出す。
どちらも同じイベント列からは同じ順で出るので、一時停止・一手送り・戻す・速度変更・
自動再生のどれでも崩れない。**飛ばす手段も既にある**（速度変更と一手送り）ので、
専用のスキップは置かない。

### 解禁は Stage 1 から（作者判断）

Stage 0 は2人・1 pack の導入で、武器と技の違い・隊列・応急手当をここで覚える。
そこへもう一つの仕組みを載せると、覚えることが多すぎる。**3人になる Stage 1 から開く。**

### engine と schema を触らずに書けている

「1戦闘に1回」は、規則を持たない状態 `ultimate_spent`（表示名「必殺」）を自分へ付け、
「その状態が付いていないこと」を発動条件にすることで表した。「隊の誰かが削られていること」も
既存の `target_exists` + `hp_percent` で書ける。engine には必殺という言葉が一つも無い
（`ecology/ultimate.test.mjs` が engine.mjs / schema.mjs の本文を読んで確かめる）。
必殺技の定義そのものは固定 content に入れず、遠征ごとの装備と同じように
`runContentBundle` が bundle へ混ぜる。だから validator が毎回通り、契約 ID の表は増えない。

## 9. 採らなかった案（再提案する前に読む）

全過去 pack を毎回累積する／Stage ごとに pack を全交換する／pack は固定するが新 pack を
保証しない／敵数値だけを大幅に上げる／新 pack だけを極端に強くする／Stage ごとに正解
build を一つ登録する／回復役を削除する／自由回復を残して敵を round ごとに強化する／
12戦を一つの HP pool で通す／結果を隠して緊張感を作る／未来の system を全て先に実装する／
作者 Gate 前に content 量を増やす／将来使うかもしれない語彙を空実装する／
必殺技を専用の技能表として作る／パッシブを必殺技の候補にする／補給を払って必殺ゲージを貯める／
必殺の発動権を隊で共有する／必殺技のために常設の画面枠を置く／必殺だけ回復の上限契約を破る／
必殺技の指定と構えを別々の操作として押させる／必殺技のチュートリアルでも時間を巻き戻す／
カットインを着弾と同じ拍に重ねる／カットイン専用のスキップ釦を足す。

いずれも一度検討して**採らなかった**案です。再提案するなら、当時の理由（`docs/HISTORY.md`）
と何が変わったかを添えてください。

### 生成装備の常時効果と発火効果（issue #210）

耐久は「装備の効果が何回働けるか」をプレイヤーが読める有限性として使う。生成装備の発火効果は
原則として毎回耐久1を払い、複数効果・多段・範囲は耐久2を払う。発火上限だけに有限性を任せず、
カードの消費表示と戦闘ログの残耐久を一致させる。

能力値補正は装着中の常時効果であり、イベントへ反応するactionではないので摩耗させない。
修理は耐久を払って同量を戻す自己相殺を避け、HPまたは防壁という別の有限資源を払う例外とする。
この区別により、耐久切れは「追加効果は止まるが、戦闘開始時から有効だった常時補正も次の
BattleStateでは壊れた装備として停止する」という既存engine契約と整合する。

## 8.13 判断の軸を分ける——装備はボス戦だけ、補給は遠征あたり固定（作者指摘 2026-09-12 / PR #255）

作者試遊の訴えは「装備を毎回選ぶのと、補給と比較するのが、思考負荷が高くてつらい」だった。

毎戦の勝利が3択（装備2 + 補給1）を出していた。**一つの画面に二種類の判断が混ざっていた**
のが問題で、装備どうしを比べる判断（効果の噛み合わせ）と、装備を捨てて補給を取るかという
判断（いまの安全と将来の出力）は、比べる尺度が違う。しかもそれが12戦のあいだ途切れない。

軸を分けて、片方を画面から外した。

- **装備は密度を下げる。**選ぶのはボス戦（4・8・12戦目）を突破したときだけにした。12戦目も
  外さない——12戦目もボス戦なので、そこを抜くと規則に穴が空く。遠征はそこで終わるが、
  拾った品は**精算で残す設計図の候補**（§8.14）になるので選ぶ意味は残る。結果として、
  装備を選ぶ場面は遠征あたり3回になり、一回ごとの重みが上がる。
- **補給は判断を一本にする。**遠征の開始時に3個で固定し、報酬で増やさない。表記も残り／
  総数（3/3）にした。残るのは「どこで使うか」だけで、「取るか取らないか」は消える。
  総数を動かすのはギルドの「開始補給」だけで、**遠征の外の判断**として別の場所に置いた。
- **必然的に、ボス戦以外の勝利は結果画面を挟まずキャンプへ戻る。**決めることが何も無い
  画面を一枚挟んでいた。直前の一戦の要約はキャンプの上端の一枚が預かる。設計の想定は
  「先見の予測がよほど悪くなければ、即次の戦闘に進む」である。

**負けたときの経路は変えていない。**敗北には決めることがある（再挑戦するか、精算するか）。

この変更で遠征あたりの回復量は大きく減った（以前は毎戦 +1 を取り続けられた）。後半が厳しく
なるのは意図した方向で、`analysis/ecology-stage3-builds.mjs` の測定前提も遠征あたり3個へ
合わせた。難度そのものの調律は作者試遊のあとに別途行う。

## 8.14 残す設計図は、最後の価値判断をレアリティへ渡さない（issue #151）

遠征終了時の Blueprint 保存は等級順の自動保存だった。装備の組み合わせを見つけるゲームで、
**最後の価値判断だけがレアリティに置き換わっていた**——今回の構成を成立させた低レア品より、
使わなかった高レア品が残る。

候補と上限を外へ出して選ばせる。設計上の約束は三つである。

1. **選ぶ余地が無いときに画面を増やさない。**候補が上限以下なら全部残るので、そのまま精算へ
   進む（「確認だけの画面」を作らない）。
2. **選ばなかった品は残らない。**埋まっていない枠を自動で埋めると、選ばせた意味が消える。
3. **残す前に全文が読める。**拾う前に読めるものを、残す前に読めなくしない。

候補の並びは等級 → 表示名 → id で決定的にする（取得順に依らせると、同じ遠征を同じように
遊んでも一覧の並びが変わる）。持込品は既に archive にあるので候補にしない。

**持ち帰れるのは、12戦を抜けて生還したときの1件だけにした**（勝利1・安全撤退0・敗北0。
作者判断 2026-09-12）。ボス戦だけで装備を拾うようになって候補が遠征あたり最大3件へ減った
のに保存数が2〜1のままだと、「見つけた品はだいたい残る」になって遠征の終わりの判断が
消える。撤退と敗北を0にしたのは**12戦を抜けることそのものに意味を戻す**ためで、確定した
活動資金を持ち帰る規則は変えていない——撤退は敗北ではない、という区別は資金と Stage 解禁の
側が持つ。

結果として、選択画面が出るのは**完走して2件以上拾った回だけ**である。毎回出ないのは意図した
ことで、出るときは必ず「どれかを捨てる」判断になる。持ち帰れない回は、精算画面が**なぜ
残らないのか**を書く（見つけた品が消えた理由が読めないと、拾った意味が分からなくなる）。

## 8.15 装備のコンボは、目録の穴を埋めて作る（作者指摘 2026-09-12 / PR #255）

作者の指摘は三つだった。「『回復が仲間全体につく』のに回復効果のない装備がある」
「ダメージ増加系の装備がない」「スキルやキャラとのコンボのワクワクがあまり感じられない」。

三つとも**組み立ての不具合ではなく、目録の穴**だった。

- **ダメージ増加が作れなかったのは trigger が無かったから。**`damage_proposed` を読める
  trigger は「自分が受ける直前」だけで、**与える側の直前を読むものが無かった**。払い先
  （`modify_pending_amount` の increase）は engine にあったのに、繋ぐ入口が無かったので
  一つも生成されない。`src_outgoing` と `pay_amplify` で繋いだ。
- **コンボが無かったのは、装備が自分だけで完結していたから。**隙も裂傷も技能が配るのに、
  それを読む語彙が装備側に無かった。条件（`cnv_exposed` / `cnv_bleeding`）と払い先
  （`pay_rend` / `pay_rupture`）を足して、**誰かが先に刻む構成の中でだけ強く鳴る**品を
  作れるようにした。AGENTS.md の「発生源・変換器・利得先を分け、閉じたレシピにしない」を
  装備側でも満たす形である。
- **「回復が全体につくのに回復効果がない」は量の問題だった。**keystone は元から heal を
  要求していたが、回復の基準値が barrier の 1/5（3/5/12）で、「全員へ届く」と書いてある
  のに実質ゼロだった。10/18/30 へ上げた。anti-stall の形（被弾 chain の中だけ・有限
  コスト・chain 1回）は変えないので、回復量はその攻撃で受けた傷が上限のままである。

**死に効果を作らないための規則も一つ増やした。**「刻んだ状態を読む払い先」は、敵を的にした
出来事の隣にしか置かない（`requires: ["enemy_target_alive"]`）。手当てや被弾を trigger に
した品へ付くと、隙も裂傷も配れないまま条件だけが並ぶ。

採ったのは、**`POSITIONS` そのままの3列×2行を上端に一つだけ置き、タブは操作だけをそこへ
掛ける**という形である。盤面の並び・行の見出し・格子は戦闘中の盤面と同じにした。キャンプで
見ていた並びが、そのまま戦闘の盤面になる。

- **セルが持つのは五つだけ。**顔と名前、HP（予測があれば開始→終了）、減少量と戦闘不能見込み、
  行動点／反応点の丸。**立ち位置は文字で書かない**——セルが盤面のどこにあるかがそれを出している
  （8.7.8 の「数で足りるものは数で、形で足りるものは形で」の続き）。
- **空き枠は残す。**5人未満のとき、どこが空いているかは情報である（前3後2 と 前2後3 の違いが
  まさにそれ）。戦闘盤の `unit-empty` と同じ扱いにした。
- **金の枠は「いま操作の主語である」の意味だけに使う。**隊列モードでは動かす一人、技能・装備
  タブでは技能点と装備枠を出している一人が光る。
- **補給タブは、通常はセルを押せない形にする。**誰を選ぶ場面でもないのに押せる形にすると、
  押した結果を予想できない。集中治療・蘇生を選んだあいだだけ対象選択になり、**対象になり得ない
  仲間も消さずに薄く残す**（消すと、誰が候補になり得るのかが読めない）。単体治療の対象を
  engine 側が自動で決めるのもやめた——補給1を払う先は、プレイヤーが指す。

集計値も同じ主語へ揃えた。**同行者の人数は、固定の区画では分母を出さない**
（`2 / 2人` の分母は「まだ入れられる」と読めるが、その回は誰も足せない。作者指摘 2026-09-08）。
**スキルタブの残り技能点は隊全体の合計**にした——選んでいる一人の残点では、他の誰かが
使い残していることがこの画面から読めない。**装備タブの比は、装着済みの総数を、手元の装備数と
枠の総数の小さいほうで割る**——所持が足りなくても枠が足りなくても、埋めきれば `X/X` になる。

隊列の選択は**誰も選んでいない状態**で開く。先頭の仲間を選んだ状態で始めると、盤面のどこかが
最初から光っていて「もう一手目を打った」と読める（作者指摘 2026-09-08）。

## 8.7.11 固定領域は、画面の三割を黙って取っていた（issue #235、作者試遊）

**「あそこ、fix なので、あまり大きいと画面が奪われてしまう」**（作者、2026-09-11）。

8.7.10 で上端へ置いた共通盤面は、正しい判断だったが**高すぎた**。iPhone 幅（390×844）で
実測すると、貼りついたままの `.camp-top` が 234px、そのさらに上に「安全に撤退する」と
「セーブ / ロード」の常設ボタンが 64px。**本文が始まるまでに 298px** で、ツールバーが出ている
実機では第一画面のほぼ半分だった。

作者は編成タブの廃止にも戦闘の主導線化にも「プロコンがある」と言った。どちらも**盤面か固定
ウィンドウを大きくする**からである。だから順番を変えた。**先に削れるものを削れば、
トレードオフは消える。**

- **常設ボタンの 64px は、トレードオフなしに消える。**撤退とセーブは遠征単位の操作で、
  準備タブと役が違う。旧「戦闘」タブを「遠征」に改め、次の一戦・撤退・セーブをそこへ集めた。

- **セルは4行積みを2行へ畳む。**出す情報は一つも減らしていない。名前の行へ AP/RP のピップを

  1セル 67px → 46px、固定領域 234px → 203px。
- **そのうえで編成タブは廃止できる。**このタブは実測で `scrollHeight` がビューポート
  ちょうど・本文230文字、つまり**スクロールする中身が無かった**。隊列操作は 8.7.10 で

結果、本文が始まるまで **298px → 203px（-32%）**。この節は 8.7.10 を否定していない。
**主語を一つにする判断はそのままで、その一つが占める面積だけを下げた。**

## 8.7.12 説明文は削り、ヘルプは残す（issue #236、作者方針）

8.7.8 が技能画面で確立した「文章ではなく形と色」を、他の画面へ広げた。**削る対象は画面本体の
説明文で、畳んだヘルプの中身ではない**（作者判断、2026-09-11）。必要な人が開ける状態は保つ。

削り方の規則は四つだけである。

- **同じ数を同じ画面で二度出さない。**「補給 3 / 5」は見出しの札とバーの頭に二つあった。
  装備の「手元 3 / 12」も見出しと折りたたみの札に二つあった。残すのは、その数が一番効く一方。
- **見出しが言っていることを、直下でもう一度書かない。**「技能ツリー」は見出しと summary に
  二つ、「ゴウの装備枠」は直上の人物帯が既に「ゴウ」と言っていた。
- **押せる形は、それ自体が説明である。**カードが並んでいる一覧に「選んでください」と
  書き添えない。金の主ボタンに「次の操作」の札を重ねない。**二手続きの操作で次の一手が
  要るときだけ**、一行を出す（装備を選んだあとの「装着する枠を選ぶ」など）。
- **数が言っていることを、文で言い直さない。**「獲得予定の活動資金: 250（到達 3 / 12）。
  負けても、ここまで確定した分は持ち帰ります」は、前半だけで足りる（後半はルールなので
  ヘルプにある）。勝敗カードの「この組み合わせは通りました」も、✓ と「突破した」の後では
  三度目である。

開発語も落とした。野営治療の一行は「一人をmaxHpの40%回復する。tank・背水役等、一人へ損傷を
集める構成向け」だった。**画面に出る文に `tank` も `roster` も要らない**ので「一人を最大HPの
40%回復」にした。数が構成の向き不向きを既に言っている。

同じ種類の敵が2体並ぶ回は、拾い屋の一行（`enemy-lore`）を最初の1枚にだけ出す。R12 §4.B が
置きたかったのは「この敵についての言い習わし」であって、同じ一行を2枚3枚と重ねることではない。

## 8.7.13 同じことを二通りに表さない——「取得済みだが未装着」の廃止（issue #236、作者試遊）

**「いま特に意味のない『取得済みだが未装着』という状態があって、いらないので、
そもそもこれを廃止できるならしてほしい」**（作者、2026-09-11）。

作者はこれを、技能ツリーの見た目の話として出した。取得済みを強調しようとすると、
**強調を2種類用意しなければならない**（取得済み・未装着と、装着中）。だが調べると、
これは見た目の話ではなかった。

技能枠には上限が無い（`SLOT_LIMITS` の `active` / `reactive` / `passive` は
`Number.MAX_SAFE_INTEGER`。上限があるのは装備の2枠だけ）。**取得したのに装着できない
場面が存在しない。**では未装着に何の意味があったかというと「出さない」ことで、それは
オン／オフが既にやっている。同じことを二通りに表していただけだった。

廃止できる条件は一つ、**engine から見てオフと未装着が同じであること**である。
`allyInput()` は tactics・reactives・passives のすべてを `enabled()` に通して
`disabled` を除いてから battle input を組む。必殺技も `enabled()` 後の列へ差し込む。
同じだった。だから廃止した。

置き換えで気をつけたのは一点、**既にある遠征の結果を動かさないこと**である。

- **プレイヤーが点を払って取った技能はオンで装着する。**払ったものがその場で回り始める。
- **starter の無償閉包で取得済みになる親の節は、オフで装着する。**これまで未装着だった
  ものをオンにすると、選んで取ったわけでもない技能が急に順番を食う。8.7.5 の
  「装着を増やすほど一本あたりの出番は減る」がそのまま効いてしまう。
- 旧い保存が持っている未装着の技能も同じで、読み込んだ時点でオフの装着済みへ揃える。

結果、通しの検査（tutorial 154 / trial 143）が出す勝敗・ラウンド数・被害は一つも動いて
いない。**表し方だけを変えた**ことの証拠である。

副産物として、技能欄が「取得した技能の一覧」になった。これまでは取得したのに
どこにも名前が出ない技能があり、作者が求めた「取得スキルがわかるように」は、
新しい表示を足すことではなく**この状態を消すこと**で満たされた。

`analysis/ecology-trial.mjs` の解禁の経路は、これまで一度も踏まれていなかった。
技能点は0で始まり戦闘をクリアして初めて貯まるので、キャンプに着いた直後の台本では
取得できる節が常に0個だったためである（`if` の中が丸ごと素通りしていた）。
保存へ点を入れてから踏むようにした。

## 8.7.14 物語の出来事を、システム画面の操作にしない（作者試遊 2026-09-11）

**「『時間がまきもどる』は本来めっちゃかっこいい演出なはずなので、こんなシステム画面の
一部にしてほしくないです。ノベルゲームみたいに、負けイベント会話の最後に、会話画面に
被せる形でど真ん中にボタンを配置してほしい」**（作者）。

置き場所が間違っていた。これまでの流れはこうだった。

    倒れた会話「届かなかった」 → 結果画面（✕ 足を止めた・味方HP損失・敵HP損失・
    反応発火・装備摩耗・戦闘後の状態・出した順番）→ その主操作［時間が巻き戻る］
    → 会話「もう一度、門の前」

杭を引いて時間を戻すのは**ゴウがその場でやったこと**である。会話の最後の行は
「腰の杭が鳴った。備蓄が一息で空になり、坑が来た道を逆にたどっていく」で、
物語はもう戻り始めている。そこへ勝敗カードと4つの数字を挟み、その下の
［次の操作］として釦を置いていた。**演出の真ん中に決算書が入っていた。**

新しい流れは三拍になる。

    倒れた会話「届かなかった」→（最後の行を読み終えた拍で、舞台に被さって
    ど真ん中に［時間が巻き戻る］）→ 会話「もう一度、門の前」

- **門は最後の行でしか出ない。**途中の行で出すと、読み飛ばすための釦になる。
- **押すまで越えられない。**舞台を叩いても AUTO でも進まない。ノベルゲームの選択肢と
  同じ置き方で、ここは「読む拍」ではなく「決める拍」だと形で言う。
- **文字送りが終わるまで出さない。**最後の一行を読み終えた瞬間に現れる、という間
  そのものが演出なので、CSS（`.vn.typed .vn-gate`）が出す。
- **結果画面は挟まない。**この経路から外した。損失の数字は、時間ごと無かったことに
  なる一戦には要らない。

**「この一戦は遠征に数えません」も消した。**結果画面が言っていた一行だが、この拍の
プレイヤーは活動資金をまだ一度も見ていないので読んでも意味が取れず、演出の真ん中に
システムの断り書きが立つ。答えは次の会話（「もう一度、門の前」）が、時間が戻ったこと
自体で返す。

**門は序盤の一戦専用にした。**通常の敗北で時間は戻らない——結果画面から編成を見直すか、
補給1で再挑戦するか、精算して終える（作者判断「他の敗北は、巻き戻ることなくタイトルに
戻るのが妥当です。先見機があるので、こんなことは詰みとタップミス以外には起きないはず」）。
だから `STORY_GATES` は1件しか持たず、増やす前提も置かない。汎用の仕組みに見えるのは
「beat の id で引く表」という形だけで、それは**二件目が要るまで一件で正しい**。

## 8.7.15 巻き戻しは、戻っていく過程を見せなければ成立しない（作者試遊 2026-09-11 / issue #200）

**「いまは押した瞬間次の会話に遷移していて、巻き戻っている感覚がないです。もっと演出を
強くしたいです」**（作者、8.7.14 の直後）。

8.7.14 で釦の**置き場所**は直った（結果画面の一項目から、会話の舞台に被さる一つの操作へ）。
だが押した先は普通の会話遷移のままで、「時間が巻き戻る」という**出来事そのものは一度も
画面に出ていなかった。**釦の名前が出来事を名乗っているだけで、起きたことは
「次の断片が表示された」である。

演出の中身は、**いま読んだ会話を逆に流すこと**に決めた。

    杭が鳴る … 腰の高さで一度だけ閃く（`.firing`）。ここでは何も動かさない
    逆走     … 読んだ行が、後ろの行から順に、末尾から消えていく。名前も立ち絵も
               行と一緒に戻る。画面は色を失い、走査線が上へ流れ、筋が右から左へ走る
    静止     … 誰も何も言っていない時点まで戻ったら、揺れも帯も止まり、色が戻る
    光       … 白へ抜けて、同じ朝（「もう一度、門の前」）が始まる

- **新しい台詞を足さない。**逆走に使うのは `state.story.log`（実際に読んだ行）だけである。
  読んでいない行を混ぜると、演出が新しい説明になる。逆走の材料が無ければ（履歴が空なら）
  演出は出ず、そのまま会話へ渡す。
- **読んだ行だと気づく一拍を置く。**行は全文で出てから消え始める（`REWIND_LINE_HOLD_MS`）。
  いきなり消し始めると、文字が減る動きだけが残って「さっき読んだ行」だと分からない。
- **止まる拍まで作る。**逆走が尽きた瞬間に切り替えず、名前も消して一拍静止する。
  ここが「ツグミがまだ何も言っていない時点」で、白へ抜ける前の底である。
- **演出は進行を止めない**（会話画面と同じ約束）。舞台を叩けばどこでも追い越せる。
  `prefers-reduced-motion` でも**逆走そのものは残す**——消すと何が起きたのか分からなく
  なるので、止めるのは揺れ・帯・筋・閃光と、文字が消える動きだけである。
- **状態は演出の前に巻き戻す。**演出は表示だけを持ち、途中でリロードしても進行を失わない
  （保存は phase を `story` へ寄せるので、再開は巻き戻し後の会話から続き、演出は二度出ない）。
- **スキップは門まで飛ばす**（作者指摘「スキップする時、そもそも『時間が巻き戻る』の
  ボタンまでのスキップにできませんか」）。スキップは「読むのをやめる」操作であって、
  **決める拍まで飛ばすものではない**——門は押すまで越えられないのに、スキップだけが
  越えられるのでは筋が通らない。飛ばした行は履歴へ積むので、**飛ばした人の巻き戻しも
  同じだけ材料を持つ**（逆走が一行で終わらない）。

長さは 2〜3 秒（`prefers-reduced-motion` では 1 秒ほど）に収めた。**物語のテンポを壊さず、
通常の会話遷移と区別できる**ことがこの拍の条件で（issue #200）、長い演出は二周目に邪魔になる。

この一件で、**一押しが二つ鳴っていた**ことも分かった。会話の門の釦は `.vn-stage`
（叩いて進む）の中にあるので、押すと釦と舞台の両方が反応し、巻き戻し後の会話の一行目
（「同じ朝。同じ光。」＝**時間が戻ったことを見せる行**）が読み飛ばされていた。
舞台に被せた操作は舞台へ落とさない、を handleAction の入口で守る。

## Build metadata

公開物の識別は、ソースへ時刻付きの生成ファイルをコミットして行わない。Cloudflare Pages の build command（`npm run build`）が、Pages が注入する `CF_PAGES_COMMIT_SHA` から無視対象の `core/build.generated.mjs` を作る。

`BUILD` はデプロイされたコミットを特定する運用メタデータ、`FINGERPRINT` はルール・content の互換性を表す source-controlled な契約版である。前者はpreviewの古い配信を検査で拒否し、D1のプレイ記録を版ごとに分けるために残す。後者は意味が変わったときだけ更新する。生成sidecarをPRへ含めないことで、build印だけが原因のブランチ間コンフリクトをなくす。
